# Процедура полной проверки

## Состояние

Скрипт хранит состояние в служебном пути Git, полученном через
`git rev-parse --git-path`. Этот путь работает для обычного клона и отдельного
рабочего дерева и не входит в область `git add`.

Допустимые состояния:

- `running`
- `waiting_decision`
- `blocked`
- `interrupted`
- `complete`
- `complete_with_accepted_risks`

Перед каждым содержательным действием открой одно применение командой
`start-application`. Оно связывает ровно одну возможность или проблему с
областью охвата, способом, проверяемой поверхностью, точным действием, снимком
Git и версией входа возможности. После действия закрой его командой
`finish-application`.

Снимок Git включает содержимое, вид и признак исполняемости рабочего файла, а
также режим и объект индексной записи. Поэтому изменение исполняемости или
gitlink подмодуля прерывает применение так же, как изменение содержимого. Версия
входа возможности включает её поставляемую классификацию. Изменение области,
вида участия или применимости делает прежнее применение устаревшим. При первом
переходе от хеша только файлов неизменная классификация получает составной хеш
без потери прежнего решения. Этот переход не скрывает последующие изменения
контракта.

Успешное завершение требует:

- отдельного применения для каждой возможности или проблемы
- наблюдаемого артефакта либо команды с кодом завершения
- содержательного свидетельства, объясняющего наблюдаемый результат
- решения `accept` для метода `review`
- неизменного снимка Git между началом и завершением применения

Успешное применение проверочной возможности (`check`) дополнительно требует:

- описания фактически проверенного охвата через `--coverage`
- одного или нескольких проверяемых выводов через `--claim`
- хотя бы одного предметного артефакта через `--artifact`

Смысловым считается любой метод `review`, а также любая проверочная возможность
в областях `requirements` и `design`, даже если для неё указан метод
`validation`. До её начала объяви способ обнаружения предметной области:

- `--subject-index <файл>` добавляет индекс и связанные из него локальные
  Markdown-файлы
- `--subject-pattern <шаблон>` добавляет все совпавшие файлы рабочего дерева
- `--subject <файл>` добавляет отдельный файл, но не заменяет обнаружение
  полного класса документов

Контроллер сохраняет способ обнаружения и развёрнутый набор файлов. Для
поэтапной перепроверки требований и другого полного смыслового прохода ручной
перечень отдельных файлов без индекса или шаблона недопустим. Не называй область
шире развёрнутого набора.

Если хотя бы один критерий ограничен семантическим типом предмета, до начала
наблюдений составь таблицу охвата: каждому развёрнутому файлу назначь ровно один
тип через `--subject-type <файл>=<тип>`. Тип должен иметь применимый критерий.
Контроллер отклоняет наблюдение, если критерий не разрешён для типа файла.

Представление графа с ролью `navigation` подтверждает состав и путь к материалу,
но не входит в обязательный предмет смысловой проверки. Оно остаётся доступным
для проверки навигации и структуры. Канонические, поддерживающие и другие
ненавигационные представления проверяются по смысловым критериям полностью.

После начала отдельно запиши наблюдение по каждому предметному файлу:

```bash
scripts/project_review.py record-observation \
  --application <применение> \
  --artifact <файл> \
  --start-line <начальная-строка> \
  --end-line <конечная-строка> \
  --criterion-id <критерий> \
  --result supports|problem|not_applicable \
  --note '<наблюдаемое содержание и его значение>'
```

Не изменяй состояние контроллера напрямую: ни вручную, ни через интерпретатор,
импорт `project_review.py` или сгенерированный скрипт. Только
`record-observation` создаёт наблюдение и его запись в журнале контроллера.
Наблюдение без такой записи не является доказательством и не может закрыть
применение. Если состояние было изменено в обход команд, не продолжай этот
проход: начни новый цикл через `restart` и повтори затронутую проверку.

Открытая блокирующая находка останавливает несвязанную предметную работу.
До следующего `start-application` подготовь решение по этой находке или
выполни одну из проверок, нужных для решения. Нельзя продолжать код, тесты,
документацию или другую независимую область, пока блокер не получил решение,
не исправлен и не перепроверен. Это ограничение действует для любого вида
поверхности, а не только для документации.

Для возможности с поставляемыми критериями `--criterion-id` должен входить в её
контракт. Для собственного критерия дополнительно передай `--criterion` с его
формулировкой. Команда возвращает точный фрагмент и сохраняет его хеш, диапазон
строк, критерий, результат и предметное наблюдение. В `--note` назови
наблюдаемое положение и объясни результат: `supports` означает соответствие
критерию, `problem` — обнаруженный дефект, `not_applicable` — неприменимость
критерия к этому файлу с указанной причиной. Факт существования, чтения или
правильного формата файла не является смысловым наблюдением.

Критерий с охватом `each_subject` проверяется для каждого развёрнутого файла.
Критерий с охватом `surface` проверяется хотя бы на одном фрагменте набора. У
каждого предметного файла должен быть хотя бы один результат `supports` или
`problem`. `not_applicable` допустим для отдельного критерия с объяснением, но
не заменяет содержательную проверку файла. Результат `problem` требует записи
находки с параметром `--observation <идентификатор-наблюдения>`. Находка
создаётся до завершения активного применения. Несвязанное наблюдение не
позволяет закрыть применение даже с результатом `failed`. Результат `problem` не
допускает успешное завершение применения. Перед успешным завершением:

- свяжи каждый `--claim` с одним `--claim-support <идентификатор-наблюдения>`
- сформулируй возможное опровержение через `--challenge`
- передай его результат через `--challenge-outcome`
- свяжи опровержение с наблюдениями через `--challenge-support`

Попытка опровержения проверяет правдоподобное исключение, альтернативное
объяснение, противоречащее положение или отсутствующую связь. Успешный результат
допустим, только если опровержение отклонено (`--challenge-outcome refuted`).
Подтверждённое или неразрешённое опровержение требует находку, ограничения
результата или решения человека.

Предметный артефакт должен быть раскрыт из представлений онтологии и относиться
к проверяемому содержанию. Его включение не зависит от отслеживания или
игнорирования VCS. Если представление отсутствует, недоступно или спорно по
правилам VCS, до профильного применения создай `record-finding` без
`--observation`, затем подготовь запрос через `prepare-decision` и сохрани
решение пользователя. Файл контракта самой возможности, например
`SKILL.md` или описание роли, не считается предметным артефактом. Команда
форматирования, тестирования, проверки различий или другая общая техническая
проверка может быть дополнительным свидетельством, но не заменяет предметный
артефакт, охват и проверяемые выводы. Для обзора реализации и тестов успешный
запуск сборки, линтера или набора тестов не закрывает профильную проверку без
наблюдений по исходному коду или тестам, выводов с опорой на них и попытки
опровержения.

Свободная запись `passed`, общий вывод сразу о нескольких возможностях, ручной
перечень части документального класса, перечисление файлов без наблюдений и
структурная проверка вместо предметного применения не являются доказательством.
Участие `check` завершается результатом `passed`. Участия `constraint`,
`preparation` и `correction` завершаются результатом `applied`. Хеш применённой
возможности должен совпадать с её актуальным входом.

Состояние заменяется атомарно. Состояние прежней версии нужно обновить командой
`migrate`. Миграция удаляет результаты без обнаруженной предметной области,
критериального следа и обоснования приоритета, затем повторно открывает области.

## Онтологические зависимости

Если классификация возможности содержит `ontology_scope`, контроллер получает
целевые вершины из `.ai-dev-team/project-impact.json`, а не из шаблонов имён или
каталогов.
Целевыми становятся терминальные вершины указанного вида внутри текущей области
проверки. До их проверки контроллер требует успешные профильные применения для
каждой входящей вершины на полной глубине. Каждое применение должно охватывать
все обнаруженные представления соответствующей вершины.

Поля `paths` и `representations` графа раскрывают состав представлений, а его
связи задают обязательный частичный порядок проверки. Одновременно готовые
независимые вершины выбираются по ожидаемой пользе. Если граф отсутствует,
недействителен или не называет целевую вершину, онтологическая проверка не
начинается.

## Обязательное начало с концепции

Инвентаризация объединяет проекции одного компонента для разных клиентов.
Собственные компоненты получают участие из поставляемой классификации.
Компоненты зависимостей и проекта получают происхождение и доступные метаданные.

Первым исследовательским действием после определения корня и технического
снимка VCS найди в корневых инструкциях агента однозначный указатель на
концепцию. Указатель может вести на раздел `README.md`, отдельный документ,
короткий обзор раздела документации или набор документов. Не требуй
фиксированного имени или каталога.

После создания состояния зарегистрируй результат поиска:

```bash
scripts/project_review.py record-concept \
  --result found \
  --instructions AGENTS.md \
  --concept docs/concept.md \
  --evidence '<что в корневых инструкциях однозначно указывает на концепцию>'
```

Для концепции из нескольких документов первым `--concept` передай короткий
обзор, затем повтори параметр для каждой части. Контроллер проверяет, что
корневые инструкции и все названные документы доступны в рабочем дереве, а
точный путь к обзору присутствует в инструкциях. Включение спорного
представления определяет решение пользователя, выполняющего проверку.

Если концепция отсутствует, используй `--result missing`, передай проверенные
корневые инструкции через `--instructions` и не передавай `--concept`. Если
найдено несколько возможных представлений без однозначного указателя, используй
`--result ambiguous` и передай каждый документ отдельным `--concept`. В обоих
случаях добавь проверяемое `--evidence`. Контроллер сохраняет хеш инструкций и
найденных кандидатов, затем переводит полную проверку в заблокированное
состояние. Не продолжай так, как будто замысел проекта известен.

После результата `found` первым применением выполни только возможность проверки
концепции:

```bash
scripts/project_review.py start-application \
  --id concept-review-001 \
  --stage requirements \
  --capability skill:ait-docs-concept \
  --method review \
  --surface '<все найденные части концепции>' \
  --action '<содержательно проверить концепцию>' \
  --priority-rationale '<обязательное смысловое основание остальных областей>' \
  --subject docs/concept.md
```

Для набора документов повтори `--subject`. Точный идентификатор возможности
возьми из инвентаризации, не копируй его из примера. Предмет применения должен
включать все документы, зарегистрированные через `record-concept`.

Проверь по профильным критериям:

- согласованную связь проблемы, цели, способа достижения и ожидаемого итога
- существенные рамки, только если без них замысел становится неоднозначным
- внутреннюю согласованность и различие текущего состояния, цели и желаемого
  свойства
- отсутствие подмены концепции нормативным функциональным контуром, запретами
  или критериями приёмки

Применение подчиняется полному договору смыслового следа. По каждому документу
нужно предметное наблюдение. Каждый вывод связывается с наблюдением и
проверяется правдоподобным опровержением. Чтение для ориентирования,
существование файла, форматирование, проверка структуры и общая самооценка не
завершают барьер.

Только после успешного результата `passed` и решения проверки `accept` получи
минимальное понимание:

- для чего существует проект и для кого
- какой ожидаемый результат и существенные рамки выражает замысел
- где закреплены требования, решения и другие авторитетные основания
- какие зависимости могут обесценить последующую проверку

Это понимание служит выбору дальнейшей работы. Оно не заменяет отдельную полную
проверку README, требований или решений и не задаёт их обязательную
последовательность.

Неуспешное применение сохраняет смысловой след и связанные находки, но не
открывает остальные области. До решения по находкам, исправления проблем
концепции и последующей повторной профильной проверки всего зарегистрированного
состава другие предметные области недоступны.

## Обязательная проверка корпуса после концепции

После успешной проверки концепции не сравнивай остальные области по приоритету.
Вторым этапом найди корпус знаний по правилам и договору проекта и зарегистрируй
результат:

```bash
scripts/project_review.py record-knowledge \
  --result found \
  --root knowledge \
  --evidence '<как установлен корень и полный доступный состав корпуса>'
```

Если проект не объявляет корпус, используй `--result absent` без `--root`.
Зафиксируй отсутствие как ограничение, но не имитируй проверку несуществующих
источников. Для внешнего корпуса в режиме `peer` предметом остаются локальный
договор, индекс и доступные утверждения с трассировкой до исходных артефактов.
Полная проверка репозитория не получает внешние материалы вне разрешённого
проектом способа доступа.

При результате `absent` не передавай `--knowledge-phase` никакому применению.
Техническую и смысловую фазы можно передавать только найденному корпусу и ровно
зарегистрированной возможности `kc-validation` в области `repository`.

Для найденного корпуса сначала проведи минимальный технический допуск:

```bash
scripts/project_review.py start-application \
  --id knowledge-technical-001 \
  --stage repository \
  --capability skill:kc-validation \
  --method validation \
  --knowledge-phase technical \
  --surface '<полный допускаемый состав корпуса>' \
  --action '<проверить возможность достоверного смыслового прохода>' \
  --priority-rationale '<обязательный второй этап после концепции>' \
  --subject-pattern 'knowledge/**'
```

Точный идентификатор возможности возьми из инвентаризации. Допуск устанавливает:

- полный состав корпуса, допускаемый к автоматической проверке, и читаемость
  его договора
- доступность источников и утверждений
- прослеживаемость утверждений до исходных или нормализованных артефактов
- ограничения доступа и публикации
- препятствия безопасности по операционной проверке `kc-validation`

Не расширяй допуск до полной формальной проверки. Неизвестный состав,
недостоверное происхождение, недоступное содержание или препятствие безопасности
останавливают смысловую фазу. Несущественный формальный дефект получает
неблокирующую находку, точную границу непроверенного состава и ограничение
выводов.

После допуска обязательно проверь доступный корпус относительно концепции.
Запусти ту же профильную возможность способом `review` и передай
`--knowledge-phase semantic`. Обнаружь предмет через договор, индекс или
корневые шаблоны. Охвати каталог, слой понятий, карточки всех источников, прямые
и производные утверждения.

Не передавай для смысловой фазы общий шаблон вроде `knowledge/**`. В него
попадают заголовки HTTP, двоичные вложения и другие технические представления,
которые не являются источниками, утверждениями или понятиями. Для корпуса с
переносимым договором используй отдельные шаблоны:

```bash
--subject-pattern 'knowledge/corpus.yml' \
--subject-pattern 'knowledge/catalog.yml' \
--subject-pattern 'knowledge/concepts.yml' \
--subject-pattern 'knowledge/**/source.yml' \
--subject-pattern 'knowledge/**/statements.yml' \
--subject-pattern 'knowledge/**/derived-statements.yml'
```

Контроллер отклоняет предмет, в который вместе с этими представлениями попали
технические или двоичные файлы. Для нестандартного договора сначала явно
обнаружь его содержательные представления и передай только их.

По каждому источнику проверь:

- связь с проблемой, целью и выраженными в концепции существенными рамками
  замысла
- связь нормативных границ, запретов и критериев с требованиями, решениями и
  правилами проекта
- согласованность утверждений с концепцией и другими источниками
- явные и скрытые противоречия
- пробелы охвата и ограничения выводов
- ценность как основания для решений и их обоснования

Запиши предметные наблюдения, свяжи с ними каждый вывод и проверь правдоподобное
опровержение. Только успешный смысловой проход корпуса открывает динамический
выбор остальных областей.

## Динамический план после концепции и корпуса

### Обязательные смысловые барьеры обнаруженного содержания

Полная проверка не может объявить применимым только удобный поднабор навыков.
Классификация активирует следующие барьеры по представлениям онтологии и
материалам рабочего дерева:

- `.ai-dev-team/project-impact.json` требует смысловой проверки истинности узлов, рёбер,
  охвата и транзитивного влияния графа, а не только запуска его валидатора,
- обнаруженный каталог требований требует поэтапной перепроверки всех его
  документов, их смысла, оснований, проверяемости и согласованности,
- документация требует полного аудита структуры и отдельной проверки качества
  каждого документа, его назначения, авторитетности и понятности читателю,
- материалы о персонажах или UX требуют проверки различимости персонажей,
  их целей, контекста и трассировки до сценариев и решений продукта.

Контроллер сам делает эти возможности применимыми и требует весь набор файлов,
который соответствует их шаблону. Агент не может снять барьер решением
`not_applicable`, заменить полный класс одним примером или завершить его
формальным результатом. Если структура проекта нестандартна и шаблон не находит
предмет, агент обязан обнаружить такой класс по индексу, правилам или содержанию
и классифицировать профильную возможность как применимую с объяснением.

Для каждой внешней возможности модель определяет:

- вид участия: `check`, `constraint`, `preparation`, `correction` или
  `not_applicable`
- область охвата, если участие относится к ней
- применимость к текущему репозиторию
- краткое основание

Недостаточное описание даёт `unknown`. Такой компонент остаётся препятствием,
пока человек или доступное основание не позволят его классифицировать.

Поставляемая классификация может задать для проверки `decision_paths`. Эти
шаблоны связывают проверку с путями группы, к которым её нужно применить до
решения человека. Например, находка с разрешённым путём `README.md` требует
применить профильные проверки README и пользовательского текста именно к этому
файлу. Шаблон не задаёт глобальную очередь и не связывает проверку с другими
путями.

## Выбор следующей работы

После обязательных проверок концепции и корпуса и после каждого следующего
содержательного результата сравни оставшиеся применимые возможности, открытые
проблемы и проверки исправлений. Выбери работу с наибольшей ожидаемой пользой
для проекта при доступном времени. Оцени:

1. возможное влияние на смысл, жизнеспособность, пользователей и рабочие
   процессы проекта
2. широту последствий и число решений или артефактов, которые могут оказаться
   неверными
3. способность проблемы обесценить или заблокировать другую работу
4. вероятность проблемы и достоверность доступных свидетельств
5. время до проверяемого результата и стоимость проверки или исправления
6. ценность результата, если процесс прервётся сразу после текущего действия

Это критерии суждения, а не формула баллов. Сохрани в `start-application`
краткое `priority_rationale`, которое объясняет выбранный компромисс. Не
обосновывай выбор только порядком области, простотой команды, наличием
автоматического валидатора или удобством закрыть формальный дефект.

Если проблема делает конкретное основание недостоверным, не выполняй зависящую
от него работу. Это не запрещает выбрать независимую работу с большим ожидаемым
влиянием. После новой находки, исправления, решения человека или изменения
снимка сравни кандидатов заново.

## Области охвата

Техническое поле `stage` хранит область применения возможности. Массив `stages`
хранит состояние полноты по всем областям. Порядок его элементов нужен только
для устойчивого вывода и не определяет план проверки.

### `repository`

Состав репозитория, правила, настройки, корпус оснований, структура и
воспроизводимость.

### `requirements`

Цели, направляющие положения, требования, критерии, ограничения, согласованность
и трассируемость.

### `design`

Архитектура, значимые решения, пользовательский опыт, дизайн, интерфейсы и их
связь с требованиями.

### `code`

Реализация, границы, обработка ошибок, данные, зависимости и соответствие
принятым решениям.

### `tests`

Тестовая стратегия, покрытие рисков, регрессионные проверки, воспроизводимость и
диагностическая ценность отказов.

### `assurance`

Безопасность, надёжность, эксплуатационные материалы, лицензии, персональные
данные и пользовательская документация.

### `impact`

Повторная инвентаризация и снимок, связи и влияние всех исправлений на
требования, дизайн, код, тесты, документацию, планы, качество и риски.

Конечный переход повторно вычисляет живой снимок Git и отпечаток инвентаризации.
Несовпадение требует `refresh` и не допускает конечный статус.

## Проблемы и группы

Проблема имеет устойчивый идентификатор, область охвата, серьёзность, признак
блокировки, свидетельства и статус. Связанная группа дополнительно задаёт:

- основную причину
- последствия
- точные разрешённые пути изменения
- команду или наблюдаемый способ проверки

Одно согласие разрешает всю группу. Выход за разрешённые пути требует нового
решения. Внешнее изменение переводит процесс в `interrupted`.

Перед показом группы контроллер сопоставляет её разрешённые пути с
`decision_paths` применимых возможностей. Группа готова к решению, только если
каждая найденная проверка завершена на текущем снимке и её предметные артефакты
охватывают связанные пути. Завершение проверки с найденной проблемой считается
применением, но требует пересобрать причину, состав, границы и способ проверки
группы. Неприменимость должна быть зафиксирована классификацией, а не пропуском
применения.

До готовности группы состояние остаётся `running`. Контроллер отклоняет
`waiting_decision` и `record-decision` с перечнем незавершённых проверок. Такой
барьер не требует выполнять проверки, чьи `decision_paths` не совпали с путями
группы.

Если после успешной проверки исправления `refresh` обнаружил только пути из
одной или нескольких явно согласованных групп, прими снимок, ожидающий принятия.
В одном вызове передай параметр `--finding` для каждой группы:
`accept-snapshot --finding <идентификатор-1> --finding <идентификатор-2>`.
Каждая указанная проблема должна иметь решение `fix` и успешную проверку.
Успешная проверка должна быть записана для самого снимка, сохранённого при
прерывании, а не для предыдущего содержимого. Команда сопоставляет текущую
область Git с этим снимком и отклоняет принятие, если область с тех пор
изменилась или содержит пути вне границ выбранных групп.

Если человек явно подтвердил внешние изменения как новое входное состояние,
перечисли каждый подтверждённый путь отдельным параметром
`--external-path <путь>` и запиши основание через `--external-reason <текст>`.
Эти параметры можно сочетать с `--finding`. Контроллер отклоняет отсутствующие в
изменении, неподтверждённые и добавленные после подтверждения пути, а также
пустую причину и причину без внешних путей. Событие принятия хранит
идентификаторы прежнего и принятого снимков, точные пути и основание решения.
Принятие обновляет вход проверки, но не означает одобрения содержания файлов.

Перед принятием снимка передай изменённые пути и аспекты в
`ait-impact-analysis`. Для каждой области из `review_stages` результата добавь
`--reopen-stage <область>`, а в `--impact-rationale <текст>` сохрани пути
влияния и итоги профильных проверок. Контроллер повторно открывает только
перечисленные области. Выполнявшуюся во время изменения область нельзя сохранить
как незатронутую. Активное применение прежнего снимка становится
недействительным, после принятия снимка его нужно начать заново. Завершённые
независимые области и их применения остаются связанными с прежним входным
снимком.

## Повторное использование результата

Не выполняй область повторно, если одновременно неизменны:

- снимок проверенных файлов
- состав и версии применённых возможностей
- версия процедуры
- решения, от которых зависит результат

При изменении состава сначала классифицируй новые возможности. Новая применимая
проверка повторно открывает назначенную область. Остальные области открывай по
полному транзитивному результату общего графа проекта, а не по отдельному
ручному выводу внутри полной проверки. Завершённые независимые области сохраняют
применения, связанные с их зафиксированными входными снимками. Неизвестная
возможность переводит процесс в `blocked`. Применимая возможность всегда требует
назначенной области. Классификация последней неизвестной возможности возвращает
процесс к выбору работы и открывает её назначенную область.

Конечные состояния неизменяемы. Новый полный проход запускается отдельной
командой `restart`. Она доступна только после завершения, архивирует прежнее
состояние в служебном каталоге Git и создаёт новый цикл для того же рабочего
каталога.

## Сообщения человеку

Старт сообщает содержательную область, технический снимок VCS, результат поиска
концепции, её полный найденный состав, источники возможностей и режим
продолжения. Первой предметной работой он называет смысловую проверку
концепции, второй — проверку корпуса знаний. Обоснование фиксирует обязательность
этих оснований, а не изображает динамическое сравнение с техническими
кандидатами.

Запрос решения должен быть понятен как отдельное сообщение без предыдущей
переписки. Перед переходом к ожиданию решения создай его через контроллер:

```bash
scripts/project_review.py prepare-decision \
  --finding <проблема-из-группы> \
  --review-context '<полная проверка какого проекта выполняется>' \
  --checked-subject '<что именно проверено сейчас>' \
  --relation '<как этот предмет относится к полной проверке>' \
  --problem '<понятное описание первой проблемы>' \
  --impact '<последствия для проекта или достоверности проверки>' \
  --proposed-change '<что предлагается сделать>' \
  --decision-question '<какое одно решение требуется от владельца решения>'
```

Повтори `--problem` для каждой части группы, которую владелец решения должен
понимать до решения. Контроллер добавляет точную границу файлов и способы
проверки из находок, сопоставляет сохранённый снимок с живым репозиторием,
сохраняет запрос для текущего снимка и возвращает поле `message`. Передай это
поле человеку как основу ответа. Пока запрос не подготовлен, состояние остаётся
`running`. Прямой переход в `waiting_decision` запрещён.

`message` — короткий самодостаточный запрос, а не отчёт этапа. После контекста
полной проверки последовательно назови проблему, её последствие, предлагаемое
действие и один вопрос владельцу. Передай поле `message` без дополнений. Не
включай критерии приёмки, перечень проверенных и непроверенных областей,
остаточные риски, границу файлов, способы проверки и технические состояния.
Не убирай описание проблемы как повтор, даже если оно уже было в прежнем
сообщении. Описание проблемы поясняет проверенный предмет и его связь с полной
проверкой. Остальные сведения остаются в сохранённом запросе и выдаются только
по просьбе человека.

После первого сообщения ожидание решения приостанавливает автоматическое
продолжение. Не повторяй сохранённый вопрос, не сообщай, что ответа всё ещё нет,
и не меняй ожидание на блокировку из-за автоматических ходов без решения,
принятого через `record-decision`. Если такой ход создан средой, закончи его без
нового сообщения человеку.

Поля запроса отвечают на разные вопросы:

- `review-context` — какая полная работа выполняется и точное название проекта
- `checked-subject` — какой компонент, документ или процесс проверен сейчас
- `relation` — почему этот предмет входит в общую проверку
- `problem` и `impact` — что не так и чем это грозит
- `proposed-change` и `decision-question` — что будет сделано и что требуется
  решить владельцу решения одним ответом по всей группе

Внутренняя область `code`, слово «реализация», имя навыка, контроллера,
валидатора или файла не являются самостоятельным предметом сообщения. Сначала
назови продуктовую функцию понятными словами, затем при необходимости добавь
техническое имя как точный след.

Служебное состояние является техническим входом, а не готовым текстом для
человека. Не копируй из него `summary`, `evidence`, `next_action`,
идентификаторы проблем, коды состояний или требования без преобразования. Для
каждого технического обозначения найди понятное название либо кратко опиши его
смысл. Для каждого требования прочитай его заголовок. При каждом употреблении
технического обозначения показывай рядом понятное представление. Если
обозначение не нужно повторять, убери его или перестрой фразу. Перед отправкой
проверь каждое употребление в готовом сообщении: название другой сущности и
название при предыдущем употреблении не поясняют голое техническое обозначение
дальше по тексту. Точное обозначение добавляй в скобках, только если оно нужно
для ссылки, команды, воспроизводимости или следующего действия. Например, пиши
«проверка ожидает решения владельца (`waiting_decision`)» и «требование
„Качество пользовательских интерфейсов“ (ФТ-10) ошибочно связано с требованием
„Явный выбор клиентского инструмента“ (ПТ-3)».

Промежуточная сводка сообщает наиболее значимые найденные и исправленные
проблемы, охват, остаточные риски, обоснование следующей работы и следующий шаг.
В управляемом режиме она прямо говорит, что продолжение создаст хост. В ручном
режиме промежуточная сводка не завершает ход, пока доступно следующее безопасное
действие. Она сообщает о ручном возобновлении только при фактической остановке
по условию процедуры или пределу среды.

Сообщение о смысловом выводе называет проверенное правдоподобное опровержение:
исключение, альтернативный режим, противоречащее положение или недостающую
связь. Если опровержение не найдено в доступных предметных файлах, перечисли
проверенную область и не обобщай вывод за её пределы.

Остановка сообщает один требуемый следующий шаг.

Итог различает понятными описаниями полное завершение, завершение с принятыми
рисками и блокировку. Точные статусы `complete`, `complete_with_accepted_risks`
и `blocked` добавляет как технические обозначения состояния.

Успешный `validate` не является итогом полной проверки. Если контроллер отклонил
действие или процесс остаётся в `running`, `blocked` либо `interrupted`, сообщи
промежуточный результат и следующее действие. Не объявляй полный проход
завершённым до успешного конечного перехода.

При статусе `complete` итог связывает полный охват, результаты проверок и
исправлений с выводом о том, что в согласованной области не осталось выявленных
проблем. При принятых рисках, непроверенной области или препятствии итог прямо
ограничивает уверенность пользователя. Ни один статус не доказывает отсутствие
любого возможного скрытого дефекта.

## Разделение модели и скрипта

Контроллер выполняет повторяемую механику: технический снимок VCS, хеши,
происхождение компонентов, жизненный цикл одного применения, выдачу точных
предметных фрагментов, сохранение наблюдений и обоснования приоритета,
атомарную запись и проверку переходов. Анализатор графа отдельно проверяет
договор и вычисляет достижимость на полной глубине. Модель определяет аспект
изменения, применимость, критерий наблюдения, содержательный вывод, возможное
опровержение, группы исправлений, значимость и наиболее ценную следующую
работу.
