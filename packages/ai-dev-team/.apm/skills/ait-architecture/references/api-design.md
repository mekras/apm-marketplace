# Проектирование API

Основание в корпусе знаний — книга Сергея Константинова «The API Book» (`APIB`)
и книга Марка Массе «REST API Design Rulebook» (`RADR`). Пометки вида `APIB-001`
в тексте справки — идентификаторы утверждений этих источников, они приведены для
трассировки и не заменяют название источника в текстах для человека.

Используй этот файл, когда задача — спроектировать или развивать прикладной или
веб-API: интерфейс, которым пользуются другие команды или внешние разработчики.
Это стилезависимая справка, а не выбор по умолчанию: если у системы нет
публичного или межкомандного контракта, опирайся на `component-design.md` и
`quality-criteria.md`. REST, HTTP и JSON здесь — частая, но не единственная
форма, принципы проектирования и совместимости применимы и к другим протоколам.

API — это формальное обязательство связывать программируемые контексты. Его
потребители — инженеры, а ошибки и нарушения совместимости умножаются на число
потребителей. Поэтому цена ошибки в API выше, чем в обычном коде: плохое имя
исправить просто, неверно понятое назначение — почти невозможно.

## Проектирование сверху вниз

Проектируй API от смысла к деталям, а не наоборот. Порядок шагов и цена ошибки
растут к вершине:

1. **Область применения.** Сначала определи, какую проблему и для кого решает
   API. Проверь решение, задав вопрос «какую проблему мы решаем?» с ударением по
   очереди на каждом слове: нужна ли задача, наша ли это компетенция, адекватно
   ли решение.
2. **Уровни абстракции.** Раздели уровни так, чтобы каждый был самостоятельной
   промежуточной предметной областью, переводящей задачу из одного контекста в
   другой. Признак смешения уровней — одно поле, означающее разное в разных
   интерфейсах. Изоляция уровней усложняет интерфейс, но гибкость не бывает
   бесплатной.
3. **Области ответственности.** Сформулируй назначение каждой сущности.
   Модифицирующие операции переформулируй на каждом уровне — они не должны
   «перепрыгивать» уровни. Проверь номенклатуру, встав на место разработчика и
   попробовав написать код по сценариям использования.
4. **Конечные интерфейсы.** Опиши сигнатуры. Правила интерфейса применяй
   осмысленно, а не механически.

Критерии качества API: **очевидность** (как решить задачу), **читаемость**
(правильный код по номенклатуре) и **консистентность** (действие по аналогии).
Большинство проблем рождается не в начальном ядре, а при развитии.
Проектирование «на будущее» небесплатно: избыточные абстракции оправданы, только
если у API это будущее действительно есть, иначе это оверинжиниринг.

Правила конечных интерфейсов: имя сущности должно делать очевидными её действие
и побочные эффекты (за чтением нет модификаций), не экономь на именах, делай тип
поля ясным из названия, ошибки делай информативными, стремись к идемпотентности
операций, не изобретай собственную безопасность и явно декларируй технические
ограничения. Используй привычные, устоявшиеся механизмы взаимодействия:
собственный стандарт вместо существующего оправдан только явными и очевидными
преимуществами нового подхода.

**API-first.** В техническом смысле API-first означает, что контракт
(машиночитаемая спецификация, например OpenAPI или `.proto`) фиксируется до
реализации и определяет её. При расхождении контракта и реализации правится
реализация, а не контракт — это защищает партнёров, уже написавших код. Гарантия
действует только при качественном дизайне: неисправимая ошибка спецификации
вынудит нарушить приоритет контракта.

## Обратная совместимость

Совместимость — временна́я характеристика качества: код потребителей должен
продолжать решать свою задачу со временем. Это отличает разработку API от
разработки ПО вообще.

- **Слом совместимости — налог на потребителей.** Не ломай совместимость, если
  это возможно. По semver мажорная версия эквивалентна обратно несовместимому
  изменению. Срок поддержки версии увязывай с жизненным циклом приложений
  потребителей (золотое правило): переписать код им придётся не раньше, чем
  устареют сами приложения.
- **Минимальная публичная поверхность («ватерлиния айсберга»).** Выставляй
  наружу минимум функциональности, каждое публичное поле и метод — продуктовое
  решение и обязательство. Не легитимизируй серые зоны: либо функциональность
  гарантируется всегда, либо на её существование не намекают. Неявные
  договорённости (например, модель консистентности) фиксируй явно.
- **Расширение через абстрагирование.** Расширяй так, чтобы существующие методы
  становились частным случаем более общего интерфейса. Рассматривай каждую
  сущность как реализацию более общего контракта. Вышестоящие сущности должны
  быть информационными контекстами для нижестоящих — сообщать состояние и давать
  средства его менять, а не предписывать поведение. Эти приёмы узнаются как
  принципы SOLID, дополненные понятием уровней абстракции (см.
  `component-design.md`).
- **Слабая связность.** Сильная связность (попытка модифицировать чужую базовую
  функциональность) схлопывает чистоту интерфейсов, параметризуй взаимодействие,
  чтобы разорвать жёсткие зависимости. Изолируй сторонние зависимости
  программной обвязкой с точками расширения, а не проксируй чужой API «как
  есть». Тестируй именно формальные интерфейсы, включая «самоочевидные»
  инварианты.

Совместимость и версионирование пересекаются с разделами `quality-criteria.md` и
`component-design.md` — не дублируй их, опирайся на них.

## Паттерны дизайна API

Паттерны ниже касаются любого сетевого API независимо от протокола.

- **Устойчивость к исключениям.** В распределённой системе исключения на
  клиенте, сервере, в канале связи и у промежуточных агентов — норма жизни,
  клиенты должны уметь восстановить своё состояние после любого исключения.
  Ожидай не только сетевых ошибок, но и логических ошибок в коде партнёров,
  ошибки одного партнёра не должны приводить к отказу в обслуживании других.
  Нельзя полагаться на быстрое выполнение критических действий: многошаговые
  операции проектируй продолжаемыми с текущего шага.
- **Авторизация вызовов.** Два основных способа: операции от имени специального
  аккаунта-«робота» либо авторизация вызывающей системы целиком (API-ключи,
  подписи, сертификаты), они различаются гранулярностью доступа. Роботы требуют
  исключений из систем безопасности (обход капчи, длинные токены), ключи проще
  во внедрении, но гранулярные ограничения на уровне бизнес-сущностей заметно
  дороже и применяются редко.
- **Синхронизация и консистентность.** Идемпотентность снимает проблему
  повторной обработки запроса, но не все операции идемпотентны сами по себе
  (создание заказа). Пессимистичные блокировки в распределённых API почти не
  применяются: непредсказуемые задержки, отдельная подсистема сильной
  консистентности, «висящие» блокировки из-за чужого кода. Оптимистичное
  управление параллелизмом (версия, дата модификации, ETag) прячет сложность
  внутри системы, но требует от клиентов штатной обработки конфликтов версий.
  Опубликованную модель консистентности нельзя понижать, даже если она не была
  задокументирована. Гарантию «read-your-writes» реализуй передачей токена
  последней известной операции. Вероятность коллизии равна отношению задержки
  репликации к типичному интервалу повтора операции: для серверных клиентов фон
  ошибок существенно выше, такой фон маскирует настоящие ошибки и усложняет
  мониторинг.
- **Асинхронность.** Асинхронное задание вместо немедленного выполнения
  сокращает окно возможной коллизии. Но повсеместная асинхронность — единая
  точка отказа через общий сервис очередей, усложнение партнёрского кода, риск
  потери и дублирования заданий, размытие смысла SLA. Ограничивай асинхронные
  интерфейсы случаями, где они критически важны, и по возможности выражай их как
  статус ресурса, а не как отдельную сущность «задание».
- **Перебор списков.** Параметры limit/offset при изменяющихся данных приводят к
  пропуску и дублированию элементов, API должно давать способ получить полный и
  целостный набор. Для пополняемых списков используй перебор по монотонному
  идентификатору или курсору — он ещё и кэшируем. Курсор делай непрозрачным
  (закодированным): читаемый формат курсора становится публичным контрактом и
  мешает менять нижележащую технологию.
- **Push против опроса.** Периодический опрос (поллинг) — всегда компромисс
  между отзывчивостью и нагрузкой. Доставка push-уведомлений на устройства
  никогда не достигает 100% — используй push как триггер внеочередного опроса, а
  не замену ему. Для канала backend-to-backend в публичных API практически
  безальтернативен `webhook`, произвольный URL обратного вызова — вектор атак
  (перехват данных партнёра, канал DoS, SSRF на инфраструктуру провайдера),
  поэтому смена адреса требует усиленной авторизации (например, второго
  фактора). Учитывай лимиты размера сообщений, если уведомление содержит лишь
  ссылку на событие, различай статусы «доставлено» и «обработано» — иначе
  теряется мониторинг состояния интеграции.
- **Массовые операции и частичные обновления.** Для массовых изменений есть
  четыре варианта гарантий (атомарность с идемпотентностью, идемпотентность без
  атомарности, ни того ни другого, запрет перезапросов через ревизию), и каждый
  определяет, какой код придётся написать партнёру. Атомарный эндпойнт с одним
  неисправимым подзапросом блокирует и валидные — эндпойнты массовых изменений
  нежелательны как класс, если они есть, ответ обязан содержать разбивку по
  подзапросам. Наивные частичные обновления через «магические» значения полей
  перекладывают вычисление разницы на клиента и ломаются, когда результат
  зависит от порядка операций, надёжнее декомпозиция на независимые
  идемпотентные суб-эндпойнты. «Настоящее» совместное редактирование требует
  отдельного гранулярного формата изменений с явной политикой разрешения
  конфликтов.
- **Предсказуемость и деградация.** Для партнёра предсказуемость API — не низкий
  процент ошибок, а ясность из документации и номенклатуры ошибок, какие
  проблемы возможны и какой код писать для их обработки. Включай в ошибку
  рекомендации по восстановлению отдельно для пользователя и для разработчика,
  документируй некритичность отдельных ошибок, предусматривай понятное поведение
  по умолчанию для неизвестных клиенту ошибок, включая транспортные.

## HTTP API: терминология и выбор технологии

- **«REST API» не имеет консистентного определения.** Диссертация Филдинга
  (2000) — абстрактный обзор ограничений распределённой архитектуры, не
  привязанный к HTTP и URL и не содержащий правил дизайна. Шесть ограничений
  REST (клиент-сервер, stateless, разметка кэшируемости, стандартные интерфейсы,
  многослойность, code-on-demand) полезны как принципы. Трактовке Филдинга-2008
  (никакого априорного знания об API, всё через гипермедиа — HATEOAS) не
  удовлетворяет ни одна реально существующая система. Практичный рабочий термин
  — «HTTP API» (JSON-over-HTTP): HTTP 1.1+, JSON, URL и семантика вызовов по
  стандарту, без сознательных нарушений веб-стандартов. Оси при этом
  ортогональны: REST — архитектурный стиль, HTTP — прикладной протокол. «HTTP
  API» здесь — категория дизайна, а не транспорта: API, туннелирующее вызовы
  процедур поверх HTTP (SOAP, JSON-RPC через POST), использует HTTP лишь как
  транспорт и HTTP API в этом смысле не является.
- **Главный принцип HTTP API** — разрабатывать API так, чтобы промежуточные
  агенты (клиентские фреймворки, прокси, API-гейтвеи) могли читать и
  интерпретировать метаданные запроса и ответа без дополнительного кода.
  Обратная сторона: агенты действуют по метаданным и без ведома разработчика и
  могут трактовать их неверно.
- **Выбор технологии.** Для публичных API JSON-over-HTTP — выбор по умолчанию:
  сжатие практически нивелирует разницу в размере с бинарными форматами, а
  оптимизированные десериализаторы снимают проблему разбора. gRPC даёт
  contract-first и кодогенерацию ценой сложности отладки и слабой поддержки
  браузеров. GraphQL уместен в насыщенных разнородными данными областях, но
  внешние GraphQL API — экзотика: с ростом данных и запросов сервисом сложно
  управлять. В ресурсоориентированной парадигме клиент не вызывает процедуру, а
  применяет одну из стандартных операций к ресурсу по его адресу, клиент и
  сервер принципиально не имеют разделяемого состояния — все параметры
  передаются явно в каждом запросе.

## HTTP API: семантика и организация

Актуальная семантика HTTP — RFC 9110 (кэширование — RFC 9111, метод PATCH — RFC
5789).

- **Глаголы.** Каждый глагол однозначно задаёт семантику и свойства: GET
  безопасен и идемпотентен без тела, PUT заменяет ресурс целиком, идемпотентен,
  DELETE идемпотентен, POST и PATCH не безопасны и не идемпотентны. URL — ключ
  кэширования для GET и ключ идемпотентности для PUT/DELETE, GET, PUT и DELETE
  над одним URL обязаны быть симметричны. Частые антипаттерны: модифицирующие
  операции за GET (кэширование и автоповтор агентами), неидемпотентные — за
  PUT/DELETE. Соответствие CRUD-операций глаголам — лишь мнемоника: выбирай
  глагол по семантике из стандарта. HTTP-клиенты автоматически повторяют только
  немодифицирующие запросы (GET, HEAD, OPTIONS).
- **Статус-коды.** Неизвестный клиенту код `xyz` по спецификации обрабатывается
  как `x00` той же группы — учитывай это при вводе нестандартных кодов. Коды 4xx
  по умолчанию не кэшируются, кроме 404, 405, 410 и 414. Разные части запроса
  имеют разные общепринятые стили записи имён (kebab-case в домене, заголовках и
  пути, snake_case в query, snake_case или camelCase в теле) — единый стиль во
  всех частях невозможен.
- **Ошибки.** Каждому из трёх акторов (пользователь, клиент, сервер) нужны
  ответы на четыре вопроса: кто ошибся, чинится ли повтором, чинится ли
  переформулированием, что делать иначе. Повтор 4xx обычно бессмыслен, кроме 429
  и 404 (по стандарту — «состояние неопределённости», персистентное отсутствие —
  410). Возврат 401 без заголовка `WWW-Authenticate` — де-факто стандарт,
  формально противоречащий спецификации. Практический базовый набор: 400
  (валидация), 403 (авторизация), 404 (не найдено или скрытая причина), 409
  (конфликт), 410 (удалено), 429 (лимиты). RFC 9457 (Problem Details) покрывает
  только базовый сценарий — машиночитаемый формат деталей остаётся за вами.
  Стандарту полностью соответствует только смешанный подход: значимые
  статус-коды плюс детали в теле ответа.
- **Организация сервисов.** Делай запросы stateless: передавай контекст
  (например, `user_id`) явно, а не заставляй каждый сервис извлекать его из
  токена заново. Каждый сервис — чётко очерченная зона ответственности, чужие
  данные для него — только идентификаторы контекста. Кэширование строй на
  ревизиях ресурса: `ETag` и условный GET с `If-None-Match` (304), оптимистичная
  конкурентность — `If-Match` (412). При полностью stateless-запросах и
  правильном кэшировании промежуточный гейтвей становится необязательным звеном.
- **URL и CRUD.** Правила организации URL (path — строгая иерархия, query —
  нестрогие отношения и параметры) существуют только для читабельности —
  стандарты семантики этим частям не предписывают. Версию API размещай в пути —
  это вариант по умолчанию, если проект зафиксировал решением
  ресурсоориентированный REST-дизайн со сводом RADR как конвенцией, приоритет у
  правила RADR — версия не в URI (см. раздел ниже). Идемпотентное создание: POST
  с токеном идемпотентности, PUT с клиентским идентификатором или схема
  «черновик — подтверждение» (предпочтительна). Реальная номенклатура CRUD
  быстро растёт до ~8 URL и 9–10 методов, когда нужны контроль параллелизма,
  совместное редактирование, архивирование и поиск.
- **Итоговые рекомендации.** Последовательность проектирования: happy path →
  операции и номенклатура URL/методов → анализ ошибок и восстановления →
  функциональность уровня HTTP → спецификация с проверкой псевдокодом. Всегда
  возвращай корневой JSON-объект (задел на расширение, пустой объект или 204
  вместо пустой строки). Не изобретай формат передачи массивов и вложенных
  объектов в query — используй глагол с телом запроса. Поддержи OPTIONS и CORS,
  если API доступен из браузеров, закладывай защиту от типовых уязвимостей:
  CSRF, SSRF, HTTP Response Splitting, Unvalidated Redirects and Forwards.

## Правила веб-уровня (свод REST поверх HTTP)

Практический свод правил по «REST API Design Rulebook», степень «RESTful» удобно
оценивать по модели зрелости Ричардсона (уровни URI, HTTP, Hypermedia).
Модальность сохраняй (обязательно / следует / допустимо).

Область применения свода: проект явно зафиксировал решением (например, в ADR)
ресурсоориентированный дизайн веб-API и этот свод как свою конвенцию. Внутри
этой области порядок приоритета при расхождениях: действующие спецификации HTTP
(RFC 9110/9111) → RADR в вопросах стиля и конвенций (формат URI, архетипы
ресурсов, версия не в URI, представления, гипермедиа) → общие рекомендации APIB.
Без такого решения применяй разделы «HTTP API» выше как вариант по умолчанию.

- **URI и ресурсы.** Слеш `/` — для иерархии, без завершающего слеша, дефисы, а
  не подчёркивания, нижний регистр, без расширений файлов. Архетипы ресурсов:
  существительное в единственном числе для документа, во множественном — для
  коллекции и хранилища, глагол — для контроллера. Имена CRUD-функций в URI не
  используются — операцию задаёт HTTP-метод. Фильтрация и пагинация — через
  query (`pageSize`, `pageStartIndex`), сложную выборку выноси в контроллер с
  телом запроса.
- **HTTP-методы.** GET — получение (безопасный, без тела), HEAD — заголовки, PUT
  — вставка и обновление, POST — создание в коллекции и запуск контроллеров,
  DELETE — удаление, OPTIONS — метаданные взаимодействий. Не туннелируй методы
  через GET/POST.
- **Коды состояния.** Выбирай точный код, а не только 200. 2xx: 200 (успех с
  телом), 201 (создание), 202 (асинхронный старт), 204 (пустое тело). 3xx: 301,
  303, 304, 307, 302 не использовать. 4xx: 400, 401, 403, 404, 405, 406, 409,
  412, 415. 5xx: 500. Не передавай ошибки кодом 200.
- **Метаданные и кэширование.** Обязателен `Content-Type`, в ответы добавляй
  `Last-Modified` и `ETag`, для созданного ресурса — `Location`. Хранилище
  поддерживает условные PUT (`If-Match`, при несовпадении — 412). Поощряй
  кэширование (`Cache-Control` с `max-age`), кастомные заголовки не меняют
  поведение методов. Используй прикладные медиатипы и согласование через
  `Accept`.
- **Представления и гипермедиа.** JSON как формат по умолчанию, корректный и в
  camelCase, без лишних «конвертов». Единообразные формы ссылок, связей и
  ошибок, обязательная ссылка `self`. Минимизируй число точек входа (опирайся на
  docroot), ссылки — это контекстно-зависимое меню действий (HATEOAS).
- **Потребности клиентов.** Версию обозначай не в URI (`v2`), а через схемы
  (версии формы) и ETag (версии состояния), новый URI — только для нового
  концепта (при выбранной конвенции RADR это правило имеет приоритет над
  рекомендацией книги «API» размещать версию в пути — см. область применения
  выше). Защита ресурсов — OAuth или решения API management. Частичные ответы и
  встраивание связанных ресурсов — через query (`fields`), кросс-доменный доступ
  — CORS (чтение и запись), JSONP — устаревшая альтернатива только для чтения.

Учитывай возраст конкретных рекомендаций (свод сформулирован в `2012` году) и
сверяй с современной семантикой из разделов «HTTP API» выше и с действующими
спецификациями.

## SDK и UI-библиотеки

Когда поверх клиент-серверного API выпускается клиентская обвязка, различай два
вида инструментов: **SDK** — обёртка с высокоуровневым (обычно нативным)
интерфейсом к API — и **UI-библиотека**, с которой конечный пользователь
взаимодействует напрямую.

- **Что должен решать SDK.** Тривиальный слой — адаптация к платформе: форматы
  данных, стиль кода, парадигма ошибок, логика перезапросов с уважением
  `Retry-After` и растущих интервалов. Слой высокого порядка — разрешение ссылок
  на сущности вместо голых идентификаторов, подгрузка связанных объектов и
  кэширование, удобная подписка на серверные события, восстановление после
  ошибок бизнес-логики. Кодогенерация по спецификации (gRPC, OpenAPI) покрывает
  только тривиальный слой. Хороший SDK снижает число ошибок в клиентском коде,
  избавляет разработчиков от ненужного кода и даёт вендору контроль над
  интеграциями вплоть до бесшовной смены мажорных версий API.
- **UI-компоненты добавляют актора.** Появление конечного пользователя требует
  на порядок более глубокой проработки дизайна. Чем ближе интерфейс к сырым
  данным API, тем он обычно менее удобен. Внешний вид, реакция на действия и
  элементы UX должны переопределяться независимо, иначе типовые сценарии
  кастомизации конфликтуют. Трижды подумай перед программной настройкой
  UI-компонентов: полное разделение бизнес-логики, вида и UX-поведения может
  утроить иерархию абстракций SDK.
- **Декомпозиция и MV\*.** Прямые вызовы между подкомпонентами ломаются на
  первом же сценарии кастомизации, события снижают связность, но не устраняют
  взаимозависимость, а трансляция всех событий через родителя ведёт к
  бесконечным циклам. Решение — дополнительный уровень абстракции («composer»),
  не зависящий от реализации дочерних компонентов и модерирующий потоки данных и
  событий. Ограничение путей взаимодействия (подкомпоненты читают состояние,
  контроллер получает действия пользователя) даёт MVC, требование полностью
  описывать состояние в модели делает модель плохо версионируемой и
  сериализуемой, в MVP presenter не имеет собственного состояния и только
  вычисляет данные представления из модели.
- **Разделяемые ресурсы экрана.** UI-компоненты делят общий ресурс — экран и
  внимание пользователя, одновременные асинхронные вызовы требуют явной политики
  арбитража. Наивный булев флаг блокировки не масштабируется и может
  заблокировать интерфейс навсегда, используй явный захват блокировки с
  освобождением в `finally` и максимальным временем жизни, по истечении которого
  блокировка снимается автоматически.
- **Backend-Driven UI.** Получение с сервера готовой разметки или списка
  действий позволяет менять поведение клиента в реальном времени и экономит на
  публичной номенклатуре SDK, но требовательно к сети, а гибридный код,
  сочетающий серверное и клиентское состояние, сложнее чистого клиентского,
  заметных продуктов, целиком построенных в этой парадигме, нет. Не путай с
  серверным рендерингом (SSR): при SSR клиент способен извлечь из ответа
  семантические данные, в Backend-Driven UI ответ — «чёрный ящик».
- **Вычисляемые свойства.** Если свойство наследуется по нескольким иерархиям
  (данные и настройки отображения), нужны явные правила приоритета. Давай доступ
  не только к заданному, но и к реально вычисленному значению свойства и к
  событию его изменения.

Итог раздела в источнике: качественная UI-библиотека — отдельная и сложная
инженерная задача, не сводимая к автоматической генерации SDK по спецификации
или модели данных.

## API как продукт

Когда API публикуется наружу, он становится продуктом со своей аудиторией:
пользователи, бизнес-заказчики и разработчики, чьи интересы не совпадают. Это
влияет на архитектурные решения:

- запас прочности и SLA выше обычного: одна строка кода потребителя резко меняет
  нагрузку, а уязвимость API тиражируется на все приложения потребителей,
- для API недоступен дешёвый MVP — проверка гипотез требует, чтобы потребители
  вложились в код, помогает референсное приложение,
- нужна тестовая среда, симулирующая реальные действия и позволяющая
  автоматизировать тестирование на стороне потребителя,
- публикуй роадмапы (хотя бы условные), особенно при прекращении поддержки
  функциональности.

Документация — лицо продукта и часть его контракта. Формальная спецификация (в
том числе OpenAPI) не заменяет документацию — нужны словесные описания,
лаконичные примеры кода и короткий quick start (разросшийся quick start —
признак недоработки частотных сценариев). Подробнее о подготовке документации
см. навык `ait-writing`.
