# Сквозное выполнение задачи

Используй справку при построении маршрута задачи, которая проходит несколько
этапов до проверяемого результата. Она связывает существующие навыки
и помогает сохранить потребность, необходимые решения, выполнение, проверку
и передачу результата при переходах между ними.

## Выбрать необходимые этапы

Состав, порядок и глубину работы определяй по цели, критериям, рискам
и полномочиям. Найди применимые инструкции, навыки и процедуры целевого
проекта. Используй уже принятые ответы и решения без повторного согласования.
Необходимость уточнения определяй по оставшемуся пробелу в доступных сведениях.

Доставка, развёртывание, отдельная среда проверки и ответ внешнему инициатору
нужны только при соответствующем контексте задачи. Не предполагай наличие
конвейера сборки, тестового стенда, определённой VCS или процесса выпуска.
Поручение подготовить изменение само по себе не разрешает его публикацию.

Построй маршрут из применимых частей:

1. **Потребность и критерии.** Свяжи задачу с установленной целью. Определи,
   какой результат нужен и какие наблюдения покажут его достижение.
   При неясной потребности используй `ait-analysis`, при пробелах требований —
   нужные `ait-req-*`. Установи условия проверки до зависящей работы.
2. **Необходимые решения.** Найди действующие решения и открытые вопросы,
   которые влияют на выполнение. Значимый архитектурный выбор направь
   в `ait-architecture` и `ait-decisions`. При принятом в проекте SDD используй
   `ait-sdd` в его области. Продолжай после необходимых решений в пределах
   полномочий, сохраняя связь решения с критерием результата.
3. **Выполнение.** Выбери профильный навык для нужного артефакта. Для кода
   используй `ait-code-construction`, для выбора целостного рефакторинга —
   `ait-refactoring`, проверки разработчика —
   `ait-code-testing`, обзор готового кода — `ait-code-review`. Для документа
   примени профильный навык и `ait-writing`. После изменений выполни
   `ait-impact-analysis`. Если обнаружен дефект требования или решения,
   верни маршрут к соответствующему этапу.
4. **Доставка, если нужна.** По правилам проекта установи, куда и в каком
   состоянии должен попасть результат, каким способом и кто вправе это
   выполнить. Свяжи свидетельство доставки с конкретным артефактом или версией
   и местом назначения. Используй проектные навыки и средства доставки.
5. **Проверка результата.** Выполни выбранные проверки на нужной границе
   и в требуемых условиях. Для проверки поведения установи фактически
   используемую версию и среду. Сопоставь наблюдение с критерием, назови охват
   и ограничения. Используй уже имеющиеся достаточные свидетельства, если они
   относятся к проверяемому состоянию. Новая версия или изменение условий
   требует оценки актуальности прежней проверки.
6. **Передача.** Примени `ai-work-result-evaluation` перед передачей результата
   по шагу 5 маршрутизатора. Если по контексту нужен ответ инициатору, включи
   его подготовку в работу. Содержание проверь по `ai-human-communication`,
   форму и канал выбери по правилам проекта. Отправляй в пределах полученных
   полномочий. Уже выданное разрешение используй без повторного запроса.

Связь этапов сохраняй в существующем плане или следе задачи. Для каждого
перехода должно быть понятно, какое основание позволяет продолжить: критерий,
принятое решение, проверенный артефакт или результат проверки. Переход сам
по себе не даёт новых полномочий и не закрывает оставшиеся критерии.
Существенные возражения переноси между этапами и разрешай по разделу
«Значимость и глубина»
[порядка управления сложностью](complexity-in-software-development.md).

Сохранение состояния задачи не предписывает новый файл. Выбор существующего
представления, рекомендацию нового и решение человека о его создании выполняй
по разделу «Промежуточные артефакты»
[общего порядка управления сложностью](complexity-in-software-development.md).

## Различать достигнутые состояния

Выполненное действие подтверждает только проверенные свойства результата.
Для применимых к задаче действий различай:

- **Код или другой артефакт изменён.** Есть фактическое изменение нужного
  артефакта. Проверки исходников подтверждают только свой охват.
- **Изменение доставлено.** Есть свидетельство поступления конкретной версии
  в предусмотренное место. Назови это место: доставка в ветку и развёртывание
  в среде подтверждают разные состояния.
- **Поведение проверено.** Нужный сценарий выполнен на установленной версии
  в указанных условиях, наблюдаемый результат сопоставлен с критерием.
- **Ответ подготовлен или отправлен.** Назови фактическое состояние отдельно
  от состояния самого изменения. Текст ответа не подтверждает отправку,
  а отправка не подтверждает приёмку результата адресатом.

Для свидетельства укажи проверяемое свойство, артефакт или версию, условия,
способ проверки и наблюдение в достаточном для задачи объёме. Эти различия
не требуют заводить новые статусы в системе учёта целевого проекта.

Если требуемая проверка недоступна, сохрани её как невыполненную, назови
препятствие, ближайшее действие и его исполнителя. Продолжай доступную работу
в согласованных границах по правилам маршрутизатора. Недостаток полномочий
на доставку или отправку не мешает подготовить доступный результат, но
не позволяет объявить соответствующее действие выполненным.

## Пример границы свидетельства

Задача требует проверить исправление сохранения формы в определённой тестовой
среде. Код изменён, конвейер сборки завершился успешно. Это позволяет сообщить
об изменении и фактически пройденных проверках сборки. Для вывода о поведении
в требуемой среде ещё нужны свидетельства используемой версии и выполнения
сценария сохранения формы в этой среде.

Если конвейер сам выполнил нужный сценарий, используй результат конкретной
проверки с её версией, средой и наблюдением. Общего статуса успеха недостаточно.
При недоступной среде сообщи о непроведённой проверке и оставшейся работе.

Этот пример проверяет соответствие свидетельства заявленному свойству.
Для другой задачи нужные действия, условия и критерии определяет её контекст.
