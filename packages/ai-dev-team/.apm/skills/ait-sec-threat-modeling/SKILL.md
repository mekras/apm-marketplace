# ait-sec-threat-modeling

Помогай находить угрозы и меры до реализации, опираясь на модель системы, а не
на список модных средств защиты или реакцию на инцидент.

## Обязательная зависимость

- Используй `ru-lang` как базовый навык для русского текста. Если работа
  относится к разработке ПО, подключай набор «разработка».

## Когда применять

Навык применяется, если нужно:

- построить модель угроз для системы, сервиса, API, фичи или изменения,
- построить модель угроз использования или разработки ИИ как часть сквозной
  работы: сначала примени `ait-sec-ai`,
- проверить готовую модель угроз на полноту и связь мер с угрозами,
- выбрать метод поиска угроз (STRIDE, деревья атак, библиотеки атак),
- вывести меры и остаточный риск из найденных угроз.

## Когда не применять

- задача — только выбор механизма контроля доступа к API: применяй
  `ait-sec-access-control`,
- задача — аудит или рецензия уже реализованной системы: применяй
  `ait-sec-audit`,
- задача — выбор конкретного инструмента: применяй `ait-sec-tooling`.

## Обязательный порядок

При проверке готовой модели:

- Применяй шаги ниже ко всем запрошенным записям, включая те, выводы которых
  сохраняются. Для цепочки покажи основания каждого перехода и его состояние
  по [справке][chains]. Фраза «цепочка сохранена» не заменяет эту проверку.
- При запрете записи выдавай исправления в ответе, не пытайся править файлы.
  Ограничение записи не мешает завершить анализ и предложить исправления.
- Для находки укажи точный объект и поле, противоречащее свидетельство и
  минимальное исправление. Сохраняй прежние ID и связи при опровержении пути.
  Новую угрозу связывай отдельно, не стирая историю прежней угрозы и риска.
- Не переноси вопрос на другой объект. Отсутствие проверки меры не означает
  отсутствия её записи. Если принятие риска не подтверждено, предложи снять
  состояние «принят», оставив реакцию предложенной до решения человека.

1. Определи цель и границы: какую систему или изменение моделируем, что считаем
   защищаемым активом и какой нарушитель рассматривается.
2. Ответь на первый вопрос — **что вы строите**: построй модель системы. По
   умолчанию используй диаграмму потоков данных (процессы, хранилища, потоки
   данных, внешние сущности) и отметь границы доверия и точки входа. Сверь
   модель с реальной системой до поиска угроз. Если доступны только описание
   или схема, явно назови эту границу проверки. Назначь устойчивые обозначения
   элементам, потокам, нарушителям и допущениям. Используй
   [шаблон модели](assets/threat-model-template.md).
3. Ответь на второй вопрос — **что может пойти не так**: найди угрозы. По
   умолчанию проходи модель по STRIDE, при необходимости заменяй или дополняй её
   деревьями атак и библиотеками атак, не меняя остальную рамку. Учитывай угрозы
   приватности отдельно. Для элементов и пересечений границ доверия веди
   [проверку покрытия](references/coverage-and-traceability.md). Детали методов
   см. в `references/finding-threats.md`.
   Для многошаговой угрозы проверь [переходы цепочки][chains]: возможности
   нарушителя, основания каждого перехода и сохранение изменений. Неизвестная
   предпосылка сохраняет условную угрозу, а не исключает её из покрытия.
4. Ответь на третий вопрос — **что с этим делать**: для каждой угрозы предложи
   реакцию (избежать, снизить, принять, передать, осознанно проигнорировать) и
   меру, свяжи меру со свойством защиты по STRIDE. Принятие риска и осознанное
   игнорирование требуют решения человека. Детали см. в
   `references/risk-and-validation.md`.
5. Ответь на четвёртый вопрос — **достаточно ли хорошо проверили**: проверь
   критерии выхода, покрытие и связи результатов по справке о покрытии.
   Разделяй предложенную, реализованную и проверенную меру. Глубокую проверку
   реализованных мер ведёт `ait-sec-audit`.
6. Веди угрозы, риски, меры и допущения с устойчивыми ссылками. При обновлении
   модели сохраняй обозначения и отмечай зависимые от изменённых допущений
   выводы для пересмотра. Отделяй принятый остаточный риск с указанием решения
   человека. Не назначай владельца риска без основания.

## Ограничения

- Не подменяй модель угроз перечнем средств защиты: сначала угроза и актив,
  потом мера.
- Не считай диаграмму доказательством безопасности: модель должна
  соответствовать реальной системе.
- Не смешивай несовместимые методы (например, фокус на абстрактном «террористе»
  вместо модели ПО): выбирай метод под задачу.
- Не объявляй угрозу закрытой без проверяемой меры и без указания остаточного
  риска.
- Решение о принятии остаточного риска принимает человек, а не навык.
- Пустая ячейка или открытый вопрос не подтверждают полноту покрытия.
- Не исключай угрозу из-за отсутствия подходящей техники библиотеки атак.

## Вывод

Сообщай: что моделировалось и в каких границах, какая модель системы построена,
какие угрозы и каким методом найдены, какие меры выбраны и какие свойства защиты
они дают, есть ли решение о принятии остаточного риска и кто его принял,
что осталось проверить.
Покажи покрытие, допущения и отдельные записи рисков с устойчивыми ID,
текущей оценкой и прогнозом после предложенных мер. Проверь полную цепочку
«элемент — угроза — риск — мера»: ссылки мер только на угрозы её не заменяют.

При STRIDE результат содержит матрицу: одна строка на каждый элемент и поток
модели, столбцы `S`, `T`, `R`, `I`, `D`, `E`. В каждой ячейке укажи ID угрозы,
ID открытого вопроса или ID обоснования неприменимости. Раскрой вопросы и
обоснования после матрицы. Сверь строки с перечнем объектов, а не только с
найденными угрозами. При ином методе используй его представление покрытия.

Итоговые числа выводи из записей: отсутствующие строки объектов, пустые ячейки
проверок и уникальные открытые вопросы считай отдельно. Заполненная ячейка
с вопросом не является пропуском. У каждого риска укажи текущую оценку,
предложенную реакцию, меры либо причину их отсутствия и отдельно прогноз
после мер. Если данных нет, запиши открытый вопрос вместо пропуска поля.

Формат целевого проекта имеет приоритет над шаблоном, но должен сохранять эти
сведения и проверяемые ссылки.

## Что читать дополнительно

- `references/finding-threats.md` — STRIDE и варианты, деревья атак, библиотеки
  атак, инструменты приватности.
- `references/attack-chains.md` — основания переходов многошаговой угрозы,
  условные и опровергнутые переходы, границы вывода по свидетельствам.
- `references/risk-and-validation.md` — стратегии работы с риском, привязка
  свойств защиты к STRIDE, приоритизация, проверка мер и требования
  безопасности.
- `references/coverage-and-traceability.md` — покрытие, связи и критерии выхода.
- `assets/threat-model-template.md` — формы модели, допущений, рисков и мер.
- `references/adaptation-source.md` — источник адаптации и границы
  заимствования.
- Если моделируется публичный или партнёрский API — обязательно проверь разделы
  о безопасности в `ait-architecture/references/api-design.md`: векторы атак
  через URL обратного вызова (`webhook`) — перехват потока данных партнёра,
  канал DoS, SSRF на инфраструктуру провайдера — и типовые уязвимости HTTP API
  (CSRF, SSRF, HTTP Response Splitting, Unvalidated Redirects and Forwards).
  Основание — книга «The API Book»[^apib-099].

Читай только те справки, которые нужны для текущей задачи.

## Опорные источники

Используй корпус, только если его корень объявлен в доступных инструкциях
проекта. Все пути ниже указаны относительно этого корня. Сначала найди источник
по `id` в `catalog.yml`, затем используй `data/<slug>/source.yml`,
`data/<slug>/items.yml` и связанные утверждения: `SMAS`, `TMDS`, `ATCK`, `MWAT`,
`OWTT`, `ETL5`, `ASVS`, `SSDF`. Для угроз публичных и партнёрских API
дополнительно — `APIB` (через `ait-architecture/references/api-design.md`). Коды
источников и идентификаторы утверждений в этом разделе служат навигацией по
корпусу: в текстах для человека называй источник по его названию из
`catalog.yml`.

[^apib-099]:
    Сергей Константинов. «The API Book», разделы «безопасность настройки
    webhook», «CORS и защита от типовых уязвимостей». Внутренние идентификаторы
    утверждений: `APIB-099`, `APIB-152`.
