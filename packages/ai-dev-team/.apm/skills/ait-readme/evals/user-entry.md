# Проверка: README как пользовательская точка входа

## Ситуация

Агенту поручили написать или изменить главный `README.md` проекта. В проекте
есть внутренние документы с требованиями, архитектурными решениями,
интеграционными протоколами и командами разработки.

## Ожидаемое поведение

Агент должен:

- определить конкретную роль основного читателя `README.md` по профилю проекта,
  концепции и пользовательским сценариям,
- определить первое практическое действие читателя,
- поместить это действие в основной пользовательский сценарий,
- вынести внутренние требования, протоколы и подробности разработки в отдельные
  документы или разделы после основного сценария,
- добавить признак результата, если он определяет следующий шаг или помогает
  распознать сбой,
- сохранить ссылки на подробные документы, не заставляя читать их до первого
  полезного действия.

## Ошибочное поведение

Агент не должен:

- задавать общий вопрос «Кто основной читатель README.md?», если роль и задача
  уже следуют из профиля проекта,
- считать слово «пользователь» достаточным описанием аудитории,
- выбирать структуру `README.md` по заранее заданному шаблону без учёта проекта,
- описывать требования к интеграции вместо шагов пользователя,
- предлагать ручной запуск фонового сервера как проверку, если команда выглядит
  зависшей,
- объяснять внутренний протокол раньше результата для пользователя,
- смешивать подключение, диагностику, разработку и архитектуру в один основной
  сценарий.

## Критерий прохождения

Новый пользователь за первую минуту чтения понимает:

- что это за проект,
- зачем он ему нужен,
- какое первое действие выполнить,
- как продолжить после первого действия или распознать описанный сбой,
- куда перейти за подробностями после основного сценария.

## Регрессия: следы исходного задания

### Ситуация

Пользователь попросил перечислить возможности продукта от фундаментальных
подходов к частным. Агент добавил перед списком пояснение, что возможности
расположены именно в таком порядке. В другом разделе агент объяснил границы,
которые пользователь не считает полезными для выбора и первого действия.

### Ожидаемое поведение

Агент должен:

- расположить возможности в требуемом порядке без объяснения редакторского
  решения,
- проверить каждый вводный абзац и раздел по задаче конкретного читателя,
- удалить раздел, который владелец продукта явно признал лишним,
- не сохранять спорный раздел только ради полноты или демонстрации осторожности.

### Ошибочное поведение

Агент не должен:

- пересказывать в README требование к порядку материала,
- объяснять, почему выбрана структура документа,
- сохранять отвергнутый владельцем раздел под видом универсальной пользы,
- принимать прохождение первого технического действия за доказательство
  отсутствия лишнего метатекста.

### Критерий прохождения

README содержит только сведения, которые помогают конкретному читателю понять
продукт, решить, нужен ли он, подключить его или перейти к следующему действию.

## Регрессия: выбор продукта до подключения

### Ситуация

README описывает команду специализированных ролей и поддерживаемые подходы, но
помещает эти сведения после команд установки. Читатель должен изучить
подключение раньше, чем сможет решить, подходит ли ему продукт.

### Ожидаемое поведение

Агент должен:

- поставить краткое объяснение команды сразу после вводного описания продукта,
- разместить поддерживаемые подходы до раздела подключения,
- сохранить команды установки и настройки в отдельном инструктивном блоке,
- выбирать порядок по решениям читателя, а не по внутреннему устройству
  продукта.

### Ошибочное поведение

Агент не должен:

- начинать практическую часть с подключения до объяснения ценности продукта,
- прятать состав команды и поддерживаемые подходы после команд установки,
- добавлять служебное объяснение, почему разделы расположены в таком порядке,
- превращать первый экран в полный справочник ролей и навыков.

### Критерий прохождения

До раздела подключения читатель понимает ценность продукта, принцип работы
команды и поддерживаемые области. После этого он получает короткий путь
установки и настройки.

## Регрессия: наблюдаемый, но бесполезный результат

### Ситуация

После команды установки автор добавил отдельный абзац: продукт появится в
зависимостях, нужный навык станет доступен, а команда настройки должна
завершиться без ошибок. Абзац можно проверить, но он повторяет смысл успешных
команд и не объясняет, что делать при сбое.

### Ожидаемое поведение

Агент должен:

- назвать отдельную пользу каждого абзаца для решения, действия, диагностики или
  навигации читателя,
- удалить ожидаемый результат, который только повторяет смысл успешной команды,
- сохранить признак результата, если он помогает отличить успех от сбоя и задаёт
  следующий шаг,
- описать подтверждение или вопрос человека, если без него действие не
  продолжается.

### Ошибочное поведение

Агент не должен:

- считать наблюдаемость достаточным основанием для отдельного абзаца,
- добавлять формулу «команда должна завершиться без ошибок» вместо полезной
  диагностики,
- сохранять внутренний критерий приёмки ради полноты инструкции.

### Критерий прохождения

Каждый ожидаемый результат помогает читателю выбрать следующее действие или
распознать сбой. Очевидные результаты успешных команд удалены.

## Регрессия: режим раздела и отрицательная рамка

### Ситуация

README одновременно знакомит с продуктом, даёт команды подключения и направляет
к подробной документации. Агент пишет все разделы одинаково сухо, а описание
команды начинает фразой «Продукт не поручает всю разработку одному
универсальному агенту».

### Ожидаемое поведение

Агент должен:

- описать пользу и устройство команды в презентационном режиме,
- дать команды подключения в инструктивном режиме,
- оформить переходы к подробным материалам в справочном режиме,
- начать описание команды с прямого утверждения, например: «Продукт распределяет
  работу между специализированными ролями»,
- поместить нужное для выбора сравнение после прямого тезиса и назвать
  конкретное различие,
- сохранить отрицания, которые сообщают значимый запрет, отсутствие, исключение,
  ограничение или риск.

### Ошибочное поведение

Агент не должен:

- вводить свойство продукта через отвергаемую альтернативу,
- делать презентационный раздел перечнем внутренних сущностей,
- добавлять художественные образы в команды, условия или критерии проверки,
- превращать весь README в однородный справочник или рекламный текст.

### Критерий прохождения

Каждый раздел решает свою читательскую задачу подходящим режимом изложения.
Презентационная проза начинается с прямого утверждения о продукте, а
содержательные запреты и ограничения сохраняют точный смысл.
