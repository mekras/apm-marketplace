# Навык: сопровождение проектного README

## Назначение

Навык задаёт порядок создания, изменения и проверки главного `README.md`
проекта.

Главный `README.md` является пользовательской точкой входа в проект. Он не
должен подменяться спецификацией, архитектурным описанием, журналом решений или
документацией реализации.

## Когда применять навык

Навык должен применяться, если нужно:

- создать новый `README.md`,
- изменить существующий `README.md`,
- проверить качество `README.md`.

Навык не должен применяться для второстепенных файлов `README.md` проекта, а
также `AGENTS.md`, `CHANGELOG.md` и других файлов.

## Входные данные

Для применения навыка должны быть доступны:

- понимание смысла и характера проекта,
- концепция проекта или явное понимание, что концепция ещё не создана,
- понимание конкретной роли основного пользователя `README.md`, его задачи и
  интересов,
- человекочитаемый заголовок проекта, а не только имя каталога, slug пакета или
  технический идентификатор,
- сведения о первом практическом действии, которое пользователь должен смочь
  выполнить,
- проверяемые факты о подключении, запуске, использовании или разработке
  проекта.

Если этих сведений недостаточно, сначала выведи их из профиля проекта,
концепции, существующих пользовательских сценариев и способа поставки. Обращайся
к человеку только при неоднозначности, которая меняет основной сценарий
документа. Общие слова «пользователь» и «читатель» не закрывают этот пробел.

Если в проекте есть концепция, `README.md` не должен расходиться с ней. Если
концепции нет, зафиксируй это как ограничение и не выдумывай её внутри README.

## Что читать дополнительно

Если главный `README.md` описывает коллекцию APM с навыками, правилами или
инструкциями для агентов, прочитай `references/apm-skill-collections.md` перед
выбором аудитории, сценария установки и структуры README.

## Порядок применения

### 1. Определить пользователя README

Нужно явно понять:

- для кого пишется `README.md`,
- за чем этот пользователь пришёл,
- какое первое практическое действие он должен смочь выполнить после чтения.

Перед изменением `README.md` агент должен самостоятельно зафиксировать:

- кто основной читатель документа,
- какое первое действие он должен выполнить,
- какие разделы помогают этому действию,
- какие разделы являются внутренними подробностями и должны быть вынесены.

Это внутренняя проверка основания, а не обязательный вопрос человеку. Если
профиль проекта уже задаёт конкретную роль, задачу и способ взаимодействия, не
спрашивай повторно, кто читатель. Если остаётся существенная развилка, уточняй
первое практическое действие или выбор между конкретными ролями, а не проси
выбрать между общими категориями «пользователь» и «разработчик».

Отдельно определи, как проект должен называться в первом заголовке README. Не
переноси имя репозитория, slug пакета, имя каталога или технический
идентификатор в `H1` автоматически. Если это не собственное название, выбери
краткий человекочитаемый заголовок по назначению проекта: например, «Навыки для
OpenClaw» вместо `openclaw-skills`.

Структура `README.md` не должна выбираться по шаблону заранее. Агент должен
сначала определить тип проекта и основное первое действие пользователя, а затем
выбрать минимальную структуру под этот сценарий.

Типовые первые действия:

- подготовить систему к использованию продукта,
- установить и запустить приложение,
- использовать библиотеку в коде,
- развернуть сервис,
- открыть документацию или спецификацию,
- начать разработку самого проекта.

### 2. Собрать только нужные факты

Перед правкой нужно собрать подтверждённые сведения:

- что это за проект,
- в чём его смысл, для чего он нужен,
- что он даёт пользователю,
- как начать его использование,
- что потребуется пользователю в дальнейшем.

Все факты должны опираться только на подтверждённые сведения.

Не включай в README следы постановки задачи или авторского рассуждения:
объяснение порядка разделов, причины выбора структуры, отчёт о выполнении
запроса и формулировки, которые нужны только для демонстрации соблюдения
инструкции. Каждый абзац должен помогать конкретному читателю понять продукт,
принять решение о применении или выполнить следующий шаг.

Для каждого абзаца, списка и примера назови одну конкретную функцию: помочь
выбрать продукт, выполнить действие, учесть необходимое условие, отличить успех
от сбоя, выбрать следующий шаг или перейти к подробностям. Если фрагмент
повторяет соседний текст либо его удаление не меняет решение или действие
читателя, удали его. Наблюдаемое состояние само по себе не доказывает пользу.

Если есть концепция проекта, смысл и границы проекта для `README.md` должны
опираться на неё. Если концепция противоречит другим источникам, не сглаживай
конфликт: зафиксируй его и вынеси решение человеку.

Если сведения нужны разработчику проекта, но не нужны пользователю для первого
практического действия, их нужно вынести в отдельный документ и дать ссылку
после основного сценария.

Для каждой команды, которую агент собирается включить в `README.md`, нужно
отдельно определить и зафиксировать область действия команды. Минимальные
классы:

- установка пакета или продукта,
- установка зависимостей для разработки самого проекта,
- настройка клиента или среды пользователя,
- подключение конкретного проекта,
- проверка установки или подключения,
- локальная разработка или сопровождение.

Классификация должна опираться не на название команды, а на проверяемый эффект:
какие файлы, каталоги, настройки или артефакты она изменяет и в какой области.
Если команда пишет в домашний каталог пользователя, глобальную конфигурацию,
настройки клиента или другой ресурс вне текущего проекта, её нельзя описывать
как шаг подключения конкретного проекта.

Если проект меняет формат поставки продукта, например переходит с `npm` на
`APM`, агент обязан заново проверить основной пользовательский способ установки
и обновления. Нельзя оставлять старую команду установки только потому, что она
раньше была правильной. Команда установки продукта должна соответствовать
актуальному публичному способу поставки.

Команды установки зависимостей разработки (`npm install`,
`apm install --target ...` из корня репозитория и похожие) не заменяют команду
установки продукта для внешнего пользователя. Если новый менеджер пакетов уже
ставит пользовательское поведение продукта, он должен быть основным путём в
пользовательском разделе. Если новый менеджер пакетов пока ставит только часть
поведения, это нужно явно отделить от полного пользовательского способа
установки и зафиксировать как ограничение или переходный режим.

### 3. Выбрать структуру под сценарий

`README.md` должен закрыть пользовательские вопросы:

- что это за проект (кратко), в чём его смысл,
- что он даёт своим пользователям,
- как установить, подключить или начать применение,
- какое первое действие выполнить после установки или подключения,
- где найти подробную документацию.

Сведения, по которым читатель решает, подходит ли ему продукт, размещай до
подключения. К ним относятся назначение, практическая ценность, принцип работы,
состав команды и поддерживаемые подходы, если они влияют на выбор. Сначала
читатель принимает решение о продукте, затем переходит к командам установки и
настройки.

Раздел разработки добавляется только если `README.md` адресован сопровождающим
проекта или пользователь явно просит описать разработку.

Нельзя делать структуру репозитория основной формой `README.md`. Разделы про
каталоги, внутренние инструменты и служебные файлы не должны идти раньше
назначения проекта, пользы и способа применения.

Если раздел называется «Как пользоваться», он должен описывать пользовательский
сценарий, а не внутренние компоненты.

Режим изложения выбирается по задаче раздела:

- первый экран, описание пользы и основания выбора используют презентационный
  режим,
- подключение, настройка, первое действие и обновление используют инструктивный
  режим,
- навигация, перечни документов и сведения для сопровождения используют
  справочный режим.

Раздел о возможностях может сочетать презентационный и справочный режимы:
сначала он даёт основание для выбора продукта, затем помогает быстро проверить
нужную область. Названия режимов и объяснение их выбора остаются частью работы
автора и не попадают в README.

Презентационная часть начинается с того, что продукт делает, даёт или
поддерживает. Нужное для выбора сравнение следует после прямого тезиса и
называет конкретное различие. Метафора допустима как короткий образ продукта, но
не как замена проверяемому факту.

### 4. Разделить пользовательский и разработческий сценарии

Пользовательский сценарий должен содержать:

- подходящий для читателя способ установки, подключения или первого запуска,
- команду обновления, если она нужна пользователю,
- последствия установки, подключения или запуска, которые определяют следующий
  шаг либо помогают распознать сбой,
- первый рабочий шаг после установки, подключения или запуска.

Описывай результат действия, когда он помогает выбрать следующий шаг или
отличить успех от сбоя. Укажи документированный признак проблемы и действие
читателя, если они известны. Удаляй очевидные критерии вроде «команда должна
завершиться без ошибок»: они повторяют смысл успешного выполнения и не помогают
при сбое. Не переноси в README формулы из внутренних тестов и критериев приёмки.

В записи о файле называй его назначение и фактическое расположение после
установки. Объясняй, куда установщик не копирует файл, только если это
документированный признак сбоя, ограничение или условие следующего действия.
Требование описывать область действия команды не относится к каждой записи о
файле.

Если сравниваются способы подключения, считай отдельными действиями заказчика
каждый обязательный выбор или ввод, команду, ручную операцию с файлом, открытие
клиента и ответ на обязательный вопрос. Сравнивай варианты от одинакового
исходного состояния до установленного, настроенного и проверенного проекта.
Скрипт или составная команда не уменьшают число действий, если лишь скрывают
несколько смысловых операций либо переносят их за границу сценария.

Разработческий сценарий должен содержать локальные проверки, структуру проекта и
команды сопровождения только в отдельном разделе разработки.

Команды установки и первого запуска должны соответствовать сценарию читателя.
Если документ адресован внешнему пользователю, основной путь должен быть
воспроизводим вне локального окружения автора. Локальные пути допустимы, когда
`README.md` описывает локальную разработку, внутреннюю установку или явно
ограниченный сценарий.

### 5. Внести правки в файл

- Внести в `README.md` требуемые изменения, используя `ru-lang` с набором
  «разработка».

### 6. Проверить README как пользовательский вход

После правки нужно перечитать `README.md` как новый пользователь и проверить:

- понятно ли за первую минуту, что это за проект,
- понятно ли, что он даёт пользователям,
- не расходится ли описание проекта с концепцией, если она есть,
- есть ли рабочая команда установки, подключения или первого запуска,
- не попали ли внутренние проверки в пользовательский сценарий,
- не описывает ли документ структуру раньше пользы,
- не остались ли объяснения порядка изложения, выбора разделов или выполнения
  исходного задания,
- находятся ли сведения для выбора продукта раньше команд подключения,
- есть ли у каждого абзаца, списка и примера отдельная функция для решения или
  действия читателя,
- изменит ли удаление каждого ожидаемого результата следующий шаг читателя или
  его способность отличить успех от сбоя,
- соответствует ли режим изложения задаче каждого раздела,
- начинаются ли описательные разделы с прямого утверждения о продукте, его
  действии или результате,
- все ли команды имеют понятную аудиторию,
- для каждой ли команды явно понятно, что именно она меняет: систему
  пользователя, клиент агента, текущий проект или только проверку состояния.
- описаны ли результаты установки и настройки через наблюдаемое состояние, а не
  через определение внутреннего критерия проверки,
- можно ли заменить объяснение внутренней механики прямым состоянием или
  инструкцией без потери ограничения, диагностики или следующего действия,
- не остались ли в русском тексте гибридные формы и англоязычные родовые слова,
  которые должен исправить `ru-lang`,
- не подменяет ли `H1` человекочитаемый заголовок техническим slug.

## Результат применения навыка

Результатом должен быть `README.md`, который:

- опирается на проверяемые факты,
- ориентирован на пользователя проекта,
- ведёт к первому практическому действию,
- даёт понятный маршрут следующего шага.

## Что считается ошибкой применения навыка

- Агент спрашивает, кто основной читатель, хотя конкретная роль и задача уже
  следуют из профиля проекта.
- Общий ответ «пользователь» принят как достаточное описание аудитории.
- В документ попали непроверенные команды, статусы или сценарии использования.
- Документ содержит требования вместо руководства для пользователя.
- Документ объясняет собственную структуру, порядок изложения или соответствие
  исходному заданию без пользы для решения и действий читателя.
- Команды подключения появляются раньше сведений, по которым читатель решает,
  подходит ли ему продукт.
- Презентационный раздел начинается с отвергаемой альтернативы вместо прямого
  утверждения о продукте.
- Весь README написан в одном режиме вопреки разным задачам его разделов.
- Документ объясняет внутренний протокол раньше пользовательского результата.
- Внутренний критерий приёмки или тестового сценария перенесён в README как
  нормативное определение вместо наблюдаемого результата для читателя.
- Наблюдаемый, но очевидный результат добавлен только ради полноты и не меняет
  решение, диагностику или следующий шаг читателя.
- Документ смешивает основной сценарий с диагностикой и разработкой.
- Документ заставляет читать несколько документов до первого полезного действия.
- Документ описывает структуру проекта раньше назначения и пользы.
- Пользовательский быстрый старт содержит команды сопровождения проекта.
- Команды установки или первого запуска не соответствуют аудитории документа.
- После смены формата поставки продукта в пользовательском сценарии осталась
  устаревшая команда установки без явного переходного статуса.
- Команда установки зависимостей разработки описана как установка продукта для
  внешнего пользователя.
- Команда отнесена к установке, подключению проекта или проверке только по
  названию, а не по фактической области действия.
- Заголовок раздела обещает пользу или использование, но внутри описан состав
  файлов или внутренние проверки.
- Главный заголовок README взят из slug репозитория или имени пакета, хотя нужен
  краткий человекочитаемый заголовок.

## Связь с другими элементами продукта

Этот навык должен применяться вместе:

- с ролью технического писателя,
- с навыком технического письма как общим основанием,
- с документами о подключении, запуске или первом применении, если `README.md`
  описывает использование продукта в проекте,
- с контрольным слоем, если изменение `README.md` влияет на значимый
  пользовательский источник истины.

## Внешние основания навыка

Для этого навыка уместно использовать публичные авторитетные материалы по
проектной и пользовательской документации.

В частности:

- руководства сообщества `Write the Docs`.

Публичный источник помогает обосновать правило навыка, но не заменяет проверку
того, что именно нужно пользователю конкретного проекта.
