# Договор графа влияния проекта

`.ai-dev-team/project-impact.json` — единый машинно-проверяемый договор о смысловых
артефактах проекта, их представлениях и направлениях возможного влияния. Ребро
`from → to` означает: изменение
вершины `from` в одном из перечисленных аспектов требует проверить вершину `to`.

Граф описывает возможность влияния, а не приказ изменить все достижимые
артефакты. Смысловой вывод остаётся за профильной проверкой.

## Структура

Корневой объект содержит только поля:

- `schema_version` — целое число `2`. Анализатор читает версию `1` для
  обратной совместимости трассировки, но `validate` считает такой граф
  семантически неполным и завершается с ненулевым кодом. Новые графы создавай
  в версии `2`.
- `graph` — настройки договора
- `nodes` — непустой список вершин
- `edges` — список направленных рёбер

Объект `graph` содержит:

- `name` — непустое имя проекта
- `description` — назначение конкретного графа
- `default_facet` — аспект по умолчанию
- `unmapped_paths` — `block` или `warn`
- `ignore` — шаблоны путей, не входящих в договор

## Результат проверки

`validate` возвращает `status: ok` только для графа версии 2 с моделью
артефактов и представлений. Для корректного по старой схеме графа версии 1
команда возвращает `status: incomplete`, `semantic_model: false`, проблему
`semantic-model-unavailable` и ненулевой код. Такой граф можно трассировать во
время миграции, но его нельзя объявлять пригодным для проверки авторитетности,
смысловых типов или размещения представлений.

`status: ok` не гарантирует пустой список `problems`: для графа версии 2 с
циклом среди рёбер `basis: true` `validate` сохраняет `status: ok` и
`semantic_model: true` (модель артефактов и представлений корректна), но
добавляет в `problems` находку `basis-cycle` с перечнем узлов цикла и
завершается ненулевым кодом — цикл авторитета требует разбора, но не делает
граф семантически неполным. Проверяй необходимость разбора по `problems`, а
не только по `status`.

В версии `2` каждая вершина обозначает смысловой артефакт, а не каталог или
файл как таковой, и содержит:

- `id` — устойчивый идентификатор из строчных латинских букв, цифр и дефисов
- `title` — понятное название части проекта
- `kind` — тип из списка ниже
- `semantic_type` — понятный тип артефакта в предметной модели проекта
- `authority` — `canonical`, `supporting` или `derived`
- `representations` — непустой список файловых представлений. Для каждого
  указаны `path` и роль: `canonical`, `supporting`, `navigation`,
  `implementation` или `verification`
- `checks` — непустой список профильных навыков или проверок
- `review_stages` — необязательные области полной проверки

Для постепенной миграции вместо `representations` можно указать `paths`.
Каждый такой путь считается представлением с ролью `canonical` для канонического
артефакта и `supporting` для остальных. Этот сокращённый вид не применяй, когда
одному артефакту нужны разные роли представлений.

Один файл может представлять несколько артефактов. Один документ также может
содержать несколько артефактов. Не добавляй в граф абзацы и каждую строку кода:
включай только устойчивые артефакты, важные для происхождения, решений,
реализации или проверки.

Допустимые типы вершин:

- `concept`
- `knowledge`
- `requirements`
- `architecture`
- `decision`
- `implementation`
- `test`
- `documentation`
- `operation`
- `process`
- `configuration`
- `delivery`
- `other`

Каждое ребро содержит:

- `from` и `to` — существующие вершины
- `relation` — тип смысловой зависимости
- `facets` — непустой список аспектов, при которых ребро действует
- `rationale` — проверяемое объяснение направления
- `basis` — необязательное булево поле. Различает направление обоснования от
  направления, дающего только повод перепроверить цель:
  - `true` — источник ребра является содержательным основанием цели; ссылка
    на него засчитывается как обоснование при оценке обоснованности цели.
  - `false` — ребро задаёт только повод перепроверить цель при изменении
    источника; само по себе обоснованием не является.
  - Поле отсутствует — значение не определено. Трасса влияния (`trace`,
    `assess`, `coverage`) идёт по ребру независимо от значения `basis` и от
    его отсутствия: поле не влияет на обход графа, только на интерпретацию
    ребра при оценке обоснованности.
  - Поле не заменяет и не переопределяет `authority` вершины
    (`canonical`/`supporting`/`derived`): `authority` — свойство узла,
    `basis` — свойство направленного ребра.
  - Подграф рёбер с `basis: true` должен оставаться ациклическим — иначе
    оценка обоснованности узла опирается сама на себя транзитивно. Команда
    `validate` сообщает найденный цикл находкой `basis-cycle`, но не
    отказывает в загрузке графа: обход `trace`/`assess`/`coverage` цикл
    авторитета не блокирует.

Допустимые отношения:

- `constrains`
- `informs`
- `refines`
- `realizes`
- `verifies`
- `documents`
- `configures`
- `packages`
- `operates`
- `governs`

## Аспекты изменения

- `semantic` — изменён смысл, обязательство или вывод
- `interface` — изменён внешний или внутренний договор взаимодействия
- `data` — изменены данные, схема, происхождение или жизненный цикл
- `quality` — изменено требуемое или обеспечиваемое свойство качества
- `security` — изменена граница доверия, угроза или мера защиты
- `reliability` — изменено поведение при отказе или эксплуатации
- `operation` — изменены развёртывание, сопровождение или рабочая процедура
- `structure` — изменены размещение, состав или навигация без заявленного
  изменения смысла
- `documentation` — изменено пользовательское или справочное представление
- `any` — ребро действует при любом аспекте

`any` разрешён только в `facets` ребра. Изменение получает конкретный аспект.

## Сопоставление путей

Пути записываются относительно корня проекта с разделителем `/`. Разрешены
шаблоны `*`, `?`, `[]` и `**`. Один путь может принадлежать нескольким вершинам,
если артефакт действительно выполняет несколько обязанностей.

Режим `unmapped_paths: block` не допускает завершить работу с новым или
изменённым путём вне графа. Режим `warn` разрешён только как явно принятое
временное состояние проекта и должен оставлять ограничение в результате.

## Обход и циклы

Анализатор обходит пары «вершина, аспект» в ширину. Он применяет ребро, если
аспект входит в `facets` либо список содержит `any`. Каждая пара обрабатывается
один раз, поэтому цикл завершается в неподвижной точке. Результат содержит
кратчайший найденный путь до каждой затронутой пары.

Если профильная правка достигнутой вершины создаёт аспект, которого не было у
неё во входном наборе, эта пара добавляется как новый вход. Обход повторяется
для объединённого набора до тех пор, пока профильные проверки не перестанут
порождать новые пары.

## Завершённость

Для каждой затронутой вершины обязателен один итог:

- `updated`
- `verified_no_impact`
- `human_decision`
- `blocked`

Команда `assess` завершается успешно, только если все затронутые вершины имеют
итог `updated` или `verified_no_impact`. Остальные итоги сохраняют точный
блокер, но не разрешают завершить проектную задачу.
