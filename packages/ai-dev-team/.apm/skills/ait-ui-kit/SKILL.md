# ait-ui-kit

Помогай проекту завести и использовать минимально достаточный UI Kit. UI Kit в
этом навыке — сопровождаемый набор визуальных решений, токенов, компонентов,
состояний, правил применения и проверяемых примеров для повторного использования
в интерфейсах проекта.

UI Kit может быть частью дизайн-системы, но не заменяет её автоматически.
Дизайн-система может дополнительно включать принципы, управление изменениями,
бренд, содержание и организационные правила. Конкретный носитель UI Kit
определяет целевой проект: документация, макеты, код, каталог компонентов,
дизайн-токены или согласованное сочетание этих артефактов.

## Когда применять

- нужно понять, полезен ли проекту UI Kit и какой объём оправдан
- нужно создать первый UI Kit или выделить его из существующего интерфейса
- нужно добавить, изменить, устареть или удалить токен, компонент либо вариант
- нужно применить UI Kit при проектировании или реализации интерфейса
- нужно устранить расхождение между документацией, макетами, кодом и примерами

## Когда не применять

- задача относится к одному экрану и не требует повторно используемого решения —
  применяй `ait-interface-design`
- ещё не ясны пользователи, цели и сценарии — сначала применяй `ait-ux-design`
- нужно выбрать позиционирование или фирменный стиль вместо человека с
  соответствующими полномочиями
- поставляемая сторонним разработчикам библиотека требует проектирования
  публичного API — добавь `ait-architecture` и раздел «SDK и UI-библиотеки»

## Обязательный порядок

1. Проверь основание: платформы, число экранов и исполнителей, повторяющиеся
   решения, расхождения, срок жизни продукта и стоимость сопровождения. Выбери
   статус `не нужен`, `нужен стартовый набор` или `нужен сопровождаемый UI Kit`.
2. Найди существующие `DESIGN.md`, UI Kit, макеты, токены, темы, компоненты,
   каталоги примеров, снимки и интерфейсные проверки. Не создавай второй
   источник истины поверх уже действующего.
3. Предложи минимально достаточный состав и 2–3 варианта носителя, если проект
   его ещё не выбрал. Для вариантов назови разовые затраты, будущую стоимость
   сопровождения, риск расхождения, обратимость и влияние на работу людей.
4. До создания зафиксируй договор:
   - назначение, пользователей UI Kit и поддерживаемые платформы
   - канонические и производные артефакты, их расположение и владельцев
   - связь с `DESIGN.md`, макетами, кодом и платформенными правилами
   - именование токенов и компонентов, состояния и варианты
   - уровни зрелости `экспериментальный`, `стабильный` и `устаревающий`
   - проверки, правила совместимости и порядок устранения расхождений
5. Создавай UI Kit от одного реального пользовательского сценария и небольшого
   сквозного набора. Включи только нужные основы, семантические токены,
   компоненты, состояния, доступность, платформенные варианты и примеры. Не
   заполняй каталог предположительными компонентами «на будущее».
6. При сопровождении свяжи изменение с интерфейсной задачей или выявленным
   расхождением. Обнови канонический артефакт, зависимые реализации, примеры,
   проверки и сведения о зрелости. Несовместимое изменение сначала предложи
   человеку вместе с влиянием, переходом и сроком удаления старого решения.
7. При применении сначала выбери существующие токены, компоненты и состояния. Не
   создавай локальный вариант только ради удобства текущего экрана. Если решения
   не хватает, явно выбери: собрать экран из существующих примитивов, расширить
   UI Kit или оставить ограниченное исключение с причиной и условием пересмотра.
8. Проверь результат: сценарий, платформенность, доступность, состояния,
   визуальную согласованность, примеры и доступный след выполнения проверок.
   Отдельно проверь расхождение между заявленным источником истины и
   производными артефактами.
9. Сообщи, что предложено, создано, изменено или применено, какие артефакты
   канонические, как проверен результат, что требует решения человека и какие
   риски остались.

Подробная процедура и состав артефактов описаны в
`references/ui-kit-workflow.md`. Для нового текстового носителя можно
использовать `assets/ui-kit-template.md`.

## Границы

- Не навязывай UI Kit маленькому или одноразовому интерфейсу без повторного
  использования.
- Не объявляй документацию, макет или библиотеку компонентов каноническими, пока
  проект не определил источник истины и порядок синхронизации.
- Не выдавай набор цветов и кнопок за полный UI Kit без состояний, доступности,
  платформенных различий и примеров применения.
- Не копируй внешнюю дизайн-систему или библиотеку без проверки лицензии.
- Не принимай несовместимое изменение, визуальное направление или срок удаления
  старого решения вместо человека с соответствующими полномочиями.
- Не делай формат дизайн-токенов обязательным, если проекту достаточно более
  простого и проверяемого представления.

## Связь с соседними навыками

- `ait-ux-design` задаёт пользователей, цели и сценарии.
- `ait-interface-design` проектирует экран и применяет действующий UI Kit.
- `ait-architecture` проектирует публично поставляемую UI-библиотеку и её API.
- `ait-licensing` проверяет заимствованные компоненты, иконки, шрифты и шаблоны.
- `ait-code-construction` и `ait-code-testing` реализуют и проверяют кодовые
  артефакты выбранного стека.
- `ait-writing` помогает оформить человеко-ориентированный носитель UI Kit.

## Опорные источники

Сначала проверь корпус целевого проекта. В этом продукте навык опирается на
`INMA`, `SMFR` и `WCAG`, а для точечной сверки формата и практики — на `DTCG`,
`APHG`, `MD3`, `NFRM`, `IMPD` и `OPDS`. Учитывай статус, условия использования и
ограничения карточек источников. Не заменяй отсутствие основания готовой внешней
системой. Коды источников и идентификаторы утверждений в этом разделе служат
навигацией по корпусу: в текстах для человека называй источник по его названию
из каталога корпуса.
