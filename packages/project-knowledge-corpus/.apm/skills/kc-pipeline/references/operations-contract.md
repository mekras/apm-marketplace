# Операционный контур корпуса

Этот договор дополняет `kc-pipeline` переносимым механизмом планирования и
обслуживания корпуса. Он не заменяет предметные навыки, не определяет адаптеры
и не принимает содержательные решения.

## Назначение

Контур даёт проекту пять повторяемых операций:

- построить очереди по `workflow_stage`, карточкам единиц и артефактам рядом с
  ними.
- явно запустить зарегистрированные проектные команды одной стадии.
- пересобрать общие индексы единиц и утверждений из их владельцев.
- создать локальный отчёт конкретного запуска.
- продолжить полный проход по всем автоматическим очередям с сохранением
  состояния между сеансами агента.

Средство запуска находится в
`scripts/run-corpus-operations.py`. По умолчанию оно только читает корпус и
пишет план в стандартный вывод:

```bash
python3 .apm/skills/kc-pipeline/scripts/run-corpus-operations.py knowledge
```

Корень корпуса и все пути записи принадлежат текущему проекту. Внешний источник
или peer-корпус нельзя передавать средству как корень корпуса проекта-потребителя.
Его можно читать для проверки доступности и трассировки, но состояние прохода,
отчёты, индексы и команды обработки остаются в проекте корпуса-владельца.

## Настройки операций

Настройки не входят в обязательную раскладку корпуса. Если проекту они нужны,
он создаёт отдельный файл по образцу `assets/operations.yml` и передаёт его
параметром `--operations`.

```yaml
operations_version: 1
report:
  path: .local/reports/corpus-operations.md
run_state:
  path: .local/state/corpus-pipeline.json
normalized_artifacts:
  - normalized.md
  - message.md
  - stenogram.txt
stages:
  source_sync:
    commands:
      - id: source-sync
        argv: [python3, tools/sync-source.py]
        working_directory: .
        write_paths: [knowledge/data/example-source]
        required: true
  normalize:
    commands:
      - id: normalize-next-batch
        argv: [python3, tools/normalize-corpus-queue.py]
        working_directory: .
        write_paths: [knowledge/data]
        required: true
```

`argv` — список аргументов без оболочки. `working_directory` и каждый путь из
`write_paths` задаются относительно корня проекта и не могут выходить за его
пределы. `write_paths` служит проверяемой границей ожидаемых изменений в Git.

Стадия может объявить ресурсный порог:

```yaml
stages:
  transcribe:
    task_contract: compound_media
    resources:
      min_free_disk_bytes: 2147483648
      estimated_peak_disk_bytes: 10737418240
    commands:
      - id: process-next-media
        argv: [python3, tools/process-next-media.py]
        working_directory: .
        write_paths: [knowledge/data]
        required: true
```

Оба значения задаются целым числом байтов. Исполнитель запускается, если
свободное место не меньше их суммы. `compound_media` означает, что проектная
команда хранит состояние подэтапов «получить, расшифровать, проверить,
очистить», допускает безопасный повтор и удаляет только подтверждённое
временное сырьё.

Адаптер, его секреты, параметры доступа и обработка конкретного носителя
остаются в проекте-потребителе. Исполняемый реестр и формат его результата см.
в [договоре адаптеров](adapter-contract.md). Не храните в настройках токен,
cookie, пароль или закрытый адрес.

Проект может указать путь локального реестра логических профилей:

```yaml
access_profiles:
  path: .local/access-profiles.yml
```

Файл исключается из Git. Переносимая карточка хранит только вид авторизации,
необходимые возможности, логическое имя профиля и допустимость интерактивной
настройки. Секрет и данные сессии не передаются контроллеру через аргументы,
стандартный вывод или отчёт.

## Запуск команд

Команды не выполняются при обычном планировании. Для выбранной стадии нужен
явный параметр:

```bash
python3 .apm/skills/kc-pipeline/scripts/run-corpus-operations.py \
  knowledge --operations knowledge/operations.yml \
  --stage source_sync --run-commands
```

Средство запуска передаёт `argv` напрямую, сохраняет код завершения и сравнивает
снимки содержимого всех отслеживаемых и неигнорируемых файлов Git до и после
команды. Поэтому уже изменённый или добавленный в индекс Git файл нельзя
повторно изменить вне `write_paths` незаметно для контроля. Команда с
ненулевым кодом завершения или изменением за пределами `write_paths`
останавливает обязательную стадию. Средство не откатывает изменения команды.
Восстановление выполняет проектная команда или следующий разрешённый запуск.

Для запуска адаптеров источников есть отдельный явный параметр
`--run-adapters`; он не запускает команды стадии `source_sync`.

Версия 1 выполняет прежнее получение. Для версии 2 параметр
`--adapter-operation` выбирает `probe`, `fetch`, `verify` или `authorize`.
Перед `fetch` и `verify` контроллер автоматически выполняет `probe`.
`authorize` запускается только при явном выборе и не входит в автономный
проход.

## Автономный проход

Параметр `--run-pipeline` означает явное разрешение запускать
зарегистрированные команды стадий. Контур каждый раз заново строит очередь,
выбирает первую непустую автоматическую стадию и требует наблюдаемого изменения
очереди после команды:

```bash
python3 .apm/skills/kc-pipeline/scripts/run-corpus-operations.py \
  knowledge --operations knowledge/operations.yml --run-pipeline
```

Имена групп в `stages` для полного прохода совпадают с очередями:
`content_selection`, `fetch`, `transcribe`, `normalize`, `statements`,
`traceability`, `semantic_review`, `strong_review`, `corroboration`,
`source_check`, `concepts`, `impact_audit`, `apply_changes` и
`corpus_validation`.
Исполнитель может использовать модель, локальный скрипт или внешний сервис,
но обязан обновить машиночитаемые артефакты корпуса. Если очередь не меняется,
проход получает `failed` с причиной `no_progress`.

Этот режим не заменяет содержательную работу агента по `kc-pipeline`. Если
ближайшая очередь не имеет зарегистрированной команды, агент сам формирует
ограниченный пакет, применяет профильный навык стадии и повторно строит
очередь. Отсутствие команды означает, что контроллеру нечего запускать. Оно не
образует ресурсный блокер, пока агент может обработать пакет самостоятельно.
`paused_resources` используйте только при недоступности и проектной команды, и
агента из-за объявленного ресурса или конкретного блокера.

Агент, начавший `kc-pipeline`, считается исполнителем содержательной очереди
по умолчанию. После ограниченного пакета он сам предлагает проектную команду,
если в очереди остался незаблокированный повторяемый хвост с устойчивыми
входом, результатом, критериями качества и границей записи. В предложении
указываются наблюдение из пакета, охват, входы и выходы команды, `write_paths`,
безопасный повтор и проверка. Пользователь подтверждает только невыводимый из
правил выбор: новый внешний сервис или расходы, секреты и доступы, либо
изменение содержательного результата или границы записи. Пока решения нет,
агент продолжает доступные пакеты. Отсутствие команды не создаёт
`paused_resources`.

Первые стадии выводятся из карточек, артефактов и утверждений корпуса.
Последние четыре стадии относятся ко всему проходу. Контур создаёт для каждой
глобальную задачу, выполняет их строго после первичного контура и сохраняет
завершённые глобальные стадии в состоянии. Успешная проектная команда закрывает
глобальную задачу. Поэтому отсутствие содержательных изменений должно
выражаться успешным результатом проверки, а не отсутствием исполнителя.

Каждый исполнитель должен допускать безопасный повтор. Если процесс аварийно
завершится после команды, но до атомарной записи состояния, следующий запуск
может выполнить ту же стадию ещё раз. Команда должна распознавать уже
применённый результат или повторять действие без потери данных и дублирования
эффекта.

Во время команды контроллер атомарно сохраняет `active_executor`: PID, имя
очереди, идентификатор команды, время запуска и последний heartbeat. Если
контроллер или сеанс агента исчезли, перед следующим запуском или отдельной
сводкой выполните:

```bash
python3 .apm/skills/kc-pipeline/scripts/run-corpus-operations.py \
  knowledge --operations knowledge/operations.yml --reconcile-state
```

Отсутствующий PID переводит старый `running` в `paused_limit` с причиной
`executor_interrupted` без потери `run_id` и очереди. Живой PID не допускает
новый запуск. Каталог `.local/` принадлежит контроллеру, поэтому его heartbeat,
состояние и журналы не входят в `write_paths` проектной команды.

`access_unavailable` и `source_unavailable` допустимы только после двух разных
сохранённых автоматических попыток доступа. Одна неудача остаётся
неопределённостью материала, а не человеческим блокером. Исполнитель пакета
должен вносить только проверяемые изменения очереди: неисправный пакет не
объявляет весь проход завершённым и не превращает неподтверждённую диагностику
в блокер.

Локальная недоступность не меняет сохранённый `verification.yml` текущего
снимка. Она откладывает только действие, которому нужна новая прямая сверка.
Смена хэша снимка требует новой проверки происхождения. Контроллер отклоняет
неуспешную операцию адаптера, если та изменила `verification.yml`.

Состояние записывается атомарно в `run_state.path` или путь параметра
`--state`. Если предыдущий проход не был `completed`, новый запуск сохраняет
его `run_id`, увеличивает число попыток и продолжает текущую очередь.
Ограничение `--max-steps` относится только к одной попытке и переводит проход в
`paused_limit`, а не в `completed`.

На время попытки рядом с состоянием удерживается межпроцессная блокировка.
Второй исполнитель того же пути состояния завершается до чтения или изменения
очереди. После `completed` следующий запуск получает новый `run_id`.

Терминальные состояния и коды завершения:

- `completed`, код `0`: все автоматические и внешние очереди пусты.
- `paused_limit`, код `10`: лимит попытки исчерпан, доступная работа осталась.
- `paused_resources`, код `11`: автоматический хвост остался, но ни для одной
  готовой очереди нет исполнителя или объявленных ресурсов.
- `waiting_external`, код `20`: доступная работа исчерпана, остались только
  конкретные решения человека.
- `failed`, код `1`: предварительная проверка не пройдена, исполнитель
  завершился с ошибкой, не изменил текущую очередь или итоговая проверка не
  пройдена.

Поэтому успешное завершение процесса не подменяет завершение прохода. Средство
не возвращает `0` для управляемой паузы.

При ресурсной недоступности ранней очереди контроллер продолжает другие готовые
очереди первичного контура. Глобальные стадии не начинаются, пока первичный
контур не опустел. Причины отложенных очередей сохраняются в
`resource_waiting`.

## Предзапусковая и итоговая проверки

Автономный `--run-pipeline` всегда начинает с операционной проверки. Отдельный
планирующий или одностадийный запуск может запросить её параметром
`--operational-check`. Контур вызывает существующий валидатор раскладки, а не
содержит второй сканер.
Валидатор рассматривает внутри корня корпуса отслеживаемые и неигнорируемые
неотслеживаемые файлы из `git ls-files`. Он исключает `*.local.*`, `*.tmp.*`,
`local/`, `.local/` и каталоги `*.local` прежде чтения. Поэтому новый
публикуемый файл, созданный исполнителем, тоже попадает в итоговую проверку. В
отчёте остаются только путь, номер строки и вид находки, поэтому найденное
значение не копируется в локальный отчёт.

После закрытия всех очередей тот же контроль запускается повторно. Между ним и
записью `completed` команды стадий больше не выполняются. Ошибка договора,
секрет или другой операционный блокер переводит проход в
`failed/postflight_failed`, даже если команда `corpus_validation` завершилась
успешно.

Результат разделён на ошибки договора, блокеры доступа (`access-secret`,
`credentialed-url`), предупреждения качества (`personal-data`) и очереди
корпуса. Открытый контакт в метаданных источника фиксируется отдельно и сам по
себе не блокирует запуск. Ложное срабатывание разрешается подавить только
правилом с причиной:

```text
... --operational-check --operational-policy knowledge/operational-check.yml
```

Шаблон правила находится в
`kc-inventory/assets/operational-check.yml`. Подавление меняет
классификацию, но не выводит чувствительное значение и не заменяет решение о
публикации.

## Индексы и восстановление

После успешной синхронизации пересоберите производные индексы:

```bash
python3 .apm/skills/kc-pipeline/scripts/run-corpus-operations.py \
  knowledge --operations knowledge/operations.yml --rebuild-indexes
```

Новые файлы индексов строятся полностью до записи; каждый из них создаётся во
временном файле и заменяется без появления частично записанного файла. Если
запуск прервался между заменами, карточки источников остаются владельцами
данных, а следующий запуск с `--rebuild-indexes` восстанавливает согласованную
пару общих индексов. После восстановления нужно выполнить проверку корпуса,
заданную проектом.

## Локальный отчёт

Отчёт описывает конкретный запуск: состояние прохода, размер и полный состав
очередей, коды завершения команд и число записей в пересобранных индексах. Он
не содержит содержательных выводов или отчёта влияния. Полный хвост также
сохраняется в JSON-состоянии и не теряется из-за ограничения краткой сводки.

`human_attention.max_active_groups` ограничивает только число групп решений в
кратком представлении. По умолчанию используются 20 групп. Состояние хранит
полное число элементов, все сгруппированные причины, активные группы и число
групп за пределами бюджета. Группа объединяет одинаковые `blocker_code`,
требуемое действие и последствия, выраженные конкретной причиной. Она называет
автоматические попытки и примеры.

Запись отчёта происходит только по явному запросу:

```bash
python3 .apm/skills/kc-pipeline/scripts/run-corpus-operations.py \
  knowledge --operations knowledge/operations.yml --write-report
```

Путь `report.path` должен вести в неотслеживаемый локальный слой. Не добавляйте
такой отчёт в Git.

## Очереди

Средство использует переносимые очереди `content_selection`, `fetch`,
`transcribe`, `normalize`, `statements`, `traceability`, `semantic_review`,
`strong_review`, `corroboration`, `source_check`, `concepts`, `impact_audit`,
`apply_changes`, `corpus_validation` и `human_decision`.
Штатная стадия `indexed` не считается неподдерживаемой:

- единица обычного источника без выбранного объёма обработки попадает в
  `content_selection`.
- единица с `processing_scope: selected_fragments`, `full` или
  `full_redacted` попадает в `fetch` для точечного получения.
- единица источника со `storage_strategy: index_only` без выбранного объёма
  обработки не образует массовую очередь: обновлённый индекс завершает
  штатный проход такого источника.

Неподдерживаемая стадия считается ошибкой договора. `blocked` попадает в
`human_decision` только с допустимым `blocker_code`. Содержательный отбор должен
завершиться явным решением: выбрать единицу для точечного получения, отклонить
её с причиной или отправить в `human_decision` только вопрос, который
действительно требует решения человека.

Имена нормализованных артефактов настраиваются через `normalized_artifacts`.
Сырая `transcript.txt` не считается нормализованным артефактом: она оставляет
единицу в очереди нормализации.

Для договора утверждений версии 2 очереди проверки строятся по
`processing_status`. Сила основания, уверенность извлечения, возраст сведений
и наличие независимого подтверждения не определяют завершённость обработки.
В старом договоре `status: candidate` попадает в автоматическую
`semantic_review`, а не в `human_decision`.
