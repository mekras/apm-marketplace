# Операционный контур корпуса

Этот договор дополняет `kc-pipeline` переносимым механизмом планирования и
обслуживания корпуса. Он не заменяет предметные навыки, не определяет адаптеры
и не принимает содержательные решения.

## Назначение

Контур даёт проекту пять повторяемых операций:

- построить очереди по `workflow_stage`, карточкам единиц и артефактам рядом с
  ними.
- явно запустить зарегистрированные проектные команды одной стадии.
- пересобрать общие индексы единиц и утверждений из их владельцев.
- создать локальный отчёт конкретного запуска.
- продолжить полный проход по всем автоматическим очередям с сохранением
  состояния между сеансами агента.

Средство запуска находится в
`scripts/run-corpus-operations.py`. По умолчанию оно только читает корпус и
пишет план в стандартный вывод:

```bash
python3 .apm/skills/kc-pipeline/scripts/run-corpus-operations.py knowledge
```

Корень корпуса и все пути записи принадлежат текущему проекту. Внешний источник
или peer-корпус нельзя передавать средству как корень корпуса проекта-потребителя.
Его можно читать для проверки доступности и трассировки, но состояние прохода,
отчёты, индексы и команды обработки остаются в проекте корпуса-владельца.

## Настройки операций

Настройки не входят в обязательную раскладку корпуса. Если проекту они нужны,
он создаёт отдельный файл по образцу `assets/operations.yml` и передаёт его
параметром `--operations`. Стартовый файл содержит пустые `stages` и
`adapters`; пример синтаксиса с условными проектными командами находится в
`assets/operations.example.yml`. Регистрируй только проверенные команды.
Готовность настройки определяется применимостью операций по
`kc-setup/references/setup-readiness.md`, а не наличием команд для всех
будущих видов источников. Глобальные стадии полного прохода сохраняются
и для пустого корпуса.

```yaml
operations_version: 1
transfer_policy:
  mode: apply_now # apply_now | propose_only
impact_report:
  path: .local/reports/impact-findings.yml
report:
  path: .local/reports/corpus-operations.md
run_state:
  path: .local/state/corpus-pipeline.json
normalized_artifacts:
  - normalized.md
  - message.md
  - stenogram.txt
stages:
  source_sync:
    commands:
      - id: source-sync
        argv: [python3, tools/sync-source.py]
        working_directory: .
        write_paths: [knowledge/data/example-source]
        required: true
  normalize:
    commands:
      - id: normalize-next-batch
        argv: [python3, tools/normalize-corpus-queue.py]
        working_directory: .
        write_paths: [knowledge/data]
        required: true
```

`argv` — список аргументов без оболочки. `working_directory` и каждый путь из
`write_paths` задаются относительно корня проекта и не могут выходить за его
пределы. `write_paths` служит проверяемой границей ожидаемых изменений в Git.

`impact_report.path` указывает локальный отчёт о влиянии. Контроллер читает
находки только из него. Путь `--evidence` при ручном закрытии стадии этот
отчёт не заменяет. Проход с изменениями источников или утверждений без него
не завершается: отказ называет недостающую настройку или файл.

## Граница доверия project-команд

Каждая команда из `operations.yml` — это `trusted_project_executor`: локальная
автоматизация, которую заранее задаёт владелец проекта. Это **не** OS-level
песочница. Контроллер запускает только зарегистрированный `id` из выбранной
стадии и передаёт заранее записанный `argv` без оболочки. Он не строит команду
из title, content, URL или другого материала источника; данные источника
передаются через файлы либо через строго ограниченные параметры адаптера.

`write_paths` и evidence ограничивают принимаемый результат после исполнения,
но не делают недоверенную программу безопасной. В состоянии и owner summary
исполнитель назван `trusted_project_executor`. Неизвестный executor или
незарегистрированная команда не запускаются. Для недоверенной команды проект
должен подключить отдельный executor с доказанной OS-level sandbox; пока его
нет, операция блокируется. Стадия `apply_changes` всегда исключена: её может
закрыть только контроллер через декларативный `controlled_change_set`.

Стадия может объявить ресурсный порог:

```yaml
stages:
  transcribe:
    task_contract: compound_media
    resources:
      min_free_disk_bytes: 2147483648
      estimated_peak_disk_bytes: 10737418240
    commands:
      - id: process-next-media
        argv: [python3, tools/process-next-media.py]
        working_directory: .
        write_paths: [knowledge/data]
        required: true
```

Оба значения задаются целым числом байтов. Исполнитель запускается, если
свободное место не меньше их суммы. `compound_media` означает, что проектная
команда хранит состояние подэтапов «получить, расшифровать, проверить,
очистить», допускает безопасный повтор и удаляет только подтверждённое
временное сырьё.

Адаптер, его секреты, параметры доступа и обработка конкретного носителя
остаются в проекте-потребителе. Исполняемый реестр и формат его результата см.
в [договоре адаптеров](adapter-contract.md). Не храните в настройках токен,
cookie, пароль или закрытый адрес.

Проект может указать путь локального реестра логических профилей:

```yaml
access_profiles:
  path: .local/access-profiles.yml
```

Файл исключается из Git. Переносимая карточка хранит только вид авторизации,
необходимые возможности, логическое имя профиля и допустимость интерактивной
настройки. Секрет и данные сессии не передаются контроллеру через аргументы,
стандартный вывод или отчёт.

## Запуск команд

Команды не выполняются при обычном планировании. Для выбранной стадии нужен
явный параметр:

```bash
python3 .apm/skills/kc-pipeline/scripts/run-corpus-operations.py \
  knowledge --operations knowledge/operations.yml \
  --stage source_sync --run-commands
```

Средство запуска передаёт `argv` напрямую, сохраняет код завершения и сравнивает
снимки содержимого всех отслеживаемых и неигнорируемых файлов Git до и после
команды. Поэтому уже изменённый или добавленный в индекс Git файл нельзя
повторно изменить вне `write_paths` незаметно для контроля. Изменение за
пределами `write_paths` останавливает проход. Ненулевой код завершения
отдельного запуска `--run-commands` даёт код `1`, а в полном проходе сбой
команды первичного контура откладывает зависящие задачи (см. «Сбой команды
первичного контура»). Средство не откатывает изменения команды.
Восстановление выполняет проектная команда или следующий разрешённый запуск.
Единственное исключение — метаданные источника после неуспешного или
частичного обновления индекса (см. «Ограничения среды»).

Для отдельной диагностики адаптеров источников есть параметр
`--run-adapters`; он не заменяет обновление индексов полного прохода. Ручной
`--run-pipeline` сначала вызывает операцию `index` для каждого изменяемого
источника с `items.yml`, фиксирует дельту `added/changed/removed/unchanged`,
технические изменения и отклонённые как нерелевантные единицы, затем
пересобирает индексы и только после этого строит очереди. Для
`index_only` и `external_reference` содержимое дальше получают только у
выбранных единиц.

Версия 1 сохраняется для совместимости; при полном проходе её `fetch` может
быть использован как явно помеченный fallback для полноценных локальных
стратегий, но не для `index_only` и `external_reference`. Для версии 2 параметр
`--adapter-operation` выбирает `probe`, `index`, `fetch`, `verify` или
`authorize`. Перед `index`, `fetch` и `verify` контроллер автоматически
выполняет `probe`.
`authorize` запускается только при явном выборе и не входит в автономный
проход.

`adapter: agent` не регистрируется в `adapters`: агент выполняет описанный в
`agent_route` маршрут сам и оставляет локальное свидетельство через
`--agent-index-evidence SOURCE-ID PATH` по договору
[«Строгое свидетельство agent-index»](#строгое-свидетельство-agent-index).
`--agent-index-refreshed` оставлен только как устаревшая отметка и один не
закрывает обновление. Старое
`adapter: manual` читается только в режиме совместимости с предупреждением; без
маршрута и свидетельства источник блокирует завершение.

## Автономный проход

Параметр `--run-pipeline` означает явное разрешение запускать
зарегистрированные команды стадий. Контур каждый раз заново строит очередь,
выбирает первую непустую автоматическую стадию и требует наблюдаемого изменения
очереди после команды:

```bash
python3 .apm/skills/kc-pipeline/scripts/run-corpus-operations.py \
  knowledge --operations knowledge/operations.yml --run-pipeline
```

Имена групп в `stages` для полного прохода совпадают с очередями:
`content_selection`, `fetch`, `transcribe`, `normalize`, `statements`,
`coverage_gap`, `traceability`, `semantic_review`, `strong_review`, `corroboration`,
`source_check`, `verification`, `concepts`, `impact_audit`, `apply_changes` и
`corpus_validation`.
Исполнитель может использовать модель, локальный скрипт или внешний сервис,
но обязан обновить машиночитаемые артефакты корпуса. Если очередь глобальной
стадии не меняется, проход получает `failed` с причиной `no_progress`. Для
очереди первичного контура действует «Сбой команды первичного контура».

Этот режим не заменяет содержательную работу агента по `kc-pipeline`. Если
ближайшая очередь не имеет зарегистрированной команды, агент сам формирует
ограниченный пакет, применяет профильный навык стадии и повторно строит
очередь. Отсутствие команды означает, что контроллеру нечего запускать. Оно не
образует ресурсный блокер, пока агент может обработать пакет самостоятельно.
`paused_resources` используйте только при недоступности и проектной команды, и
агента из-за объявленного ресурса или конкретного блокера.

Агент, начавший `kc-pipeline`, считается исполнителем содержательной очереди
по умолчанию. После ограниченного пакета он сам предлагает проектную команду,
если в очереди остался незаблокированный повторяемый хвост с устойчивыми
входом, результатом, критериями качества и границей записи. В предложении
указываются наблюдение из пакета, охват, входы и выходы команды, `write_paths`,
безопасный повтор и проверка. Команду для очереди первичного контура предлагай
со `scope: unit`, чтобы сбой одной единицы не откладывал остальные. Пользователь подтверждает только невыводимый из
правил выбор: новый внешний сервис или расходы, секреты и доступы, либо
изменение содержательного результата или границы записи. Пока решения нет,
агент продолжает доступные пакеты. Отсутствие команды не создаёт
`paused_resources`.

Первые стадии выводятся из карточек, артефактов и утверждений корпуса.
Последние четыре стадии относятся ко всему проходу. Контур создаёт для каждой
глобальную задачу, выполняет их строго после первичного контура и сохраняет
завершённые глобальные стадии в состоянии. Успешная проектная команда закрывает
глобальную задачу. Поэтому отсутствие содержательных изменений должно
выражаться успешным результатом проверки, а не отсутствием исполнителя.

Если для глобальной стадии команда не зарегистрирована, единственный штатный
способ закрыть её после содержательной работы — отдельный явный режим:

```bash
python3 .apm/skills/kc-pipeline/scripts/run-corpus-operations.py \
  knowledge --operations knowledge/operations.yml \
  --complete-global-stage concepts \
  --evidence knowledge/concepts.md \
  --note "Понятия согласованы вручную, конфликтов не найдено."
```

Режим ничего не выполняет и не меняет корпус: он только записывает отметку в
файл состояния. `--evidence` обязателен, задаёт репо-относительный путь к уже
существующему артефакту содержательной работы и может повторяться; `--note`
необязателен. Параметр несовместим с `--run-pipeline`, `--run-commands`,
`--run-adapters`, `--reconcile-state` и `--rebuild-indexes` и требует
`--operations`.

Перед записью контур отклоняет запрос, если: для стадии уже зарегистрирована
команда (сломанный или недоступный исполнитель чинится через саму команду или
снимается через `kc-setup`, а не обходится ручной отметкой); файл состояния
отсутствует, у него `status: completed`, либо сохранён признак незавершённого
предыдущего исполнителя с неизвестной идентичностью — та же проверка, что и
перед `--run-pipeline`; после пересборки очередей в первичном контуре остаётся
необработанная единица, выполнимая в текущей среде (задачи непроверенного
источника из `environment_deferred` не учитываются, см. «Ограничения среды»);
закрываемая стадия не является первой незакрытой среди
глобальных по их порядку; не передан ни один `--evidence`, либо переданный
путь не существует на диске. Повторный вызов для уже закрытой стадии не
считается ошибкой: контур сообщает об этом и не меняет состояние.

Каждое такое закрытие остаётся в состоянии как запись
`global_stage_completions` со стадией, автором (`manual`), временем, списком
`--evidence` и заметкой. Для `impact_audit` и `apply_changes` дополнительно
проверяются отчёт влияния, его связь с источниками и покрытие дельты по правилам
ниже. Контур не доказывает содержательную достаточность обоснований. Итоговая операционная
проверка перед `completed` выполняется независимо и не отменяется ручным
закрытием одной стадии. Прямая правка `completed_global_stages` или
`global_stage_completions` в файле состояния запрещена в любых
обстоятельствах, включая срочность и недоступность исполнителя: только этот
режим — штатный способ.

Отчёт показывает стадию, закрытую этим режимом, с пометкой
`(вручную: <пути evidence>)`, а очередь, ожидающую именно отсутствующего
исполнителя (`executor_not_configured`), — с подсказкой про
`--complete-global-stage`.

Каждый исполнитель должен допускать безопасный повтор. Если процесс аварийно
завершится после команды, но до атомарной записи состояния, следующий запуск
может выполнить ту же стадию ещё раз. Команда должна распознавать уже
применённый результат или повторять действие без потери данных и дублирования
эффекта.

Во время команды контроллер атомарно сохраняет `active_executor`: PID, имя
очереди, идентификатор команды, время запуска и последний heartbeat. Если
контроллер или сеанс агента исчезли, перед следующим запуском или отдельной
сводкой выполните:

```bash
python3 .apm/skills/kc-pipeline/scripts/run-corpus-operations.py \
  knowledge --operations knowledge/operations.yml --reconcile-state
```

Отсутствующий PID переводит старый `running` в `paused_limit` с причиной
`executor_interrupted` без потери `run_id` и очереди. Живой PID не допускает
новый запуск. Каталог `.local/` принадлежит контроллеру, поэтому его heartbeat,
состояние и журналы не входят в `write_paths` проектной команды.

`access_unavailable` и `source_unavailable` допустимы только после двух разных
сохранённых автоматических попыток доступа. Одна неудача остаётся
неопределённостью материала, а не человеческим блокером. Исполнитель пакета
должен вносить только проверяемые изменения очереди: неисправный пакет не
объявляет весь проход завершённым и не превращает неподтверждённую диагностику
в блокер.

Локальная недоступность не меняет сохранённый `verification.yml` текущего
снимка. Она откладывает только действие, которому нужна новая прямая сверка.
Смена хэша снимка требует новой проверки происхождения. Контроллер отклоняет
неуспешную операцию адаптера, если та изменила `verification.yml`.

Состояние записывается атомарно в `run_state.path` или путь параметра
`--state`. Если предыдущий проход не был `completed`, новый запуск сохраняет
его `run_id`, увеличивает число попыток и продолжает текущую очередь.
Ограничение `--max-steps` относится только к одной попытке и переводит проход в
`paused_limit`, а не в `completed`.

На время попытки рядом с состоянием удерживается межпроцессная блокировка.
Второй исполнитель того же пути состояния завершается до чтения или изменения
очереди. После `completed` следующий запуск получает новый `run_id`.

Терминальные состояния и коды завершения:

- `completed`, код `0`: все автоматические и внешние очереди пусты, обязательные
  глобальные стадии закрыты штатно, а итоговая операционная проверка успешна.
- `paused_limit`, код `10`: лимит попытки исчерпан, доступная работа осталась.
- `paused_resources`, код `11`: автоматический хвост остался, но ни для одной
  готовой очереди нет исполнителя или объявленных ресурсов.
- `waiting_external`, код `20`: доступная работа исчерпана, остались только
  конкретные решения человека.
- `environment_limited`, код `21`: работа, выполнимая в текущей среде, доведена
  до конца, глобальные стадии закрыты по проверенной части, но часть источников
  не проверена или обследована частично либо задачи отложены до среды с
  доступом к источнику. Если остались и решения человека, состояние то же, а
  сводка владельца показывает оба остатка. Следующий запуск продолжает тот же
  `run_id`. То же состояние получает попытка, в которой после сбоя команды
  первичного контура остались отложенные задачи.
- `failed`, код `1`: предварительная проверка не пройдена, команда записала
  за пределами `write_paths` или нарушила `propose_only`, исполнитель
  глобальной стадии завершился с ошибкой или не изменил её очередь либо
  итоговая проверка не пройдена.

Поэтому успешное завершение процесса не подменяет завершение прохода. Средство
не возвращает `0` для управляемой паузы.

Планирование без `--run-pipeline`, `--rebuild-indexes` и отдельный запуск
валидатора не создают свидетельство `completed`: они могут показать пустые
локальные очереди, но не выполняют глобальные стадии. Если для
`corpus_validation` зарегистрирована команда, только её успешное выполнение в
полном проходе позволяет контроллеру закрыть эту стадию. Вывод планировщика о
незавершённой глобальной стадии должен сохранять проход незавершённым.

При ресурсной недоступности ранней очереди контроллер продолжает другие готовые
очереди первичного контура. Глобальные стадии не начинаются, пока первичный
контур не опустел. Причины отложенных очередей сохраняются в
`resource_waiting`.

## Предзапусковая и итоговая проверки

Автономный `--run-pipeline` всегда начинает с операционной проверки. Отдельный
планирующий или одностадийный запуск может запросить её параметром
`--operational-check`. Контур вызывает существующий валидатор раскладки, а не
содержит второй сканер.
Валидатор рассматривает внутри корня корпуса отслеживаемые и неигнорируемые
неотслеживаемые файлы из `git ls-files`. Он исключает `*.local.*`, `*.tmp.*`,
`local/`, `.local/` и каталоги `*.local` прежде чтения. Поэтому новый
публикуемый файл, созданный исполнителем, тоже попадает в итоговую проверку. В
отчёте остаются только путь, номер строки и вид находки, поэтому найденное
значение не копируется в локальный отчёт.

После закрытия всех очередей тот же контроль запускается повторно. Между ним и
записью `completed` команды стадий больше не выполняются. Ошибка договора,
секрет или другой операционный блокер переводит проход в
`failed/postflight_failed`, даже если команда `corpus_validation` завершилась
успешно.

Результат разделён на ошибки договора, блокеры доступа (`access-secret`,
`credentialed-url`), предупреждения качества (`personal-data`) и очереди
корпуса. Открытый контакт в метаданных источника фиксируется отдельно и сам по
себе не блокирует запуск. Ложное срабатывание разрешается подавить только
правилом с причиной:

```text
... --operational-check --operational-policy knowledge/operational-check.yml
```

Шаблон правила находится в
`kc-inventory/assets/operational-check.yml`. Подавление меняет
классификацию, но не выводит чувствительное значение и не заменяет решение о
публикации.

## Индексы и восстановление

После успешной синхронизации полного прохода производные индексы пересобираются
автоматически. Для отдельного восстановления используйте:

```bash
python3 .apm/skills/kc-pipeline/scripts/run-corpus-operations.py \
  knowledge --operations knowledge/operations.yml --rebuild-indexes
```

Новые файлы индексов строятся полностью до записи; каждый из них создаётся во
временном файле и заменяется без появления частично записанного файла. Если
запуск прервался между заменами, карточки источников остаются владельцами
данных, а следующий запуск с `--rebuild-indexes` восстанавливает согласованную
пару общих индексов. После восстановления нужно выполнить проверку корпуса,
заданную проектом.

## Локальный отчёт

Отчёт описывает конкретный запуск: состояние прохода, размер и полный состав
очередей, дельту индексов, коды завершения команд и число записей в
пересобранных индексах. Он обязательно содержит краткую сводку владельца:
`run_id`, конечное состояние, счётчики единиц и утверждений, существенные
сведения, поверхности, применённые и предложенные изменения, точные решения,
блокеры и ограничения. Технический отчёт и отчёт влияния остаются отдельными
артефактами; сводка только собирает проверяемый результат. Если существенных
предложений нет, причина указывается явно. Полный хвост также сохраняется в
JSON-состоянии и не теряется из-за ограничения краткой сводки.

Пока стадия `impact_audit` не закрыта, при построении промежуточной сводки
контроллер не читает отчёт влияния: по тому же пути ещё может лежать отчёт
предыдущего прохода. Проверка отчёта при закрытии стадии остаётся обязательной.

Счётчики `added`, `changed`, `removed` и `unchanged` образуют основные категории
дельты. `technical_only` и `rejected` — дополнительные измерения: первое является
подмножеством `changed`, второе может пересекаться с основными категориями.
Поэтому сводка сообщает `unit_counts_are_unique_ids: false` и явно перечисляет
`primary_unit_categories` и `additional_unit_dimensions`.

Пересборка общего индекса выполняется как восстанавливаемая транзакция двух
производных файлов. До замены сохраняется локальный журнал с временными файлами;
если процесс прерван между заменами, следующий запуск сначала проверяет уже
установленный файл и завершает недостающую замену. Наличие только одного файла
не считается завершённой пересборкой.

`human_attention.max_active_groups` ограничивает только число групп решений в
кратком представлении. По умолчанию используются 20 групп. Состояние хранит
полное число элементов, все сгруппированные причины, активные группы и число
групп за пределами бюджета. Группа объединяет одинаковые `blocker_code`,
требуемое действие и последствия, выраженные конкретной причиной. Она называет
автоматические попытки и примеры.

Запись отчёта происходит только по явному запросу:

```bash
python3 .apm/skills/kc-pipeline/scripts/run-corpus-operations.py \
  knowledge --operations knowledge/operations.yml --write-report
```

Путь `report.path` должен вести в неотслеживаемый локальный слой. Не добавляйте
такой отчёт в Git.

## Очереди

Средство использует переносимые очереди `content_selection`, `fetch`,
`transcribe`, `normalize`, `statements`, `coverage_gap`, `traceability`, `semantic_review`,
`strong_review`, `corroboration`, `source_check`, `verification`, `concepts`, `impact_audit`,
`apply_changes`, `corpus_validation` и `human_decision`.

Очередь `coverage_gap` планировщик строит из `source-map.yml` каждого источника
с `long_source: true`: незакрытая структурная единица или `postponed` без
валидного кода блокера попадает сюда, а `postponed` с кодом блокера — в
`human_decision`. Подробности критерия — в `workflow-contract.md`, раздел
«Полнота внутри источника», и в ADR-0009.
Штатная стадия `indexed` не считается неподдерживаемой:

- единица обычного источника без выбранного объёма обработки попадает в
  `content_selection`.
- единица с `processing_scope: selected_fragments`, `full` или
  `full_redacted` попадает в `fetch` для точечного получения.
- единица источника со `storage_strategy: index_only` без выбранного объёма
  обработки не образует массовую очередь: обновлённый индекс завершает
  штатный проход такого источника.

Неподдерживаемая стадия считается ошибкой договора. `blocked` попадает в
`human_decision` только с допустимым `blocker_code`. Содержательный отбор должен
завершиться явным решением: выбрать единицу для точечного получения, отклонить
её с причиной или отправить в `human_decision` только вопрос, который
действительно требует решения человека.

Имена нормализованных артефактов настраиваются через `normalized_artifacts`.
Сырая `transcript.txt` не считается нормализованным артефактом: она оставляет
единицу в очереди нормализации.

Для договора утверждений версии 2 очереди проверки строятся по
`processing_status`. Сила основания, уверенность извлечения, возраст сведений
и наличие независимого подтверждения не определяют завершённость обработки.
В старом договоре `status: candidate` попадает в автоматическую
`semantic_review`, а не в `human_decision`.

## Строгое свидетельство agent-index

Свидетельство agent-index версии 1 содержит `contract_version`, текущий
`run_id`, `source_id`, `source_locator`, совпадающий с локатором карточки,
`operation: index`, `allowed_write_scope`, равный узкому `write_scope`
маршрута, `checked_paths` со всеми файлами области, `changed_paths`, снимки
`before` и `after` с `snapshot_hash` и полной картой хэшей `paths`, а также
`result`.
Для `external_reference` и агентного `index_only` нужна версия 2 с блоком
[`observation`](#наблюдение-внешнего-источника): версия 1 оставляет такой
источник непроверенным.

Для результата `changed` список `changed_paths` непуст и в точности равен
различиям карт; снимки источника тоже должны различаться. Для `no_change` снимки и
`changed_paths` эквивалентны. Для `unavailable` снимки эквивалентны,
`changed_paths` пуст, а `attempts` перечисляет не менее двух разных
автоматических попыток; источник остаётся непроверенным в этой среде. Любой
иной результат, другой запуск, неполная карта или путь вне области оставляет
источник непроверенным с видом `failure`, остальные источники продолжают
проход.

### Наблюдение внешнего источника

Для `external_reference` и агентного `index_only` локальные файлы не доказывают
полноту обновления. Агент предъявляет свидетельство версии 2: прежние поля
версии 1 сохраняются, к ним добавляется `observation`. Зарегистрированный
адаптер внешней ссылки передаёт такой же блок в результате операции `index`.
Зарегистрированный `index_only` по-прежнему может обновлять полный навигационный
`items.yml` без этого блока. Если он передаёт `observation`, дельта строится
по наблюдению. Агентные свидетельства версии 1 сохраняют прежний смысл для
локальных стратегий, но не подтверждают указанные внешние режимы.

```yaml
observation:
  scope: cards-navigation-v1
  complete: true
  evidence:
    - 'Навигация поставщика и отпечатки выбранных договором файлов'
  units:
    CARD-1:
      locator: cards/card-1
      fingerprint: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
```

`scope` — устойчивое обозначение сопоставимой области обследования, заданной
договором источника. `complete` подтверждает её полный охват, а `evidence`
позволяет установить способ получения состава и отпечатков. `units` хранит
только устойчивые идентификаторы, локаторы и SHA-256, без копии содержания и
состояния обработки. Отпечаток единицы должен учитывать все влияющие на неё
материалы, включая изображения и незакоммиченные изменения рабочей копии.
Один Git HEAD или число карточек этого не подтверждает. Конкретный способ
обследования остаётся у исполнителя, контроллер проверяет договор свидетельства.

Пустой `units: {}` допустим для обследованной пустой области. Отсутствующее
наблюдение оставляет источник непроверенным. `complete: false` означает
частичное обследование: дельта строится только по наблюдённым единицам,
необследованные сохраняют прежнюю базу и не считаются исчезнувшими, а источник
остаётся проверенным частично. При изменении `scope` сравнение останавливается:
исполнитель должен сохранить сопоставимую область или через `kc-setup`
определить переход с сохранением прежнего основания. Частичное наблюдение
нельзя переименовать в полное ради завершения.

В версии 2 `result: changed` допускает пустой `changed_paths`, если изменилось
внешнее наблюдение. `no_change` требует неизменности и локального индекса, и
наблюдения. Карты `before.paths` и `after.paths` продолжают описывать только
локальную область записи, они не подменяют наблюдение источника.

Наблюдения сохраняются в `index_sync.observations`, исходные — в
`baseline_observations`. Без прежнего наблюдения и без переносимой базы состав
впервые обнаружен, а не исторически добавлен относительно продукта.
Закреплённую версию продукта агент сопоставляет отдельно при анализе
последствий. До завершения прохода `baseline` и `baseline_observations` не
сдвигаются при повторном запуске.

Отчёт должен покрыть все добавления, содержательные изменения и удаления.
Технические изменения и явно отклонённые единицы сохраняют свою классификацию
и не требуют искусственных рекомендаций. Одна находка может покрывать поимённо
перечисленную группу единиц и утверждений с общим основанием. Находка на
«остальную часть дельты» недопустима. `source` обозначает основной источник и
совпадает с `source_delta.source_id`, дополнительные основания остаются в
`basis`. Удалённая единица проверяется по прежнему снимку. Ссылка на
неизменившийся источник не закрывает изменение другого источника.

Покрытие проверяется и по утверждениям. В начале прохода состояние сохраняет
базу утверждений `statement_baseline`, которая не сдвигается до завершения
прохода. Каждое утверждение, которого нет в базе или у которого изменились поля
кроме `processing_status`, `checked_at`, `checked_by` и `last_checked_at`,
должно войти в `statements` хотя бы одной находки. Ссылка на неизвестное
утверждение отклоняется. Если незавершённый проход начат версией без
`statement_baseline`, базой служит снимок утверждений после последней попытки.

Одна проверка покрытия используется при закрытии анализа вручную, после
проектной команды, перед переносом и в итоговой сводке. Она не заменяет чтение
содержания и проверку смысла обоснований. Проверенный анализ связан через
`index_sync.impact_review_hash` с исходными данными и байтами отчёта. Если они
изменились или у старого незавершённого прохода такой связи нет, повторный
полный запуск открывает `impact_audit`, `apply_changes` и `corpus_validation`.
Прочие стадии сохраняются. После исправления свидетельства повторите
`--run-pipeline`, затем обработайте заново открывшуюся очередь штатным способом.

## Ограничения среды

Корпус сопровождают разные люди в разных средах, и в каждой могут быть свои
ограничения: сеть, учётные данные, инструменты, ресурсы. Ограничение сужает
проход, а не останавливает его.

Обновление индекса каждого источника получает один из итогов, записанных в
`index_sync`:

- `checked_sources` — источник проверен полностью;
- `partial_sources` — обследована часть источника. Частичный ответ
  зарегистрированного адаптера (`partial`) и наблюдение с `complete: false`
  строят дельту только по наблюдённым единицам. Необследованные единицы
  перечислены в `unobserved` и сохраняют прежнюю базу;
- `unchecked_sources` — источник не проверен. Запись хранит статус, причину и
  вид ограничения: `environment` (доступ, сеть, профиль, недоступность),
  `configuration` (настройка проекта: неверный маршрут, незарегистрированный
  адаптер, решение об условиях) или `failure` (нарушение договора результата).
  Прежний индекс источника остаётся базой сравнения, а в дельту этого прохода
  источник не входит.

Исчезновение единицы признаётся только по полному обследованию области, в
котором её нет, или по явному признаку снятия с публикации у доступного
источника. Удаление материалов и утверждений по-прежнему требует решения
владельца.

Перед операцией `index` зарегистрированного адаптера контроллер держит копию
`items.yml` источника и файлов `item.yml`, `statements.yml` и
`verification.yml` в его каталоге (ADR-0016). После неуспешной операции он
побайтно возвращает каждый изменённый или удалённый файл из копии. После
частичной операции изменения обследованных единиц сохраняются: контроллер
возвращает в `items.yml` строки пропавших единиц и удалённые файлы метаданных.
Форматирование `items.yml` при этом может измениться. Запись источника
перечисляет `restored_paths` и `restored_units`. Восстановление выполняется до
пересборки производных индексов, поэтому свод утверждений и дельта видят
прежнее состояние источника. Если операция удалила другой файл каталога,
например материал, источник получает вид `failure` со списком `deleted_paths`:
такой файл нужно вернуть по Git или из резервной копии. Свидетельство
агентного маршрута фиксируется после работы агента, поэтому для него
изменение локального индекса только обнаруживается (`index_modified: true`).

Задачи очередей `fetch`, `source_check` и `verification` непроверенного
источника откладываются в `environment_deferred` состояния прохода с причиной
`source_not_checked_in_environment`. Остальные задачи всех источников
выполняются обычным порядком. Глобальные стадии начинаются, когда в первичном
контуре не осталось работы, выполнимой в текущей среде. Отчёт влияния не может
сослаться на дельту непроверенного источника, поэтому вывода ни об изменении,
ни об отсутствии изменений для него нет. Сводка владельца перечисляет
непроверенные источники в `unchecked_sources` с видом ограничения и датой
последней успешной проверки.

Источник `adapter: agent` без свидетельства не считается ограничением среды:
проход получает `awaiting_agent_task` с причиной
`agent_index_evidence_required` до построения содержательных очередей. Если
агент не может получить источник в этой среде, он предъявляет свидетельство с
`result: unavailable` и списком `attempts` не менее чем из двух разных
автоматических попыток. Такое свидетельство не допускает изменений индекса.
Одна попытка доказательством недоступности не считается, и источник остаётся
непроверенным с видом `failure`.

### Переносимая база сравнения

Рядом с карточкой каждого проверенного источника контроллер ведёт
отслеживаемый файл `index-baseline.yml`:

```yaml
contract_version: 1
source_id: SOURCE-ID
checked_at: '2026-11-19T10:00:00+00:00'
reviewed_at: '2026-11-19T10:05:00+00:00'
units:
  UNIT-1:
    fingerprint: aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
  UNIT-2:
    fingerprint: bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb
    eligible: false
observation:
  scope: cards-navigation-v1
  units:
    CARD-1:
      locator: cards/card-1
      fingerprint: cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc
```

`fingerprint` единицы — SHA-256 её записи индекса без технических полей
`change_policy`. `observation` хранится только для источников с наблюдением.
Файл не содержит копии содержания, сведений о среде, причин недоступности и
состояния прохода; его проверяет валидатор раскладки.

`checked_at` обновляется после каждой успешной полной проверки индекса.
Состав и `reviewed_at` сдвигаются только после того, как проход с итогом
`completed` или `environment_limited` закрыл анализ влияния, покрывающий дельту
источника. Новый проход в любой среде сравнивает источник с этим составом:
единица с совпадающим отпечатком сравнивается со своей текущей записью, а
изменённая после рассмотрения считается изменённой. Поэтому изменение,
закоммиченное другой средой без анализа влияния, остаётся в дельте. Если файла
нет, используется прежний порядок: последнее локальное состояние или текущий
`items.yml`. Продолжение незавершённого прохода в той же среде использует базу
из его состояния. Файл ведёт контроллер; карта области агентного свидетельства
его не включает. Новые и изменённые файлы базы нужно закоммитить вместе с
остальными изменениями корпуса.

## Сбой команды первичного контура

Сбой проектной команды по одной единице откладывает только зависящую работу
(ADR-0015). Команда стадии первичного контура может объявить `scope: unit`:

```yaml
stages:
  fetch:
    commands:
      - id: fetch-unit
        scope: unit
        argv: [python3, tools/fetch-unit.py, "{unit_id}", "{source_id}", "{unit_path}"]
        working_directory: .
        write_paths: [knowledge]
        required: true
```

`scope: unit` задаётся всем командам стадии и недоступен глобальным стадиям.
Контроллер запускает такую стадию отдельно для каждой задачи очереди.
`{unit_id}` и `{source_id}` проверяются по шаблону идентификатора, а
`{unit_path}` — по нахождению внутри корня проекта. Содержание единицы в
`argv` не передаётся.

Ненулевой код завершения и отсутствие продвижения откладывают задачу в
`environment_deferred` с причиной `command_failed` или `command_no_progress` и
видом `failure`. Отказ запуска, например отсутствующий инструмент, даёт причину
`command_unavailable` и вид `environment`. Для команды со `scope: unit`
откладывается одна единица, для команды без него — оставшаяся очередь стадии,
а отчёт советует перевести команду на запуск по единице. Остальные очереди и
глобальные стадии продолжаются, а попытка с таким остатком завершается
`environment_limited`.

Запись хранит очередь, единицу, команду, код завершения и
`consecutive_failures`. После двух подряд неудачных попыток по той же единице
запись получает `repeated: true`. Счётчики хранятся в `command_failures`
локального состояния, вывод команды — только в локальном отчёте. Каждая новая
попытка заново пробует отложенные задачи. В решения человека сбой
автоматически не переводится. Сбой глобальной стадии, запись за пределами
`write_paths` и нарушение `propose_only` по-прежнему дают `failed`.

## Авторизация поверхностей продукта

Проект-потребитель обязан объявить в `operations.yml` `surface_paths`: для
каждой допустимой поверхности — непустой список относительных узких путей или
шаблонов. В finding каждый `target_path` связывается с одной из
`affected_surfaces` через `target_surfaces`; при одной поверхности связь может
быть выведена однозначно. Без сопоставления proposal/apply_now останавливается.
Контроллер проверяет target, фактический post-apply diff и симлинки; все они
должны остаться в объявленной области. Каждая finding также хранит `source_delta`
со стабильными `unit_ids` допустимой текущей дельты. Отклонённая или
нерелевантная единица не может стать основанием finding, proposal или правки.
