# Допуск материала в корпус

Решение изменить проект и разрешение включить материал в корпус — разные
действия. Поручение, подтверждение гипотезы или введение термина не разрешают
автоматически сохранять рабочий разговор как источник. Предоставленный для
обработки документ тоже не становится допущенным только из-за `user_provided`.

Проверяй допуск до регистрации, копирования, нормализации и извлечения
утверждений. Запрет включения распространяется и на фрагменты, пересказ и
производные утверждения из того же материала. Для принятого проектного решения
сохраняй отдельную запись решения по правилам проекта. Понятие может ссылаться
на неё без создания источника из разговора.

## Политика проекта

При настройке корпуса `kc-setup` находит правила допуска и через `kc-inventory`
фиксирует их в `corpus.yml.source_admission`. Собственный договор проекта
сохраняется, если он обеспечивает ту же проверку. Стартовый шаблон исключает
рабочие разговоры с агентом. Остальные материалы требуют решения владельца,
пока проект не установит правило их автономного добавления.

```yaml
source_admission:
  version: 1
  default: require_approval
  rules:
    - id: reference-documents
      origins: [external_material]
      locator_prefixes: ["https://example.org/reference/"]
      action: allow
    - id: development-dialogues
      origins: [working_dialogue]
      action: prohibit
```

`default` принимает `require_approval` или `prohibit`. У правила обязательны
уникальный `id`, непустые `origins` и `action`: `allow`, `require_approval` или
`prohibit`. Происхождения разных правил не пересекаются. Необязательный
`locator_prefixes` сужает правило до перечисленных префиксов локатора.
За пределами префиксов действует `default`. Префикс сайта заканчивай `/`, чтобы
не разрешить другой домен с похожим именем.

Происхождение материала независимо от носителя и смыслового вида:

- `external_material` — материал, существующий вне текущего рабочего диалога.
- `project_artifact` — самостоятельный артефакт проекта.
- `working_dialogue` — поручения, ответы и обсуждение человека с агентом при
  работе над проектом.
- `unknown` — происхождение пока не установлено. Правило `allow` для него
  запрещено.

Форумная тема, исследовательское интервью или архив переписки могут быть
самостоятельным внешним материалом. Не запрещай весь `source_kind: discussion`.
Переименование рабочего диалога в документ или решение не меняет его
происхождения. Пересказ рабочего диалога также остаётся `working_dialogue`.
Самостоятельная запись принятого решения — `project_artifact`, но её создание
не разрешает автоматически включить её в корпус.

`prohibit` нельзя обойти разовым решением в карточке. Для исключения владелец
меняет политику. `require_approval` допускает отдельное решение. Действующее
`allow` применяется без повторного вопроса для каждого подходящего источника.
Допуск не заменяет ограничения получения, обработки, хранения и публикации из
`action_policy`, `use_policy` и условий источника.

## Карточка источника и единицы

При принятой политике карточка источника содержит:

```yaml
provenance:
  origin: external_material
  locator: "https://example.org/reference/topic"
admission:
  rule: reference-documents
```

`admission` содержит ровно один ключ: `rule` либо `decision`. Правило должно
разрешать фактическое происхождение и локатор. Для решения используй ссылку и
хэш по следующему разделу. `status: approved`, `copy_policy` и заявления агента
не заменяют ни правило, ни решение.

Единица наследует происхождение и допуск источника. Если у неё другое
происхождение или локатор, запиши `provenance` и отдельный `admission` в её
карточке. Решение для единицы покрывает `scope.items`, а не только источник.
Происхождение в `items.yml` и локальном `item.yml` должно совпадать.

## Проверяемая запись решения

`decision.ref` — путь относительно корня проекта к файлу вне корпуса.
`decision.sha256` — SHA-256 байтов этого файла. Для вложенной папки корпуса
явно передавай валидатору `--project-root`. По умолчанию корень проекта —
родитель папки корпуса.

Запись — YAML или Markdown с заголовочным блоком YAML:

```yaml
status: accepted
decided_by: "Владелец проекта"
decided_at: 2026-10-08
scope:
  sources: [EXAMPLE]
  origins: [external_material]
decision: "Использовать указанный документ как источник проекта."
```

Для единицы используй `scope.items`, для определения понятия —
`scope.concepts`. Разрешение источника или единицы дополнительно покрывает
`scope.origins`. В карточке сохраняется:

```yaml
admission:
  decision:
    ref: docs/decisions/example.yml
    sha256: "<64 шестнадцатеричных символа>"
```

Путь не должен быть абсолютным, выходить из проекта через `..` или символическую
ссылку либо вести внутрь корпуса. Смена записи решения требует повторной
проверки области и обновления хэша. Не создавай принятую запись или её хэш как
замену отсутствующему разрешению человека. Записывай только уже состоявшееся
решение и сохраняй отдельно доступное свидетельство его принятия по правилам
проекта.

## Проверки и совместимость

```text
python scripts/validate-corpus-layout.py knowledge --project-root . --strict-admission
python scripts/validate-corpus-layout.py knowledge --project-root . --admission-only
```

Первый запуск проверяет корпус целиком. Второй проверяет допуск до обработки,
не требуя завершённой нормализации или извлечения. При отказе код завершения —
`1`. Контроллер `kc-pipeline` для принятой политики выполняет второй запуск
перед операциями записи. При отказе он не запускает исполнителей и не записывает
состояние, индексы или изменения продукта. Просмотр очередей остаётся доступным.

Для старого корпуса без `source_admission` обычная проверка сохраняет прежний
код завершения и предупреждает, что допуск не проверен. `--strict-admission` и
`--admission-only` требуют настройку. При её включении проверь существующие
источники, а не присваивай им допуск автоматически. Не удаляй ранее сохранённые
данные без разрешения. Не объявляй настройку законченной, пока остались
неразрешённые случаи.

Автоматическая проверка подтверждает форму, применимость записанного правила,
существование, хэш, статус и область записи решения. Она не устанавливает,
правдиво ли агент описал происхождение и действительно ли человек принял
решение. Проекту нужна содержательная приёмка новых источников и изменений
политики. При проверке через CI сравнивай политику с принятой базой: изменение
правила в той же правке источника не считается прежним разрешением.
