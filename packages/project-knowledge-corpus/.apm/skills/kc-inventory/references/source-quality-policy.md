# Договор качества и покрытия источников

Этот договор применяет проект-потребитель к своему набору карточек источников.
Коллекция не хранит конкретный рабочий корпус и не считает какой-либо набор
источников достаточным без критериев владельца.

## Исполняемый договор

Машиночитаемый договор хранится в JSON по шаблону
[`assets/source-quality-policy.json`](../assets/source-quality-policy.json).
Он не содержит конкретный корпус поставщиков. Проверка стандартной библиотекой
Python запускается так:

```text
python scripts/check-source-quality.py --policy policy.json --sources sources.json --events events.json
```

В `areas` задаются обязательные provider/topic areas, роли `discovery` и
`evidence`, максимальный возраст успешной проверки, минимум первичных источников,
предпочтительное каноническое свидетельство, допустимые подтверждающие источники
и поля ключа события. `owner_exceptions` содержит `area_id` и проверяемую причину
исключения владельца. Результат строит матрицу со статусами `covered`,
`degraded` или `missing`, рекомендации `add`/`keep` и объединённые события с
каноническим и подтверждающими свидетельствами. Он передаётся в owner summary
как evidence проверки покрытия.

## Учёт покрытия

Для каждой поставляемой владельцем области укажите: `provider_or_topic`, нужные
типы событий, минимальную свежесть, способ обнаружения, требуемый вид
свидетельства и критерий достаточности. Для каждой карточки источника укажите
область покрытия, роль `discovery` и/или `evidence`, первичность, последний
успешный проверяемый снимок и интервал обновления. Отсутствующий источник,
просроченный снимок или источник только `on_demand`/`manual` — это явно
непокрытая способность обнаружения, а не достаточное покрытие.

Предпочитайте первичное свидетельство. Для обнаружения сначала выбирайте
официальный changelog, release feed, RSS/Atom, GitHub Releases или
документированный индекс; неограниченный web search допускается только как
вспомогательное discovery-средство и не заменяет устойчивый маршрут обновления.

Результат проверки содержит по каждой области: состояние `covered`, `partial`
или `uncovered`; фактический discovery-маршрут; последнее успешное обновление;
пробел; и рекомендацию `add`, `keep`, `replace` или `remove` с причиной.
`covered` возможен лишь при выполнении всех заранее записанных критериев.

## События и дедупликация

Один выпуск может быть одновременно в changelog, документации, блоге,
release notes и GitHub Release. Создайте устойчивый ключ события из поставщика,
официального идентификатора или версии, даты и нормализованной темы. Сначала
сопоставляйте по ключу, затем по URL и хэшу/заголовку. Выберите одно
каноническое первичное свидетельство; остальные URL сохраните как
`corroborating_evidence`, не создавая дублирующее утверждение или proposal.

Если первичное свидетельство отсутствует, это ограничение доказательства, а не
основание повысить вторичный материал до первичного. В owner summary выводите
покрытие, свежесть, пробелы, рекомендации и выбранное каноническое свидетельство
с дополнительными ссылками.
