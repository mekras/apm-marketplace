# Навык: проверка доступности знаний

## Назначение

Навык строит и запускает выборочную проверку способности модели находить через
корпус важные утверждения первоисточников. Проверка оценивает качество
приближённо и не обещает полноту всего корпуса.

Навык разделяет четыре кандидата причины неудовлетворительного результата:

1. целевой смысл не представлен в слое утверждений;
2. модель не указала доступное основание;
3. модель указала основание, но исказила его в ответе;
4. проверочный вопрос или эталон составлены неправильно.

## Когда применять

Применяй навык, если нужно:

- оценить доступность знаний корпуса для выбранной модели;
- сравнить версии корпуса, модели или способа поиска;
- построить набор проверочных вопросов из первоисточников;
- разобрать, на каком этапе теряется нужное утверждение;
- превратить реальный неудовлетворительный ответ в постоянную проверку.

Для формальной целостности корпуса используй `kc-validation`. Для извлечения
утверждений используй `kc-statements`. Проверки самого навыка не смешивай с
проверкой пользовательского корпуса.

## Входные данные

Нужны:

- корень корпуса и его договор структуры;
- доступные первичные или нормализованные материалы;
- область проверки: источники, темы или пользовательские задачи;
- способ запуска модели через адаптер;
- подтверждение, что выбранным моделям разрешено читать корпус и опорные
  фрагменты;
- локальный файл настроек модельного прогона.

Если источник нельзя передавать выбранной модели, не запускай прогон через этот
адаптер. Зафиксируй ограничение и выбери допустимую среду.

## Обязательный порядок

### 1. Зафиксировать измеряемый сценарий

Укажи модель, способ доступа к корпусу, область источников и ожидаемый
пользовательский сценарий. Не сравнивай результаты разных условий как одну
выборку.

### 2. Выбрать фрагменты независимо от слоя утверждений

Сначала выбери структурные единицы или фрагменты первоисточников. Не начинай с
готовых `statements.yml`.

Для воспроизводимой выборки можно использовать:

```bash
python3 scripts/sample-source-sections.py CORPUS_ROOT \
  --source data/example/documents/guide/normalized.md \
  --count 10 --seed 20260724 \
  --suite-id guide-sample \
  --output knowledge-evaluation.local.yml
```

Случайный выбор не определяет важность. Он только мешает составителю выбирать
наиболее удобные места.

### 3. Подготовить целевое утверждение

Составитель видит выбранный фрагмент первоисточника, но не читает извлечённые
утверждения этого источника. Он фиксирует:

- одно проверяемое целевое утверждение;
- класс и основание важности;
- границы применимости;
- допустимые варианты ответа;
- недопустимые усиления смысла.

Другой человек или отдельная модельная сессия проверяет, что утверждение прямо
следует из опорного фрагмента. Автор и проверяющий должны иметь разные
идентификаторы в карточке примера.

Для каждого примера владелец также фиксирует в `access_review`, можно ли
передавать выбранный опорный фрагмент модели-судье.

### 4. Построить вопросы

Для принятого примера подготовь не менее двух вопросов:

- прямой естественный вопрос;
- перефразированный вопрос без характерных слов источника.

Прикладной вопрос добавляй, если он соответствует реальной задаче пользователя.
Отдельная сессия проверяет понятность, однозначность и отсутствие подсказки
ответа в вопросе.

### 5. Проверить набор

Формат описан в `references/evaluation-protocol.md`, а заготовка находится в
`assets/evaluation-suite.yml`.

```bash
python3 scripts/validate-evaluation-suite.py \
  knowledge-evaluation.local.yml --corpus-root CORPUS_ROOT
```

Пример со статусом `approved` не проходит проверку без независимой проверки
целевого утверждения и вопросов.

### 6. Запустить раздельные сессии

Скопируй `assets/evaluation-config.yml.sample` в локальный файл, настрой
адаптеры и явно подтверди допустимые границы доступа.

```bash
python3 scripts/run-evaluation-suite.py \
  knowledge-evaluation.local.yml \
  --config knowledge-evaluation-config.local.yml \
  --corpus-root CORPUS_ROOT \
  --output knowledge-evaluation-results.local.json
```

Средство запуска создаёт отдельные вызовы для:

- проверки представленности целевого смысла в `statements.yml`;
- ответа через корпус без показа эталона;
- ответа без корпуса, если включён базовый режим;
- сравнения ответа с целевым смыслом и опорным фрагментом.

Модель-судья не создаёт эталон. Она только сравнивает ответ с заранее
зафиксированным основанием.

Набор, настройка и отчёт должны находиться вне корня корпуса. Инспектор получает
рабочую копию только `statements.yml`. Адаптер обязан изолировать модель текущим
рабочим каталогом и соблюдать сигнал `KC_EVALUATION_READ_ONLY=1`. Без такой
изоляции прогон не считается измерением по этому протоколу.

### 7. Разобрать результат по слоям

Отчёт должен отдельно показывать:

- представленность целевых смыслов в слое утверждений;
- успешность ответов через корпус;
- наличие существующего основания по проверенному самоотчёту модели;
- соответствие ответа источнику;
- результат без корпуса;
- прирост от использования корпуса;
- разбивку по классам важности и видам вопросов;
- транспортные ошибки и ограничения проверки.

Не своди разные причины отказа к одному показателю.

### 8. Сопровождать набор

Не пересоздавай принятые примеры при каждом прогоне. Сохраняй их как
версионируемый набор или как закрытую контрольную выборку по политике проекта.
Реальный неудовлетворительный ответ добавляй как новый пример после проверки
источника и вопроса.

## Решение о скриптах

- выбор разделов, хэши, проверка формата и подсчёт показателей выполняются
  скриптами, потому что правила детерминированы;
- выбор важного смысла и проверка содержательного соответствия выполняются
  моделью или человеком, потому что требуют суждения;
- модельный прогон отделён от обычных тестов коллекции, потому что зависит от
  локальных адаптеров, доступа и стоимости.

## Что читать дополнительно

- Формат набора, роли, показатели и классификацию отказов см. в
  `references/evaluation-protocol.md`.
- Начальную заготовку набора см. в `assets/evaluation-suite.yml`.
- Образец локальной настройки адаптеров см. в
  `assets/evaluation-config.yml.sample`.

## Ограничения

- Синтетическая выборка не заменяет реальные вопросы пользователей.
- Совпадение моделей составителя и проверяющего повышает риск общей ошибки.
- Успех без корпуса уменьшает доказательность примера как проверки корпуса.
- Самоотчёт модели о найденных файлах не равен полной трассе поиска.
- Для ранжированного поискового механизма нужны дополнительные показатели по
  фактически возвращённым результатам.
- Открытый набор подходит для воспроизводимости, но закрытая или поздно
  сформированная выборка лучше выявляет подгонку.

## Результат

Результат применения навыка — проверенный набор примеров, машинный отчёт
модельного прогона и обоснованные кандидаты мест, где корпус теряет доступные
знания.
