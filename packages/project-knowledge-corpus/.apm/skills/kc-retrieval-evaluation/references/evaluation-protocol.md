# Протокол проверки доступности знаний

## Единица проверки

Единица проверки связывает:

1. неизменяемый опорный фрагмент первоисточника;
2. одно целевое утверждение;
3. основание важности;
4. два или более пользовательских вопроса;
5. критерии приемлемого и недопустимого ответа;
6. сведения о независимой проверке.

Целевое утверждение хранит смысл эталона, а не единственную обязательную
формулировку ответа.

## Формат набора

Корень файла YAML:

```yaml
suite_version: 1
id: example-suite
description: "Выборка по руководству пользователя."
cases: []
```

Карточка принятого примера:

```yaml
- id: example-001
  status: approved
  source:
    artifact: data/example/documents/guide/normalized.md
    line_start: 10
    line_end: 18
    sha256: 0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
  target:
    text: "При изменении договора нужно повторно проверить зависящие документы."
    importance_class: rule
    importance_rationale: "Правило влияет на порядок сопровождения проекта."
    limitations: []
  acceptable_answers:
    - "После изменения договора нужно перепроверить зависимые документы."
  must_not_claim:
    - "Любое изменение требует переписать все документы проекта."
  corpus_expectation:
    representation: unknown
    statement_ids: []
  questions:
    - id: example-001-direct
      type: direct
      text: "Что нужно сделать с зависимыми документами после изменения договора?"
    - id: example-001-paraphrase
      type: paraphrase
      text: "Как изменение основного соглашения влияет на связанные материалы?"
  provenance:
    target_author: model-a/session-1
  review:
    target_entailment: confirmed
    target_reviewer: model-b/session-2
    question_answerability: confirmed
    question_reviewer: model-c/session-3
  access_review:
    source_evidence_to_judge: approved
    reviewed_by: owner/session-4
    rationale: "Выбранному судье разрешена передача этого фрагмента."
```

Путь `source.artifact` задаётся относительно корня корпуса. Номера строк
начинаются с единицы и включают обе границы. `sha256` вычисляется по
UTF-8-представлению выбранных строк после соединения символом перевода строки.

Статусы примера:

- `candidate` — фрагмент выбран, но содержательная карточка не принята;
- `approved` — эталон и вопросы прошли независимую проверку;
- `rejected` — пример отклонён, причина сохраняется в `rejection_reason`.

`corpus_expectation` заполняется только после принятия целевого утверждения.
Он фиксирует ожидаемую представленность смысла и известные идентификаторы либо
значение `unknown`. Средство запуска независимо повторяет проверку и показывает
совпадение или расхождение с ожиданием.

## Классы важности

Допустимые значения `importance_class`:

- `definition`;
- `rule`;
- `constraint`;
- `procedure`;
- `criterion`;
- `fact`;
- `limitation`;
- `example`;
- `conflict`.

Класс нужен для стратификации. Он не доказывает важность сам по себе, поэтому
`importance_rationale` обязательно объясняет значение утверждения для
пользовательской или проектной задачи.

## Независимость ролей

Минимально разделяются:

- автор целевого утверждения;
- проверяющий соответствие источнику;
- проверяющий вопросы;
- отвечающая модель;
- модель-судья.

Разные идентификаторы сессий обязательны для автора и проверяющего целевого
утверждения. Желательно использовать разные модели или семейства моделей.
Совпадение моделей нужно записывать как ограничение отчёта.

Составитель целевого утверждения читает только выбранный фрагмент и необходимый
локальный контекст источника. До принятия эталона он не использует
`statements.yml`.

## Проверка вопроса

Вопрос принимается, если:

- понятен без знания внутренней структуры корпуса;
- имеет один ожидаемый смысл в границах опорного фрагмента;
- не содержит формулировку ответа или уникальный идентификатор утверждения;
- не требует сведений, которых нет в опорном фрагменте;
- соответствует заявленному типу;
- остаётся полезным для предполагаемого пользователя.

Прямой вопрос проверяет базовую доступность. Перефразированный вопрос проверяет
семантический поиск. Прикладной вопрос проверяет перенос утверждения в рабочую
ситуацию и поэтому требует особенно строгой проверки границ применимости.

## Модельный прогон

Локальная настройка задаёт адаптеры и модели. Контракт адаптера:

```text
<команда адаптера> <модель>
```

Адаптер читает запрос UTF-8 из стандартного ввода, пишет единственный объект
JSON в стандартный вывод и возвращает код 0 при успешном транспортном вызове.
Диагностика пишется в стандартный поток ошибок. При ненулевом коде весь вызов
считается транспортной ошибкой.

Средство запуска передаёт переменную `KC_EVALUATION_ACCESS`:

- `statements` — инспектор видит рабочую копию только файлов `statements.yml`;
- `corpus` — отвечающая модель видит корень корпуса, но не набор проверки,
  настройку или отчёт;
- `closed_book` — модель запускается в новом пустом каталоге;
- `judge` — модель запускается в новом пустом каталоге и получает эталон только
  внутри запроса.

Адаптер обязан ограничить модель текущим рабочим каталогом, запустить её без
скрытого проектного контекста и запретить запись в режиме `statements` либо
`corpus`. Переменная `KC_EVALUATION_READ_ONLY=1` передаётся как обязательный
сигнал этого режима. Адаптер, который не обеспечивает эту границу, не
соответствует контракту и не должен использоваться для измерения.

JSON инспектора:

```json
{
  "representation": "present",
  "statement_ids": ["SOURCE-001"],
  "paths": ["data/source/documents/item/statements.yml"],
  "rationale": "Целевой смысл представлен."
}
```

Для `present` и `partial` нужны существующие пути к `statements.yml` и
существующие в них идентификаторы. Для `absent` оба списка пусты.

JSON отвечающей модели:

```json
{
  "answer": "Ответ пользователю.",
  "abstained": false,
  "evidence": [
    {
      "path": "data/source/documents/item/statements.yml",
      "statement_id": "SOURCE-001",
      "locator": "SOURCE-001"
    }
  ]
}
```

Каждое указанное основание проверяется по файловой системе. Для
`statements.yml` обязателен `statement_id`, наличие которого проверяется в
файле. `locator` для него должен быть пустым или совпадать со `statement_id`.
Для другого Markdown- или TXT-файла `statement_id` должен быть пустым, а
`locator` должен иметь вид `lines:N-M` и попадать в границы файла. Пустой список
допустим, но не засчитывается как указанное основание.

JSON модели-судьи:

```json
{
  "correctness": "pass",
  "groundedness": "pass",
  "target_expressed": true,
  "forbidden_claim_detected": false,
  "rationale": "Ответ сохраняет целевой смысл и ограничение."
}
```

Если `target_expressed` равен `false`, `correctness` должен быть `fail`. Если
`forbidden_claim_detected` равен `true`, и `correctness`, и `groundedness`
должны быть `fail`. Несогласованный объект отклоняется как ошибка модельного
контракта.

Средство запуска меняет рабочий каталог:

- инспектор запускается из временной копии, содержащей только
  `statements.yml`;
- отвечающая модель запускается из корня корпуса;
- ответ без корпуса и модель-судья запускаются во временном пустом каталоге.

Это снижает случайное чтение корпуса в базовом режиме, но не доказывает
отсутствие сведений в параметрах модели.

Перед прогоном локальная настройка вручную подтверждает:

- чтение корпуса выбранными адаптерами;
- передачу опорного фрагмента модели-судье.

Эти флаги останавливают случайный запуск, но не являются технической проверкой
политик источника. Для каждого принятого примера `access_review` отдельно
фиксирует, кто и почему разрешил передачу опорного фрагмента судье. Настройка и
карточка не отменяют `access`, `allowed_use`, `copy_policy` и другие
ограничения источника.

Опорный фрагмент передаётся модели-судье как недоверенные данные. Средство
запуска запрещает выполнять инструкции из него, но текстовая защита не устраняет
риск внедрения инструкций полностью. Для недоверенного источника используй
допустимую изолированную модель и проверяй спорные вердикты человеком.

## Показатели

Основные показатели считаются отдельно:

- `representation` — представлен ли целевой смысл в `statements.yml`;
- `corpus_correctness` — передан ли целевой смысл в ответе через корпус;
- `corpus_groundedness` — соответствует ли ответ опорному фрагменту;
- `evidence_self_reported` — указала ли модель существующее основание;
- `closed_book_correctness` — получен ли тот же смысл без корпуса;
- `corpus_lift` — разница долей успешных ответов через корпус и без корпуса
  только для парных вопросов, где завершились оба режима.

`evidence_self_reported` остаётся проверенным самоотчётом модели, а не полной
трассой поиска. Размер парной выборки и число непарных результатов публикуются
рядом с `corpus_lift`.

Результаты разбиваются по `importance_class` и `question.type`.

Для агента, который самостоятельно открывает файлы, нельзя честно вычислить
`Recall@k` без наблюдаемого ранжированного списка. Если поисковый компонент
возвращает такой список, его адаптер может дополнительно сохранять ранги, а
проект — считать полноту среди первых `k` результатов.

## Классификация отказов

| Наблюдение | Основной кандидат причины |
| --- | --- |
| Инспектор не нашёл смысл в `statements.yml` | Пробел извлечения |
| Смысл представлен, но ответ не содержит его | Проблема поиска или выбора основания |
| Нужное основание указано, но ответ неправильный | Проблема построения ответа |
| Ответ через корпус и без корпуса одинаково успешен | Слабая доказательность примера |
| Судья отклоняет эталон или вопрос | Дефект набора проверки |
| Результат меняется между повторами | Нестабильность модели или поиска |

Классификация указывает ближайшее место исследования, а не автоматически
установленную первопричину.

## Открытая и закрытая выборки

Открытый набор удобен для воспроизводимости, исправления регрессий и обсуждения
критериев. Он уязвим для подгонки и знакомства модели с опубликованными
вопросами.

Закрытый или поздно сформированный набор лучше оценивает обобщение. Его нужно
хранить вне публичного слоя и не включать в инструкции отвечающей модели.

Практичный контур сочетает:

- небольшой открытый набор регрессий;
- закрытую случайную выборку;
- реальные вопросы пользователей после проверки доступа и обезличивания.
