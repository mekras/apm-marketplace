# Анализ моделей для подагентов

Подготовь сравнительный профиль моделей для повторного использования в разных проектах.
Сначала установи характеристики и границы данных, затем формулируй обоснованные выводы.
Не назначай моделям роли до сравнения.
Результат этого навыка — два пользовательских Markdown-файла: цели и анализ.
Настройка проектной политики, подключение новых поставщиков и испытания моделей
не входят в обычный запуск навыка. Для настройки политики используй
`ai-setup-subagents` только по отдельному запросу.

Для целевого уточнения по готовому разбору истории сначала используй
[порядок обновления по истории](references/history-update.md). Он сохраняет
остальной профиль и не запускает заново неизменные этапы исследования.

## 1. Прочитай или сформулируй цели

1. Найди пути в запросе, текущем разговоре или явно указанной пользовательской
   настройке. Если они не заданы, сам предложи два конкретных пути по
   [правилам размещения](references/storage.md): по умолчанию в корне проекта
   или текущей контекстной папки. Проверь стандартные имена в этой папке на
   наличие сохранённых файлов. Не ищи личные файлы по всему диску и не требуй
   от пользователя придумывать имена или вводить полные пути. Предложение путей
   можно объединить с формулировкой целей для одного подтверждения.
2. Если файл существует, прочитай его и покажи пользователю сохранённые
   формулировки. Дождись подтверждения или изменений перед анализом. Подтверждение
   именно этих формулировок в текущем запуске достаточно, повторять вопрос не надо.
   Явно сообщи, что прочитал существующий файл, и процитируй либо точно перескажи
   его цели. Проси подтвердить цели или изменить их, а не «сохранить цели».
   При неизменных целях файл не переписывай. Согласованные пути назови как
   используемые, не включай их в новый запрос подтверждения.
   Не добавляй новые параметры оценки к сохранённым как уже принятые.
   Например, время предложи отдельно, если оно ещё не было согласовано.
3. Если файла нет, используй уже высказанные цели и уточни только пробелы:
   желаемый результат, приоритеты качества и затрат, допустимые исправления.
   Предложи параметры оценки: качество, полные затраты, при необходимости время
   и другие существенные характеристики. Различай измеряемый параметр и цель:
   учёт времени сам по себе не делает скорость приоритетом.
   Покажи итоговую формулировку и получи подтверждение.
4. До первой записи согласуй предложенное размещение и проверь его по
   [правилам размещения](references/storage.md): разные файлы, вне установленных
   навыков, с проверенной защитой от версионирования при наличии VCS.
   Уже явно заданные или согласованные пути повторно не согласовывай.
   Если область анализа ещё не выбрана, предложи нейтральное имя результата. Сохрани подтверждённые цели по
   [шаблону](assets/goals.md). При изменении
   обнови тот же файл, при простом подтверждении не переписывай его.
   Не превращай предпочтения одного пользователя в общие требования навыка.

## 2. Установи область и актуальный каталог

1. Прими выбранные пользователем оснастки и подключения: поставщик, подписка
   или API. Место запуска анализирующего агента не ограничивает область.
   Если область не задана, предложи подключения по несекретным настройкам
   и дождись выбора. Подключение в настройке само по себе не считается выбранным.
   Уже выбранные подключения повторно не согласовывай.
2. До предложения набора моделей получи актуальный каталог именно выбранного
   пользовательского доступа по [правилам каталога](references/catalog.md).
   Чтение каталога не должно превращаться в пробный вызов модели. Перед
   неизвестной командой проверь её назначение по справке или документации.
3. Сверь все доступные модели и поддерживаемые усилия. Старые назначения
   в локальной политике не заменяют каталог. Скрытые, устаревшие и непроверенные
   записи сырого списка не предлагай как доступные альтернативы.
   Если сведений недостаточно, назови конкретный пробел и предложи способ
   получить их без модельных вызовов. Не предлагай утвердить набор сейчас,
   обещая проверить доступность после подтверждения.
4. Не переноси уровни усилия между моделями или оснастками. Различай отсутствие
   настройки усилия и отсутствие сведений о ней. Только в первом случае
   укажи «не задаётся». При неизвестных усилиях сначала уточни их.
   Итоговый анализ содержит только выбранные доступные пары. Роли и список инструментов анализирующей сессии не заменяют каталог
   выбранного доступа. Пробелы охвата сообщи отдельно, не объявляя модель недоступной из-за ошибки сети.

## 3. Определи охват сравнения

Прочитай [правила оценки](references/assessment.md). Единица сравнения —
пара «модель + усилие» в конкретном способе доступа. Для наблюдений
делегирования дополнительно сохраняй связку с родителем по правилам оценки.
Профиль должен позволять выбирать родителя вместе с подагентами.

По умолчанию предложи охватить все доступные модели и поддерживаемые усилия
выбранных подключений по уже доступным сведениям. Покажи состав охвата
и согласуй его, только если пользователь ещё не выбрал охват.
Формулировка «все доступные пары выбранного подключения» уже задаёт полный охват,
даже если каталог ещё не получен. После сверки каталога покажи точный состав
и продолжай без нового подтверждения. Уточнение количества и названий само
по себе не требует согласования. Новый вопрос нужен при противоречии,
неоднозначном подключении или необходимости изменить выбранный охват.
Полный охват не требует испытать каждую пару или найти все возможные публикации.

Не составляй обязательный сокращённый стартовый набор. Сужение допустимо
по решению пользователя или конкретному ограничению бюджета либо объёма работы.
Объясни ограничение, предложенный охват и что откладывается. Само отсутствие
данных не повод исключать пару: оно является результатом анализа.
Большой каталог можно группировать без потери моделей и усилий.

До результатов не называй пары «экономичной», «повседневной», «основной»
или «для сложных задач», даже как предварительных кандидатов. Новизна, название,
цена токена и прежняя политика не задают качество или полные затраты.
Пользовательские наблюдения включи в исходные данные с их ограничениями,
без закрепления ролей или предпочтений в переносимом навыке.

Утверждение охвата не разрешает модельные вызовы.

## 4. Собери и сравни данные

Выполни [исследование и проверку завершённости](references/research.md):
разбери уже предоставленные наблюдения и прежние результаты, найди
опубликованные сравнительные измерения и условия расхода выбранного доступа.
Разделяй источники по предмету, проверяй всех участников найденных сравнений
и сверяй покрытие каждой модели перед завершением по правилам исследования.
Чтение общих описаний моделей не заменяет этот поиск. Отсутствие собственных
измерений не означает отсутствия опубликованных данных.

Отдельно установи состояние истории по правилам оценки. Если для чтения нужно
согласовать область, предложи конкретный ограниченный вариант и запроси выбор.
Пока ответ не получен, продолжай независимое исследование открытых материалов.
При запрете сети или недоступных инструментах используй разрешённые материалы
и обозначь выполненную часть. Не объявляй непроведённый поиск безрезультатным.

Сопоставляй характеристики с подтверждёнными параметрами оценки. Разделяй
данные по задачам и условиям, чтобы не смешивать несопоставимые результаты.
Классы работ описывают условия исследования, а не назначенные моделям роли:
извлечение сведений, классификация, анализ, редактирование, изменение кода,
проверка результатов. Добавляй специфические классы при необходимости.
Не ограничивай переносимый результат задачами текущего проекта.

Любые модельные испытания, включая пробные вызовы и повторное выполнение задач
из истории, требуют отдельного явного разрешения. До запроса разрешения покажи
конкретный вопрос, выбранные модели и усилия, передаваемые данные, число запусков
и ожидаемый расход либо его неизвестность с предлагаемым пределом. Учитывай уже
данное разрешение только в его границах. Запрос «проанализируй», выбор набора
и нехватка данных не разрешают вызовы автоматически.
При недостатке данных сохрани известные характеристики и конкретный
пробел. Не подменяй неизвестные качество, затраты или время предполагаемой ролью. Не останавливай весь анализ только ради повышения уверенности.

## 5. Сохрани результат

1. Заполни [шаблон анализа](assets/analysis.md). Для каждой утверждённой доступной пары
   укажи способ запуска и доступа, характеристики качества и полных затрат,
   время при включении в параметры оценки, условия и границы данных. Различай
   измерения, заявления поставщика, пользовательские наблюдения и выводы.
   Неизвестные значения обозначь явно. Рекомендации необязательны и допустимы
   только после сравнения с указанием поддерживающего результата и его границ.
2. Сохрани дату и условия применимости. Включай только сведения, нужные для
   последующего выбора подагентов. Не добавляй статусы доступности, журнал
   проверок, обязательный перечень источников, номера версий или историю изменений.
   Обоснование можно оформить отдельным отчётом по запросу пользователя.
3. Сохрани результат по согласованному пути. Если его ещё нет, сам предложи
   конкретный путь по [правилам размещения](references/storage.md) и дождись
   подтверждения. Личные файлы внутри проекта допустимы. До записи проверь,
   что они не отслеживаются VCS и исключены из версионирования. Не добавляй их
   в Git и не снимай отслеживание существующих файлов без отдельного решения.
4. При повторном запуске обнови прочитанный прежний результат в том же файле.
   Не переноси прежние выводы как новые наблюдения. Явное сужение набора
   пользователем определяет новый охват файла и не считается пробелом.
   При неполном охвате утверждённого набора не
   затирай прежний полный результат молча: предложи сохранить частичный
   результат отдельно либо согласуй замену. При пустом подтверждённом каталоге
   сообщи о пробеле без создания мнимого анализа и без перезаписи прежнего файла.
5. После записи прочитай оба файла и проверь соответствие подтверждённым целям,
   выбранным подключениям и утверждённым доступным парам. Сообщи пути, краткий
   результат и ограничения проверки. До заявления о завершении примени критерий
   из правил исследования. Сохранение файла само по себе не означает завершения
   анализа. Не заявляй сохранение при ошибке записи.

## Границы

- Не меняй настройки среды, подключения, модели текущего агента или политику
  проекта в рамках анализа. Исключение — точечные локальные исключения VCS
  для согласованных личных файлов по правилам размещения.
- Не читай и не сохраняй ключи, токены и другие секреты для составления отчёта.
- Файлы пользователя хранят текущие цели и сравнительный профиль. История версий,
  общий профиль политики и машинно-читаемый реестр свидетельств не требуются.
- Основной маршрут не требует Python, POSIX или установки программ. При
  отсутствии файловых инструментов подготовь текст и явно сообщи, что он не сохранён.
