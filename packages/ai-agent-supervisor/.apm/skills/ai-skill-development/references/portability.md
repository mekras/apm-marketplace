# Переносимость навыка

Используй эту справку для каждого навыка с поставляемыми скриптами, командами
оболочки или внешними исполняемыми зависимостями.

## Классы маршрутов

- **P0, базовый** — агент получает полезный основной результат по инструкциям и
  возможностям самой задачи. Маршрут не запускает поставляемый скрипт, не
  устанавливает интерпретатор или пакет, не требует сети и POSIX-оболочки.
- **P1, автоматизированный** — необязательное ускорение или детерминированная
  проверка с явно объявленным переносимым интерпретатором либо командой.
- **P2, платформенный** — необязательное действие для явно названной ОС,
  оболочки или оснастки.

Общий навык обязан иметь P0. Исключение допустимо только для задачи, которая по
своей природе невозможна без конкретной платформы. Ограничь `compatibility` и
не называй такой навык переносимым за пределами этой платформы.

## Порядок проектирования

1. Сначала опиши результат P0 и проверку его достаточности.
2. Для каждого кандидата в скрипт укажи P1 или P2, назначение, входы, выходы,
   границы записи и выигрыш относительно P0.
3. Назови интерпретатор, минимально совместимую версию, команды, платформу,
   сеть и пакеты. Поле `compatibility` должно кратко отражать эти ограничения.
4. До запуска проверь зависимости без изменения системы.
5. Если необязательная зависимость отсутствует, продолжи P0. В результате
   различай «выполнено и автоматически проверено», «выполнено без
   автоматической проверки» и «невозможно из-за обязательной зависимости».
6. Не устанавливай и не загружай код без отдельного явного решения пользователя
   или проекта.

## Команды и платформы

В P0 не используй `sh -c`, переменные вида `$VAR` и `${...}`, подстановку
`$(...)`, конвейеры, перенаправления, цепочки `&&`, `/dev/null`, `chmod`,
`mktemp`, запуск только через shebang и жёстко заданный `python3`. Не соединяй
пути вручную разделителем одной ОС.

Такие конструкции допустимы в P2 при явной пометке платформы. В P1 допускается
команда объявленного интерпретатора. Если имя запуска различается между
системами, сначала обнаружь доступный вариант или дай отдельные команды для
заявленных сред. Не помещай синтаксис нескольких оболочек в одну команду.

## Зависимости скриптов

Для Python используй стандартную библиотеку. Сторонний импорт запрещён по
умолчанию. Если специализированный P1 или P2 объективно требует пакет, до
реализации получи решение владельца и зафиксируй:

- имя пакета и совместимую версию
- воспроизводимый способ установки и проверку целостности
- источник, лицензию и необходимость сети
- безопасный отказ при отсутствии пакета
- независимый P0 для общего результата

Не скрывай установку в `pip install`, `uv run`, `npx` или похожей команде
обязательного маршрута. Метаданные зависимостей улучшают воспроизводимость, но
не создают рантайм в системе, где его нет.

## Проверка

Проверь минимум следующие среды и отказы:

- Linux, macOS и заявленный режим Windows
- путь с пробелами и символами вне ASCII
- отсутствие Python и POSIX-оболочки
- несовместимая версия интерпретатора
- отсутствие пакета и запрет сети

Автоматическая проверка нужна для P1 и P2. Для P0 добавь сценарий результата,
который доказывает полезный результат без поставляемого скрипта.

Для каждого публичного Python-скрипта P1 в первом уровне `scripts/` добавь
исполняемый контракт с реалистичной фикстурой. Он обязан запускать ровно
поставляемую команду, а не только импортировать её функции или вызывать
`--help`. Ожидаемый отказ полезен как дополнительная проверка, но каждый скрипт
должен иметь хотя бы один успешный рабочий сценарий. Команды, прямо указанные
в процедуре навыка, сопоставь со сценариями контракта. Если скрипт записывает
состояние, контракт успешно выполняет этот путь и проверяет созданный файл как
внешний формат. Для JSON это означает успешное повторное чтение JSON после
запуска. В коллекции с оснасткой `ai-setup-apm` контракт лежит в
`evals/script-contract-tests.json` и выполняется через
`run-skill-script-contract-tests.py`.

Не сохраняй `__pycache__`, `.pyc` или `.pyo` в защищённом состоянии APM:
исходниках `.apm`, развёрнутых проекциях `.agents`, `.claude`, `.codex`,
поставляемой оснастке и семантических путях `apm.lock.yaml`. Это единая граница:
чистое исходное дерево не помогает, если старый файл блокировки продолжает
разворачивать артефакт.

Для обычного запуска Python передавай `PYTHONDONTWRITEBYTECODE=1`, если защита
должна наследоваться дочерними процессами. Ключ `-B` используй только для одного
подтверждённого процесса. Ни ключ, ни переменная среды не запрещают явную запись
через `py_compile` и `compileall`. Поэтому не запускай эти компиляторы над
защищёнными деревьями. Для синтаксической проверки читай текст исходника и
вызывай `compile(source, filename, "exec")` в памяти либо используй
`validate-python-syntax.py`. Если байткод действительно нужен тесту, направляй
его в отдельный проверенный временный каталог вне проекта и не передавай этот
каталог APM.

В коллекции с `ai-setup-apm` выполняй `validate-python-artifacts.py` до и после
тестов, установки и аудита. Валидатор проверяет существующие защищённые деревья
и файл блокировки. Удаление найденного кэша закрывает только текущее состояние.
После загрязнения `apm.lock.yaml` его нужно пересоздать штатной установкой из
чистого исходного дерева, а затем повторить полный барьер.
