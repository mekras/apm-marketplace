# Проверка срабатывания и качества

Используй эту справку, когда меняются триггеры навыка, процедура работы или
признаки успешного результата.

## Проверки срабатывания

Минимальный набор содержит:

- положительные случаи — разные формулировки реальной задачи, где навык нужен;
- отрицательные случаи — близкие задачи, где навык загружаться не должен;
- пограничные случаи — задачи, где нужен соседний навык или локальное правило.

Не путай проверку срабатывания с оценкой качества:

- срабатывание показывает, что нужный навык действительно выбран;
- качество показывает, что выбранный навык даёт проверяемый результат.

Проверки хранятся в `evals/triggers.json` каталога навыка:

```json
{
  "skill_name": "example-skill",
  "cases": [
    {
      "id": "example-skill-positive-create",
      "prompt": "Создай навык для проверки договоров.",
      "should_trigger": true,
      "rationale": "Нужно создать навык агента."
    }
  ]
}
```

Структуру проверяй командой:

```text
<команда Python 3> tools/validate-trigger-evals.py --require-all
```

Для одного навыка передавай путь к его каталогу:

```text
<команда Python 3> tools/validate-skill-descriptions.py .apm/skills/<name>
<команда Python 3> tools/validate-trigger-evals.py .apm/skills/<name> --require-all
```

## Проверки качества результата

Для реалистичной задачи сформулируй наблюдаемые признаки успеха:

- создан или изменён ожидаемый файл;
- структура соответствует формату навыка;
- `description` покрывает нужные намерения и не захватывает соседние;
- подробности вынесены в подходящие директории;
- выполнены локальные команды проверки;
- отчёт называет остаточный риск.

При анализе качества навыка добавляй отдельный сценарий проверки результата:

- есть ли разница между навыком «до» и «после»;
- какие регрессии появились;
- какой случай проваливается и требует добавления в постоянный набор тестов.

## Контракт проверки применения навыка

Тест результата должен доказывать, что навык не только выбран, но и применён как
рабочая процедура. Для каждого сценария результата фиксируй:

- `evaluation_surface` — какую поверхность проверяет сценарий: маршрутизацию,
  обязательный шаг, ограничение, изменение артефакта, качество результата,
  остановку по правилу или сочетание этих поверхностей;
- `application_evidence` — наблюдаемые признаки применения навыка в ответе,
  артефакте, журнале, diff, трассе выполнения или другом проверяемом следе;
- `oracle` — критерии прохождения и признаки провала, по которым можно
  отличить применение навыка от случайно удачного ответа;
- `negative_control` — что должно провалиться без навыка, без обязательного
  шага, с неверной маршрутизацией или при типичной ошибке. Если такой контроль
  невозможен, явно укажи причину.

Недостаточные проверки не закрывают качество навыка, даже если они полезны как
вспомогательные сигналы:

- проверяется только синтаксис JSON, Markdown, схемы или существование файла;
- проверяется только факт вызова модели, инструмента, скрипта или валидатора;
- проверяется только один внешний признак результата без связи с процедурой
  навыка;
- проверяется только совпадение или отсутствие фрагмента текста;
- проверяется только `should_trigger`, без сценария результата;
- тест мог бы пройти без загрузки навыка или без выполнения его обязательных
  шагов.

Если доступна только такая проверка, называй её вспомогательной и добавляй
постоянный сценарий результата либо фиксируй остаточный риск.

## Контроль качества и модельный прогон

Раздели проверки на две независимые цели.

Детерминированный контроль качества — это валидаторы структуры. Они не вызывают
модель, сеть или внешний инструмент командной строки, поэтому проходят у
стороннего участника и в непрерывной интеграции. Это условие приёмки:

```text
<команда Python 3> tools/validate-skill-descriptions.py .apm/skills/<name>
<команда Python 3> tools/validate-trigger-evals.py .apm/skills/<name> --require-all
<команда Python 3> tools/validate-skill-result-evals.py .apm/skills/<name>
```

Модельный прогон применяет навык к сценариям через модель. Это измерение
качества, а не условие приёмки, поэтому его держат отдельной целью и не вносят в
контроль качества:

```text
<команда Python 3> tools/run-skill-evals.py .apm/skills/<name>
```

Не помещай модельный прогон в контроль качества. Если модельный шаг попадает в
команду, которую обязан выполнять сторонний участник, проверка перестаёт быть
переносимой.

## Контракт адаптера модели

Средство запуска модельного прогона не привязано к конкретному инструменту
командной строки или модели. Модель вызывается через адаптер по переносимому
контракту:

- вызов `<команда адаптера> <модель>`;
- запрос читается со стандартного ввода;
- текст ответа модели пишется в стандартный вывод;
- код выхода 0 — успех, любой другой — транспортная ошибка вызова.

Средство запуска само вкладывает требование вернуть JSON в текст запроса и
разбирает JSON из ответа. Адаптеры (имя адаптера → команда), список моделей и
модель-судью задаёт локальный файл настроек `evals.local.yml` вне Git. Средство
запуска создаёт его из образца при первом запуске. Модели и судью указывают в
формате `адаптер:модель`, поэтому один прогон может сочетать модели от разных
адаптеров. Имена моделей в навыках и манифесте не фиксируй. Каждая запись
проверяется по одинаковым критериям, поэтому результаты сопоставимы.

Транспортную ошибку модели не маскируй повтором до прохождения: повторяй только
сам сбойный вызов, а несовпадение ответа с критериями проверки считай провалом
сценария.

## Быстрый и полный циклы

Скорость проверок оптимизируй выбором минимальной области запуска, но не
сокращением критериев качества.

Если нужно повторить один модельный сценарий, запускай его по идентификатору:

```text
<команда Python 3> tools/run-skill-evals.py .apm/skills/<name> --case-id <id>
```

Через APM контроль качества и модельный прогон вызываются разными командами, а
область задаётся переменными среды:

```bash
APM_EVAL_PATH=.apm/skills/<name> apm run tests
APM_EVAL_PATH=.apm/skills/<name> apm run evals
APM_EVAL_PATH=.apm/skills/<name> APM_EVAL_CASE_ID=<id> apm run evals
```

Расширяй запуск до всей коллекции, если:

- изменён `description` и есть риск влияния на соседние навыки;
- изменены общие валидаторы, средство запуска или `apm.yml`;
- изменены несколько навыков;
- результат готовится к публикации или выпуску пакета;
- узкий запуск выявил сбой, причина которого может быть общей.

Выборочный запуск должен быть отражён в отчёте: укажи путь или `id`, что именно
он покрывает, какие проверки не запускались и почему этого достаточно для
текущего шага. Перед публикацией не заменяй полный прогон одним выбранным
сценарием.

## Виды тестов навыка

При создании, изменении или сопровождении навыка сначала проверь, есть ли у
него постоянные тесты и покрывают ли они текущий риск. Если тестов нет, их не
хватает или текущая правка меняет поведение навыка, добавь или обнови один или
несколько видов тестов. Если постоянный тест сейчас нельзя создать, в отчёте
явно укажи, какой тест нужен, почему он не добавлен и какой риск остаётся.

Не заменяй создание доступного теста предложением добавить его позже: предложение
допустимо только при недоступном контексте, отсутствии проверочной
инфраструктуры или явном ограничении области задачи.

- Тесты срабатывания: положительные, отрицательные и пограничные запросы в
  `evals/triggers.json`.
- Тесты результата: сценарий с входным запросом, ожидаемыми артефактами,
  признаками применения навыка, oracle, негативным контролем и остаточными
  рисками.
- Регрессионные тесты: случай из реального сбоя или спорного решения, который
  должен продолжать проходить после изменения навыка.
- Негативные тесты ограничений: сценарии, где навык обязан остановиться,
  передать решение человеку или выбрать соседний навык.
- Тесты материалов навыка: проверка существования ссылок на `references/`,
  `assets/`, `scripts/`, `templates/` и соответствия этих материалов
  навигации из `SKILL.md`.
- Тесты скриптов: публичный Python-скрипт P1 первого уровня в `scripts/`
  запускается в копии реалистичной фикстуры через свою поставляемую команду.
  Проверка фиксирует внешний результат: файл, формат, стандартный вывод или
  код отказа. Проверка `--help`, импорт отдельных функций или синтаксис Python
  полезны как вспомогательные, но не заменяют этот сценарий. Скрипт, который
  сохраняет JSON, должен пройти повторное чтение созданного JSON-файла.
  Необязательные входы и зависящие от них ветви покрываются по разделу об
  исполнимом контракте ниже.
- Тесты переносимости: полезный P0 без поставляемого скрипта, предварительная
  проверка P1 и P2, отсутствие рантайма или пакета, путь с пробелами и символами
  вне ASCII, заявленные операционные системы.
- Тесты защищённого состояния: исходники, развёрнутые проекции, оснастка и
  семантические пути файла блокировки не содержат `__pycache__`, `.pyc` и
  `.pyo`. Проверка выполняется до и после тестов. Отдельные регрессии
  подтверждают, что `py_compile` пишет байткод с `-B` и
  `PYTHONDONTWRITEBYTECODE=1`, поэтому синтаксис проверяется в памяти.
- Интеграционные тесты проекта: сценарий совместного применения навыка с
  `AGENTS.md`, соседними навыками и локальными правилами целевого проекта.

Минимум для нового навыка: тесты срабатывания и один тест результата. Минимум
для изменения `description`: обновлённые положительные, отрицательные и
пограничные случаи, плюс проверка бюджета `description`, если она есть в
коллекции. Минимум для изменения процедуры или ограничений: один тест
результата и один негативный тест ограничения.

## Исполнимый контракт Python-скрипта P1

Если коллекция использует оснастку `ai-setup-apm`, положи в каталог навыка
`evals/script-contract-tests.json`. Для каждого Python-файла первого уровня в
`scripts/` нужен хотя бы один успешный рабочий сценарий. Ожидаемые отказы могут
только дополнять его. Формат не зависит от оболочки:

```json
{
  "version": 2,
  "operations": [
    {
      "id": "create-state",
      "script": "scripts/create_state.py",
      "command_prefix": ["--output"],
      "inputs": ["project-impact.json"]
    }
  ],
  "cases": [
    {
      "id": "create-state",
      "script": "scripts/create_state.py",
      "fixture": "evals/script-fixtures/basic-project",
      "covers": ["create-state"],
      "prepare": [["git", "init", "--quiet", "{fixture}"]],
      "command": ["{python}", "{script}", "--output", "{fixture}/state.json"],
      "expect": {
        "files": [{"path": "state.json", "json": true}]
      }
    }
  ]
}
```

`{python}`, `{script}` и `{fixture}` заменяет запускатель. Фикстура копируется
во временный каталог, поэтому сценарий не меняет исходные данные. Необязательный
массив `prepare` выполняет команды без оболочки только в этой копии до основной
команды. `expect` должен содержать хотя бы один наблюдаемый результат: фрагмент
`stdout` или `stderr`, созданный файл, проверку JSON либо ожидаемый текст файла.
В `command` обязательны `{python}` и `{script}`. Ожидаемый код возврата `0`
означает успешный рабочий сценарий. В `operations` перечисли обязательные
операции: идентификатор, скрипт и `command_prefix` после `{script}`. Успешный
случай указывает покрываемые операции в `covers`. Запускатель принимает его
только при совпадении скрипта и префикса команды. Для каждой объявленной
операции нужен такой сценарий. Сопоставь с `operations` команды, указанные в
процедуре навыка, чтобы успешная проверка вспомогательной ветви не скрыла отказ
основного пути.

Успешный сценарий на минимальной фикстуре не доказывает работоспособность
ветвей, которые включаются необязательными входами. Прочитай скрипт и выпиши
файлы и настройки, которые он читает по условию и которые меняют сохраняемое
состояние или результат. Объяви такие файлы в `operations[].inputs`:
запускатель требует, чтобы каждый объявленный вход присутствовал хотя бы в
одной фикстуре успешного сценария этой операции. Для входа, который меняет
сохраняемый JSON, проверь результат его ветви в `expect` этого сценария, а не
только факт успешного завершения. Поле `inputs` обязательно для каждой
операции. Пустой массив означает, что код операции проверен и условных входов
не найдено. Во время успешного сценария запускатель наблюдает проверки
действительно отсутствующих путей внутри фикстуры. Отрицательный результат
`is_file()` для существующего каталога и `is_dir()` для существующего файла не
считается отсутствием. Запускатель исключает пути, созданные или заменённые
самой операцией, и отклоняет каждый оставшийся путь, которого нет в `inputs`
покрываемой операции. Это наблюдение не заменяет чтение кода для настроек и
недостигнутых ветвей. Отсутствующее поле не означает пустой список и считается
незавершённой проверкой. Поставляемая оснастка выполняет контракты командой:

```text
<команда Python 3> tools/run-skill-script-contract-tests.py [путь-к-навыку]
```

## Аудит покрытия перед завершением

Перед завершением изменения навыка проверь:

- какие тесты уже были у сопровождаемого навыка;
- какие файлы навыка изменены: `SKILL.md`, `agents/openai.yaml`, `references/`,
  `assets/`, `scripts/`, `evals/`;
- какой риск изменения появился или изменился;
- какой класс переносимости имеет основной маршрут и каждый скрипт;
- какие постоянные тесты добавлены или обновлены под этот риск;
- какие проверки запущены и что они подтвердили.

Если изменение затрагивает только текст справки, всё равно проверь, не меняет ли
оно процедуру, ограничения, критерии результата или маршрутизацию. Если меняет,
постоянные тесты нужны так же, как при изменении `SKILL.md`.

## Когда нужны дополнительные проверки

- изменено `description`;
- изменён `SKILL.md`, `agents/openai.yaml`, процедура, ограничения, критерии
  результата или справка, влияющая на поведение агента;
- добавлен новый соседний навык;
- реальная задача показала неверное срабатывание;
- навык стал длиннее или получил новые справки;
- добавлен скрипт, который может зависеть от окружения;
- проектный `AGENTS.md` изменил правила работы с навыками.
- пользователь просит создать, проверить или сопровождать тесты навыка.

## Ловушки

- Один удачный пример не доказывает качество маршрутизации.
- Проверка, которая проходит без навыка, не доказывает пользу навыка.
- Модельный запуск сам по себе не доказывает применение навыка.
- Косвенный сигнал ответа не заменяет проверку поверхности применения навыка.
- Нельзя подгонять `description` только под текущий набор примеров.
- Модель-судья полезна только вместе с фактами, файлами, выводами команд или
  другим проверяемым артефактом.
