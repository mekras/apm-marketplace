# Известные ограничения версий APM CLI

Эту справку читай перед выбором цели, диагностикой сбоя установки или
обновления, а также перед любым обновлением CLI: `apm self-update`, ручной
установкой конкретной версии или советом человеку об этом.

## Зачем нужна эта справка

Ошибка `apm` не всегда означает дефект проекта или манифеста: часть ошибок —
это ограничение или регрессия конкретной версии самого CLI. Без записанного
прецедента такую ошибку легко принять за проблему проекта и лечить правкой
`apm.yml`, зависимостей или файла блокировки — это не решает причину и может
испортить манифест. Эта справка хранит только эмпирически подтверждённые,
привязанные к версии находки, чтобы следующий навык или сессия не проходили тот
же путь диагностики заново.

## Как использовать запись

Каждая запись описывает симптом, диапазон затронутых версий и подтверждённый
или вероятный обход. Запись не доказывает, что проблема сохраняется в более
новой версии: перед тем как опереться на запись, проверь установленную версию
`apm --version` и, если запись не отмечена как подтверждённая для этой версии,
перепроверь поведение самостоятельно, а не полагайся на устаревшую находку
молча.

## Как добавлять запись

Добавляй запись только по прямому воспроизведённому свидетельству: точный текст
ошибки или наблюдаемое поведение, версия CLI, минимальные шаги воспроизведения.
Не записывай предположения, слухи и не подтверждённые прогоном формулировки.

Не переноси в запись путь, имя, домен, репозиторий или другие данные
конкретного проекта-разработчика или заказчика. Описывай класс условий
(например, «приватный git-хост с переписыванием URL в `insteadOf`»), а не
конкретный хост. Ссылку на внешний источник (тред issue, PR апстрима) оставляй,
если он сам по себе публичный и общий, а не привязан к приватному проекту.

Формат записи:

```text
### <короткое название проблемы>

- Затронутые версии: ...
- Симптом: точный текст ошибки или поведения.
- Причина: если известна.
- Обход: подтверждённое или вероятное решение.
- Апстрим: ссылка на публичный трекер, если есть.
- Источник находки: где и когда воспроизведено (без данных конкретного
  проекта).
```

## Записи

### Цель `hermes` не поддержана в контуре установки и выпуска на 0.29.0 — исправлено на 0.29.1

- Затронутые версии: подтверждено сломанным на 0.29.0 (сборка `5ac6733`);
  подтверждено рабочим на 0.29.1 (сборка `1b3d80a`) — `apm targets`, `apm lock`,
  `apm compile --dry-run`, `apm install --dry-run` и `apm pack` пройдены без
  ошибок про `hermes`, а `apm pack` реально собрал артефакт. Добавление и
  откат цели на 0.29.1 не оставили diff в `apm.lock.yaml`, и `apm audit --ci`
  дал идентичный результат с целью и без неё (242 файла дрейфа, 2 из 9
  проверок — то же самое, что и на чистом `apm.yml`, то есть не связано с
  `hermes`).
- Симптом на 0.29.0: `hermes`, добавленный в `target:`/`targets:` манифеста, принимается
  `apm compile` и показывается флагом `apm experimental list` как включённый
  (`hermes: enabled`), но ломает контур установки и выпуска:
  - `apm targets` не показывает `hermes` вовсе — ни активной, ни неактивной
    целью;
  - `apm lock` печатает `[x] Unknown target 'hermes'`, но завершается кодом 0 и
    сообщает «Lockfile written» — ошибка не останавливает выполнение и не
    видна по коду возврата. Хуже того, файл блокировки при этом действительно
    перезаписывается и теряет данные: в наблюдавшемся прогоне из записи одной
    транзитивной зависимости пропали `deployed_files` и
    `deployed_file_hashes` целиком. После любого прогона `apm lock` с
    неизвестной целью в манифесте обязательно сверь `git diff apm.lock.yaml`
    перед тем, как считать результат безопасным, и не полагайся на отсутствие
    сообщения об ошибке;
  - `apm pack` завершается чисто с ошибкой `Unknown target 'hermes'` и кодом
    выхода 2, без создания артефакта — это единственная из проверенных команд,
    которая отказывает предсказуемо.

  На 0.29.0 в этом же проекте `apm install --dry-run` показывал план удаления
  сотен уже развёрнутых файлов независимо от того, добавлена ли `hermes` в
  манифест — на 0.29.1 отдельно перепроверено, что этот план не зависит от
  цели `hermes` (виден и без неё), поэтому не считай его следствием этой
  записи; это отдельное наблюдение по `apm install --dry-run` в проекте
  такого устройства (публикуемый пакет, который сам себя устанавливает).
- Причина: список допустимых целей для `lock`/`install`/`pack` на 0.29.0 не
  совпадал со списком, который принимает `compile -t`, и с реестром
  экспериментальных флагов.
- Обход: на затронутой версии не добавлять `hermes` в `target:`/`targets:`
  манифеста. Перед добавлением цели на любой версии проверяй именно
  `apm pack` (или `apm lock`) в песочнице, а не только `apm compile --dry-run`:
  на 0.29.0 он ошибочно выглядел рабочим, хотя `lock`/`pack` уже были сломаны.
- Апстрим: в примечаниях к выпуску проекта `apm` указано, что `hermes` стал
  стабильной явно указываемой целью начиная с версии 0.29.1 — это совпадает с
  прогоном.
- Источник находки: собственная проверка этой коллекции, песочница с
  временной правкой `apm.yml` и откатом после каждой проверки (0.29.0 и
  0.29.1).

### Приватный git-хост с `insteadOf`-переписыванием URL ломает загрузку зависимостей с 0.30.0

- Затронутые версии: подтверждено на 0.30.0; предыдущая версия 0.29.0 не
  затронута.
- Симптом: `apm update` (и загрузка зависимости при обычной установке) для
  пакета с приватного git-хоста завершается ошибкой вида «Unable to verify Git
  URL rewrite safety (Git URL-match probe failed)» с кодом выхода 128. Условие
  воспроизведения — в `~/.gitconfig` задано правило вида
  `url.<ssh-адрес>.insteadOf https://<приватный-хост>/`, переписывающее HTTPS-URL
  на SSH-адрес для этого хоста.
- Причина: проверка безопасности переписывания URL в CLI выполняет пробу
  HTTP-заголовка авторизации против уже переписанного не-HTTP(S) адреса и
  закрывается отказом вместо пропуска неприменимой проверки.
- Обход: понижение версии CLI до 0.29.0 решает проблему. `apm self-update`
  обновляет только до последней версии и вернёт 0.30.0 снова — если нужна
  версия 0.29.0, устанавливать её нужно вручную (например, заменить бинарник и
  каталог `_internal` копией версии 0.29.0), не полагаясь на
  `apm self-update`, пока апстримное исправление не выпущено.
- Апстрим: issue `microsoft/apm#2898` («insteadOf rewrite matching the fetched
  URL blocks private installs since 0.30.0»), исправление в PR
  `microsoft/apm#2906` — на момент записи (2026-09-14) PR открыт, не влит.
- Источник находки: рабочая сессия с проектом-потребителем, имеющим прямую
  зависимость с приватного git-хоста и настроенным правилом `insteadOf`,
  2026-09-10 — 2026-09-11.
