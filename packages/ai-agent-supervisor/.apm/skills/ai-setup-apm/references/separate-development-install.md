# Раздельная установка продукта и средств разработки

Используй этот вариант для смешанного проекта, если одна установка не позволяет
однозначно разделить собственные навыки и устанавливаемые зависимости.
Например, проект разрабатывает навык редактирования текста, а средства
разработки транзитивно приносят выпущенную версию навыка с тем же именем.
Самоприменение означает, что проект использует разрабатываемые навыки
для работы над ними же.

Основной вариант — один `apm.yml` с `dependencies.apm` для продуктовых
зависимостей и `devDependencies.apm` для средств разработки.
Различие секций управляет составом пакета, но само по себе не задаёт
разные каталоги развёртывания и приоритет одноимённых навыков.
Если конфликта нет, второй набор состояния не нужен.

## Устройство варианта

Продукт и средства разработки получают отдельные корни установки.
В каждом корне находятся собственные `apm.yml`, сгенерированный
`apm.lock.yaml`, зависимости и проекции. Пример размещения:

```text
project/
  apm.yml                       # публикуемый продукт
  .apm/skills/text-editor/       # собственный исходник
  development/
    apm.yml                     # зависимости средств разработки
    apm.lock.yaml               # состояние их установки
    apm_modules/
    .agents/skills/              # их проекции для выбранной среды
```

Это пример организации, а не готовый шаблон для всех проектов. В корне продукта
файл блокировки появляется, если там выполняется установка. Каталог
`development/` и его содержимое должны быть исключены из публикуемого состава
продукта. Для каждого корня действуют обычные правила APM, политики VCS
и защиты состояния Python. Файлы блокировки создаёт APM, их не правят вручную.
Пример использует стандартное имя `apm.yml` в разных каталогах и не предполагает,
что CLI принимает произвольное имя манифеста.

До настройки определи:

- какие исходники принадлежат продукту, а какие файлы создаёт каждая установка,
- какой источник каждого одноимённого навыка должен читать агент,
- как выбранная среда обнаруживает навыки и из какого рабочего каталога,
- нужны ли ссылки между каталогами и кто управляет каждой ссылкой.

Разные манифесты ещё не решают конфликт в общем каталоге обнаружения.
Не объединяй две проекции простым копированием или выбором последнего
установленного файла. Если среде нужен общий каталог, сначала задай явное
отображение имён на источники и способ его восстановления после обновления.
Не перезаписывай собственные навыки и файлы неизвестного владельца.
При неразрешённом конфликте останови зависящую запись и передай выбор человеку.
Подключение агента к нужным каталогам ведётся по
[границе клиентской настройки](../SKILL.md#обязательный-порядок).

## Обновление и проверка

1. Сначала установи границы поручения: требуется описание варианта, испытание
   кандидата или изменение рабочего окружения. Применяй
   [выбор проверяемого состояния](apm-collection-settings.md#выбор-проверяемого-состояния).
   Описание варианта само по себе не разрешает перенос существующей установки.
2. Перед разрешённым обновлением сохрани проверяемый снимок собственных навыков,
   обоих состояний установки и используемых ссылок: состав, содержимое,
   назначения и владельцев. Отдели ожидаемые изменения от сохраняемых.
3. Обновляй средства разработки из их корня по принятому в проекте порядку APM.
   Состав и версии продукта изменяй только по отдельному основанию. Если проект
   использует установщик для подключения навыков, проверь его область записи
   до запуска. Эта справка не поставляет универсальный установщик.
4. Проверь аудит каждого изменённого состояния и повтори обновление с теми же
   входами. Проверь сохранность собственных исходников и выбранных проекций.
   Для каждой используемой ссылки проверь существование назначения, ожидаемого
   владельца и доступность всех нужных справок и скриптов. При отсутствии ссылок
   проверь непосредственные пути обнаружения. Сопоставь результат со снимком.
5. Независимо испытай публикуемый кандидат в отдельном проекте-потребителе
   без зависимостей разработки: установка, аудит, повторная установка и
   работоспособность относительных ссылок. Наличие файла ещё не подтверждает,
   что среда обнаруживает нужную версию навыка. Подтверди обнаружение средствами
   выбранной среды и проверь сохранность рабочего окружения после испытания.
6. Раздельно сообщи результат проверки кандидата, обновления оснастки,
   сохранности собственных навыков и обнаружения. Невыполненную проверку назови
   прямо. Успешный аудит одной установки не подтверждает состояние другой.

Польза варианта — явное владение файлами и независимое обновление оснастки.
Цена — два состояния установки и сопровождение путей подключения.
Выбирай его, когда эта цена оправданна конкретным конфликтом. Проверки
самоприменения из основной справки сохраняются, раздельная установка
не служит способом скрыть дрейф или ослабить аудит.
