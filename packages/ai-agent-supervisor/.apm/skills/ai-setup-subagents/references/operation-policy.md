# Рабочая политика настройки подагентов

Используй эту справку для деталей, которые не должны раздувать `SKILL.md`.

## Работа с пользователем

Найди цели и получи ответ пользователя по первому разделу `SKILL.md`.
После ответа используй уже прочитанный контекст и изучи остальные материалы: навыки,
шаблоны, команды, документацию процесса и сведения о моделях.
Не проси пользователя заполнять матрицы и контракты вручную, если их можно
вывести из проекта и запроса.

Модели — обязательная входная информация, но не ручная классификация для
человека. Сначала сам попробуй получить список доступных моделей из среды. Если
это не удалось, вопрос должен быть простым: «Пришлите список доступных моделей,
например строками или через запятую. Я сам предложу, какую использовать для
обычной работы, узкого поиска, анализа и проверки».

Схему использования моделей выводи из карты задач по основному порядку
`SKILL.md`. Представь её человеку через ожидаемые результаты и полномочия.
Не ограничивай предложение набором ролей из прежней конфигурации или примера.

Не требуй от пользователя объяснять цену, классифицировать модели или выбирать
внутренние назначения. Если данных о цене нет, пометь вывод как эвристику по
названию и возможностям, а не как проверенный прайсинг.

### Когда проверять политику

При корневой настройке проекта сначала прочитай проектный локальный слой и
определи состояние политики. Полную проверку запускай, если выполнено хотя бы
одно условие:

- пользователь явно попросил проверить политику;
- нет настроенной политики и нет состояния `creation_declined`;
- состояние — `configured`, а с `last_checked_at` прошло не меньше
  `interval_days`.
- средства подагентов активной оснастки отсутствуют или разошлись с источником
  установленного навыка.

При отсутствующем `interval_days` предложи настроить срок; исходное предложение
— 30 дней. Нулевое или отрицательное значение, отсутствующую, нечитаемую либо
будущую дату считай ошибкой состояния и основанием для проверки. Если политика
свежая, назови следующую дату проверки и не запускай полный аудит.

До вывода о свежести проверь средства активной оснастки командой
`check-subagent-tools-drift.py` из установленного навыка. Выбери профиль по
активной оснастке и передай корень целевого проекта. Дрейф — это состояние
`repair`, а не доказательство недоступности модели и не повод подменять
адаптер другим файлом. После подтверждения пользователем восстановления запусти
соответствующий `install-*-tools` из того же навыка, затем повтори проверку
дрейфа. Только совпавшая рабочая копия может вернуть политику в состояние,
готовое к технической проверке моделей и классов исполнения. Не редактируй
файлы в `tools/` вручную.

Состояние `creation_declined` означает осознанный отказ пользователя и не
считается отсутствующей политикой. Оно не блокирует прямой запрос на проверку
или новое решение пользователя создать политику. Срок повторной проверки к
отказу не применяется: не придумывай для него следующую дату.

Используй в `subagents.local.toml` машинно читаемый блок:

```toml
[policy_review]
state = "configured" # либо "creation_declined"
interval_days = 30
last_checked_at = "2026-01-01"
```

Дату обновляй только после завершённой проверки, а не после попытки, которая
закончилась блокером. Проверка без записи возвращает предлагаемую дату в отчёте;
её сохранение остаётся отдельным подтверждаемым изменением. Если политика живёт
в пользовательском слое оснастки, этот блок всё равно остаётся проектным
состоянием и может храниться в исключённом из Git `subagents.local.toml`.

## Режим `policy`

Используй этот режим, если пользователь просит только черновик, сравнение,
оценку схемы, проверку рисков или явно запрещает правки.

Результат режима:

- цель оптимизации и нецели;
- классы задач и уровни моделей;
- контракты делегирования;
- правила эскалации;
- проверки качества;
- бюджетные ограничения;
- открытые решения и данные, которые нужно получить до внедрения.

Если пользователь просит перенести общую часть настройки в глобальную
конфигурацию, сначала покажи черновик переноса прямо в ответе: что переносится
глобально, что остаётся проектным переопределением, какие файлы будут изменены
после согласования и как будет проверен фактический запуск.

## Режим `implementation`

Короткие команды вроде «настрой подагентов», «настрой экономное использование
подагентов» и «настрой подагентов для этого проекта» означают `implementation`:
после уточнения целей коротко сформулировать политику маршрутизации и зафиксировать
рабочую конфигурацию в поддерживаемом слое проекта.

Не меняй файлы только если пользователь явно просит один черновик, сравнение
вариантов или проверку без внедрения. В задаче внедрения всё равно сначала
кратко перечисли состав политики в ответе, а затем укажи, где она
зафиксирована.

Если режим `implementation` требует конкретных моделей, а список моделей не
удалось получить автоматически и пользователь его ещё не дал, финальная
самопроверка обязательна:

- есть ли явный статус `ожидает список моделей`;
- нет ли требования классифицировать модели по назначениям;
- есть ли прямой вопрос к человеку о простом списке доступных моделей;
- является ли этот вопрос последним содержательным блоком ответа.

## Конфигурация Codex

Для Codex не считай настройку подагентов завершённой, если результат ограничен
`AGENTS.md`: нужен реальный конфигурационный слой, закреплённые модели и
проверяемый запуск.

### Подключение рабочей политики

Пользовательская конфигурация агентов выбирает параметры дочернего сеанса, но
не заставляет обычного родителя выделить подзадачу и запустить его. Добавь в
реально загружаемую инструкцию оснастки точный фрагмент
`assets/worker-policy-entrypoint.md` через профильный навык сопровождения
инструкций. Это явная инструкция Codex рассмотреть подагента до передаваемой
работы и не противоречит тому, что оснастка сама не порождает подагентов.

Не копируй туда таблицу маршрутов. Единый источник —
`[policy_runtime]` в `subagents.local.toml`:

```toml
[policy_runtime]
schema_version = 2
launcher = "tools/run-execution-class"
target = "codex"
direct_execution = ["микрозадача"]
direct_execution_scope = "whole_parent_task"
subtask_routing = "match_each_bounded_subtask"
parent_comparison = "actual_current_session"
unknown_parent_parameters = "comparison_unresolved"
parent_change = "invalidate_comparison"
assignment_basis = "historical_only"
unavailable_route = "необязательную работу выполняет родитель"
execution_failure = "результат не использовать; применить unavailable_route; повторять только после изменения среды или маршрута"
unconfirmed_model = "результат можно принять только по result_acceptance, если задача не требует подтверждённой модели; иначе применить unavailable_route без повтора того же запуска"
result_acceptance = "родитель принимает результат по заданным критериям"

[[policy_runtime.routes]]
when = "узкий поиск по нескольким файлам"
execution_class = "cheap_readonly_research"
```

Родитель сначала отделяет полную родительскую задачу от потенциально
делегируемых действий. Значения `direct_execution` применяются к полной
родительской задаче, а каждая выделенная подзадача отдельно сопоставляется с
`policy_runtime.routes`. Поэтому прямой маршрут родителя не отменяет
ограниченный read-only анализ, если он имеет собственные входы, запреты и
приёмку. Запрет записи, утверждения решения и расширения области сохраняется
для дочернего класса независимо от маршрута родителя. Родитель не повторяет
исследование, которое поручает подагенту. Если сама родительская задача попала
в `direct_execution`, её не делегируют целиком. Отдельную подзадачу нельзя
считать покрытой этим условием только из-за его совпадения с условием
родительской задачи: для неё нужен собственный маршрут. При недоступном
маршруте применяется `unavailable_route`.

Перед сравнением маршрута родитель читает фактические параметры текущей сессии
из метаданных оснастки. `policy_design` и сохранённые назначения относятся к
историческому основанию выбора и не подставляются вместо текущих параметров.
При обновлении старой записи поля `parent_model`, `parent_effort` и
`parent_evidence` переименуйте в поля исторического основания с наблюдаемой
датой или явно сохранённой неизвестностью. Не оставляйте их в форме, которая
может выглядеть как текущие параметры исполнения.
Неизвестные параметры оставляют сравнение нерешённым, но сами по себе не
запрещают независимый ограниченный read-only анализ, если его необходимость и
границы не зависят от неизвестного значения. После смены модели или усилия
прежнее сравнение инвалидируется. Совпадение моделей само по себе не является
ни достаточным основанием передачи, ни безусловным запретом: решение требует
предметной пользы для выделенной подзадачи, проверки полномочий и приёмки.

При отказе дочернего процесса применяется `execution_failure`, а при успешном
процессе без подтверждённой модели — `unconfirmed_model`. Результат подагента
не становится результатом задачи до проверки, названной в `result_acceptance`.
Для совпавшего маршрута он вызывает `<launcher> <execution_class> --target
<target>`, передавая запрос через стандартный ввод, а каждый разрешённый файл
отдельным `--input`. Политика не допускает подменить этот вызов неименованным
встроенным ожиданием. Родитель ждёт терминальный код, читает созданную запись
запуска и только затем применяет `execution_failure`, `unconfirmed_model` либо
`result_acceptance`. Пока терминального кода и записи нет, прямой ответ не
выдаётся. После проверки он добавляет в ту же запись `acceptance` и
`quality_assessment`: статус, применённые критерии, проверенные материалы и
границу проверки. Наличие этих полей остаётся записью родителя, а не заменой
содержательной оценки проверяющего.

### Миграция существующей установки

Repair старой установки начинается с чтения `[policy_runtime]`, входного
фрагмента и локальных назначений. Для `schema_version = 1` замени значение на
2 и добавь недостающие поля семантической схемы из образца. Значения
`launcher`, `target`, `direct_execution`, маршрутов, ограничений записи и
обработки сбоев сохраняются; миграция не выбирает новые модели и не меняет
разрешения дочерних классов. В `policy_design.tasks` старые поля `parent_model`,
`parent_effort` и `parent_evidence` переносятся в `parent_basis_model`,
`parent_basis_effort` и `parent_basis_evidence`, рядом фиксируются
`parent_basis = "historical_setup_observation"` и
`parent_basis_observed_at = "unknown"`, если дата неизвестна.

Маркированный блок рабочей политики в `AGENTS.md` или соседней точке входа
заменяется текущим файлом `assets/worker-policy-entrypoint.md` ровно один раз.
Текст до и после блока сохраняется. Отсутствующий блок добавляется один раз
через навык сопровождения инструкций, а актуальный блок оставляется без
изменений. После repair проверь TOML, сохранённые локальные значения,
единственность блока и повторное применение: второй repair должен быть
нулевым по содержательным изменениям.

Проверяй статусы отдельно:

| Состояние | Свидетельство | Чего не доказывает |
| --- | --- | --- |
| Конфигурация сохранена | Разбирается `subagents.local.toml` | Загрузку инструкций |
| Точка входа ссылается на политику | Фрагмент найден в указанном файле инструкции | Фактическую загрузку файла рабочей сессией |
| Загрузка и поведение рабочей сессии наблюдались | Новая сессия выполнила обычную задачу, а журнал и артефакты показывают выбор маршрута | Качество результата или экономию |
| Запись запуска проверена | Файл записи и указанный в нём файл результата доступны. Код процесса, модель и приёмка показаны раздельно | Содержательную пригодность результата |
| Родительская приёмка записана | В записи есть `acceptance.status = "accepted"` | Качество без отдельно проверяемых критериев и материалов |
| Оценка качества записана | Есть `quality_assessment` с критериями, материалами и результатом проверки | Независимость проверки или экономию |
| Фактическая модель подтверждена | Проверяемая ссылка на событие исполнения и совпадение с назначением | Назначение из `--model` или самоотчёт |
| Измерение полной стоимости записано | Сопоставимые маршруты содержат постановку, контекст, исполнение, приёмку и исправления | Доказанную экономию, пока измерение не рассмотрено владельцем |

`assess-subagent-policy-connection.py` проверяет только сохранённые файлы и
ссылки внутри записи. Его `instruction_entrypoints = referenced` не означает
загрузку инструкции, а `working_sessions = not_observed` намеренно не меняется
без отдельного сквозного испытания. Если `returncode` дочернего процесса равен
нулю, это только завершение процесса. `result = available` означает, что файл
по `result_path` существует. `acceptance_record = accepted_recorded` — запись
о приёмке, а не её содержательная проверка. `quality = assessment_recorded` и
`economy = measurement_recorded` означают наличие материалов, но не вывод
скрипта об их истинности. `model_status = confirmed` вместе с
`model_matches = true` подтверждает модель.

Экономия требует отдельного содержательного рассмотрения сопоставимого
измерения полного маршрута, включая постановку, контекст, приёмку и исправления.
Статические и контрактные проверки не подтверждают поведение агента, качество
или экономию.

`run-execution-class` возвращает код 2, если дочерний процесс завершился
неуспешно, и код 3, если процесс завершился успешно, но фактическая модель не
подтверждена или не совпала. Во втором случае родитель читает
`unconfirmed_model`: он либо принимает содержимое по `result_acceptance` только
для задачи, не требующей подтверждённой модели, либо переходит по указанному
маршруту или останавливается. При коде 2 содержимое не используется, действует
`execution_failure`. Оба исхода запрещают повтор того же запуска без изменения
среды либо маршрута.

Основной вариант для повторяемой схемы на одной машине — пользовательский слой
Codex: `$CODEX_HOME`, пользовательская конфигурация, профили и поддерживаемое
место для глобальных определений агентов в текущей версии Codex. Проектную
конфигурацию создавай или обновляй только для локальных переопределений:
особых моделей, более строгих запретов, команд проверки, правил приёмки,
проектных источников истины или временного слоя.

Не используй искусственные идентификаторы, если такого артефакта реально нет.
Для версии схемы сам выбери короткое имя по области действия и источнику
настройки. Покажи выбранное имя и версию в человекочитаемой записи:

```text
Схема подагентов: <имя>, версия <дата или версия>.
Источник: <источник>.
```

Если проект использует другую среду подагентов, сначала определи её
конфигурационный слой. Не выдавай политику маршрутизации за техническую
настройку.

## Локальное хранение и проверка моделей

### Оснастка, каталог и история

Определи оснастку в следующем порядке: явное имя пользователя, текущая среда и
встроенные средства, пользовательская и проектная настройки, найденные
исполняемые файлы. Несколько оснасток проверяй раздельно: одинаковое имя модели
не доказывает общую доступность.

Сначала проверь, есть ли у оснастки адаптер каталога, и только потом вызови
`discover-subagent-models --adapter '<команда>'`. Контракт адаптера каталога —
вызов с аргументом `list` и JSON с именем оснастки, моделями, скрытыми
вариантами и поддерживаемыми усилиями. Адаптер Codex делает `initialize`,
уведомление `initialized` и постраничный `model/list` с `includeHidden`.
Семейство — например, «<семейство>» — служит только условием выбора точной
записи каталога.

Результат обнаружения различай по трём состояниям.

1. Каталог получен и проверен автоматически.
2. Каталог не получен при имеющемся адаптере. Назови `reason_kind`. Значение
   `adapter_contract` означает непригодную запись в `[adapters]` и требует
   исправления настройки. Значения `environment` и `timeout` разрешают повтор
   одного последовательного запуска после восстановления среды.
3. Адаптера каталога для этой оснастки нет. Это состояние «обнаружение
   недоступно для оснастки», а не отказ модели. Назови недостающую часть
   поставки, возьми модели из подтверждённого пользовательского слоя или
   простого списка пользователя и подтверждай их только свидетельством
   фактического запуска.

Установщик Claude кладёт в `tools/adapters/claude-capabilities.json` проверяемую
запись отсутствия нативного каталога. Это не адаптер: не передавай его в
`discover-subagent-models`. Не передавай туда и `tools/adapters/claude-role` —
это адаптер класса исполнения. Пока не появится отдельный документированный
контракт каталога, сообщай ограничение по этой записи и запрашивай
подтверждённый пользовательский список только если он нужен для назначения.

Ни одно из состояний не разрешает перебор предполагаемых имён и не позволяет
выдать обнаружение непроверенным.

В уже используемом проекте рекомендуй `analyze-subagent-sessions` до выбора
ролей. Начальная настраиваемая эвристика достаточной истории: 10 интерактивных
родительских сессий, 30 завершённых ходов, два дня и сведения о моделях и
инструментах для большинства ходов. Анализатор выбирает точный `cwd`, исключает
дочернюю унаследованную историю из повторного подсчёта и не выводит текстов
запросов, содержимого сессий или внешних путей. Сводка помогает выбрать материал
для изучения, но не устанавливает потребность в ролях. Отсутствие распознанных событий записи
не доказывает работу только на чтение. Для карты задач изучи ограниченную
выборку реальных запросов и результатов либо опирайся на структуру проекта,
указав границу охвата. Не включай тексты сессий в сводный отчёт.

Настройки моделей и ролей по умолчанию принадлежат пользователю или локальной
рабочей копии, а не Git-репозиторию. Если у активной оснастки есть
пользовательский слой, используй его. В остальных случаях создай
`subagents.local.toml` из образца и добавь имя файла в `.git/info/exclude`.
Перед сохранением такой политики в Git отдельно спроси пользователя и назови
конкретный файл, который станет общим для команды.

Проектное состояние проверки и явный отказ также храни в
`subagents.local.toml`, даже если сами роли и модели находятся в пользовательском
слое оснастки. Отсутствие операционной политики при состоянии `configured`
считай повреждённым состоянием, которое требует новой проверки.

Проверяй каждую назначенную модель одним последовательным запуском
`check-subagent-models`. Инструмент вызывает адаптер по контракту `<команда
адаптера> <модель>`: запрос идёт через стандартный ввод, непустой ответ при коде
выхода 0 означает доступность. Адаптер может относиться к любой оснастке.
Codex-адаптер — только пример. Не запускай несколько экземпляров проверки или
`codex exec` для разных моделей параллельно: общий каталог моделей и повторные
подключения CLI могут превратить сбой среды в ложный отказ всех моделей.

Результат «недоступна» означает отказ модели или доступа. Результат «не
проверена» означает отсутствие адаптера, исполняемого файла, сети, тайм-аут
либо диагностированный сбой среды CLI. Последний не доказывает недоступность
модели: сохрани текст ошибки и повтори один последовательный запуск после
восстановления среды. В обоих случаях не фиксируй новое назначение модели и
запроси замену или доступ только при подтверждённом отказе модели или доступа.
Короткая проверка модели не доказывает запуск подагента: его проверяй отдельно
по журналу и фактическому назначению модели.

## Предложение, внедрение и приёмка

Веди одно предложение по существенным задачам. Не создавай несвязанные списки
текущих ролей, будущих классов и кандидатов. Храни его в локальной политике,
а в режиме без записи представь в ответе.

| Поле | Содержание |
| --- | --- |
| Задача и результат | Что требуется проекту и как принять результат |
| Предлагаемый маршрут | Подагент с классом исполнения, родитель или человек |
| Сравнение с родителем | Текущие модель и усилие, источник сведений и польза передачи по процедуре выбора |
| Усилие и основание | Предлагаемый уровень, достаточность для задачи и границы уверенности |
| Кандидат и основание | Предварительное назначение либо явный неразрешённый выбор и сведения, которые его разрешат |
| Текущий маршрут | Что исполняется сейчас и почему сохранено |
| Статус проверки | Что известно о доступности, фактической модели и пригодности |
| Следующий шаг | Недостающее свидетельство и зависимое от него действие |

Причина сохранить существующую конфигурацию может состоять в совместимости
или невозможности проверить замену. Это не основание считать прежнее назначение
лучшим. При общем отказе адаптера одинаково ограничь статус старых и новых
назначений. Если различие оправдано прежним успешным испытанием, укажи его
и проверь, применимо ли оно после изменений среды.

Разделяй три результата:

- Проектирование: полный состав существенных задач, предлагаемые маршруты,
  кандидаты, основания и незакрытые решения. Отказ технической проверки
  не отменяет этот результат.
- Внедрение: фактически сохранённая конфигурация и текущие маршруты. Проект
  новой схемы сам по себе не подтверждает её внедрение.
- Подтверждение: свидетельства доступности, исполнения и пригодности.
  При техническом блокере эта часть может остаться незавершённой.

До запуска покажи краткое предложение, затем продолжай разрешённые действия.
В итоговом ответе сохрани новые существенные маршруты и подходящих кандидатов,
даже если внедрение заблокировано. Их выбор проверь по разделу «Выбор
маршрута, модели и усилия» в `confirmed-goals-procedure.md`.

Начинай итог с фактического состояния: изменено предложение, внедрена
конфигурация или проверено исполнение. Укажи незавершённую часть рядом
с результатом. Оговорка в конце не исправляет более широкое заявление
о готовности.

Приёмка охватывает предложение, политику, техническую конфигурацию
и итоговый ответ вместе:

1. В текущем запуске агент задал вопрос о целях и получил ответ пользователя.
   Рабочая формулировка учитывает этот ответ, а маршруты и критерии приёмки
   соответствуют ей. Запись прежних целей или рассказ агента о согласовании
   не заменяют наблюдаемый обмен сообщениями. При ожидании ответа допустим
   только результат «ожидает уточнения целей», без готовой политики.
2. У каждой существенной задачи есть обоснованный предлагаемый маршрут.
   Прямой маршрут не требует отдельного класса ради полноты таблицы.
   Проверены три решения по процедуре выбора: сравнение с текущим родителем,
   модель и усилие. Их основания не подменяют друг друга.
3. Подходящий новый кандидат либо предложен, либо включён в явно неразрешённый
   выбор, либо исключён по предметному основанию. Упоминания в списке мало.
4. Общий блокер одинаково ограничивает подтверждение всех затронутых назначений.
   Сохранение старого маршрута не подменяет предлагаемое решение.
5. Сводка ответа содержит существенные изменения, кандидатов и причины
   расхождения с текущей конфигурацией, последствия и условия устранения.
   Они не скрыты за ссылкой на файл.
6. Статусы соответствуют сохранённым файлам и журналам. Подсчёт маршрутов,
   успешный разбор формата и наличие вызова проверяют только свои свойства.

Если проверяет отдельный агент, передай ему этот договор и четыре поверхности
результата. Проверка адаптера или синтаксиса не заменяет приёмку предложения.
Родитель выполняет эту сверку и без отдельного агента.
Проверяй смысл, а не названия разделов. Для совпадающих предлагаемого и текущего
маршрутов достаточно одного описания с явным статусом. Для микрозадачи
допустима короткая сводка без таблицы и отдельных заголовков.

## Право на запись

Не запрещай запись всем слабым моделям только из-за уровня модели. Запрещай
запись ролям, для которых она не нужна. Например, исследователь только для чтения
остаётся без записи, а отдельный patch-worker может выполнять малые обратимые
правки, если это дешевле прямого выполнения родителем.

Подагент с правом записи допустим только при всех условиях:

- родитель явно поручил правку и указал точные файлы или узкую область записи;
- правка малая, обратимая и не требует широкого проектного контекста;
- результат можно проверить различиями, форматированием, тестом или другой дешёвой
  проверкой;
- подагенту запрещено менять правила, навыки, шаблоны, `AGENTS.md`,
  архитектурные решения, требования и другие источники истины;
- подагенту запрещено принимать проектные решения, расширять область задачи и
  самостоятельно выбирать новые файлы для записи;
- родитель проверяет diff, запускает доступную проверку и сам принимает или
  отклоняет результат.

Если хотя бы одно условие не выполнено, оставляй запись родителю или более
сильной модели.

## Проверки качества

- Требуй структурированный результат для делегированных задач везде, где это
  возможно.
- Требуй ссылки на источники для фактических утверждений и ссылки на файлы для
  утверждений о коде.
- Требуй явную неопределённость при неполных данных.
- Отклоняй результат подагента, который незаметно расширяет область задачи.
- Для подагента с правом записи требуй список изменённых файлов, описание правки
  и проверку, которую должен выполнить родитель.
- Эскалируй, когда подагент сообщает о неуверенности, противоречивых данных,
  нехватке контекста, сбое инструмента или невозможности проверки.
- Не позволяй одной и той же дешёвой модели и подготовить, и финально принять
  результат с высоким влиянием.
