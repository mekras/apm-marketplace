# Шаблоны маршрутизации

Используй эти шаблоны как отправную точку. Адаптируй их к проекту, а не
копируй без изменений.

## Матрица классификации задач

| Измерение | Делегирование дешёвой модели подходит, когда | Нужна эскалация, когда |
|---|---|---|
| Риск | Результат рекомендательный, обратимый или будет проверен позже | Результат меняет долговечное знание проекта |
| Неоднозначность | Критерии явные и локальные | Цель, область или критерии приёмки неясны |
| Контекст | Входные данные малы и самодостаточны | Правильность зависит от широкой истории репозитория |
| Проверка | Схема, тесты, ссылки или различия позволяют проверить результат | Нужно суждение человека или сильной модели |
| Цена ошибки | Плохой результат легко отбросить | Плохой результат может ввести в заблуждение будущие решения |
| Независимость | Части не влияют друг на друга | Подзадачам нужно общее изменяющееся состояние |

## Пример карты задач

Таблица показывает возможные результаты, а не фиксированный перечень ролей.
Модель назначается после оценки задачи и кандидатов. Подготовка рекомендации
не передаёт подагенту право принять проектное решение.

| Работа | Результат подагента в заданной области | Приёмка и решение |
| --- | --- | --- |
| Сбор фактов | Утверждения с источниками и пробелами | Родитель проверяет свидетельства и охват |
| Анализ | Причины, противоречия, следствия и альтернативные объяснения | Родитель проверяет выводы и неопределённость |
| Проектирование | Варианты устройства, ограничения и последствия | Родитель проверяет варианты, уполномоченный владелец выбирает решение |
| Поиск решений | Возможные подходы, сравнение по критериям и рекомендация | Родитель проверяет полноту альтернатив и основания рекомендации |
| Малая обратимая правка | Изменения только в разрешённых файлах | Родитель проверяет различия и результат |
| Независимая проверка | Дефекты, свидетельства и остаточные риски | Родитель принимает результат проверки |
| Утверждение и запись источника истины | Подагенту не поручаются | Родитель действует в своих полномочиях, решение человека остаётся у человека |

Для каждой существенной работы допустим и прямой маршрут родителя или человека.
Обоснуй его контекстом, полномочиями и стоимостью приёмки. Не исключай анализ
или проектирование только из-за того, что их итог может повлиять на решение.

## Контракт делегированной задачи

Используй компактный контракт:

```text
Цель:
Граница входных данных:
Разрешённые действия/инструменты:
Разрешённая область записи:
Запрещённые действия:
Схема результата:
Обязательные свидетельства:
Шкала уверенности:
Остановиться и эскалировать, если:
Бюджет токенов/времени:
```

Предпочитай маленькие явные контракты широким поручениям. Если контракту нужно
длинное объяснение, задачу может быть невыгодно делегировать дешёвой модели.

## Пример схемы результата

```json
{
  "status": "complete|partial|blocked",
  "items": [
    {
      "claim": "Короткое фактическое утверждение или кандидат результата",
      "evidence": "Путь к файлу, строка, URL или идентификатор источника",
      "confidence": "high|medium|low",
      "risk": "Что может быть неверно"
    }
  ],
  "open_questions": [],
  "escalation_needed": false
}
```

## Триггеры эскалации

- Не хватает обязательных входных данных.
- Источники противоречат друг другу.
- Результат не может сослаться на источники.
- Потребуется больше одной повторной попытки.
- Подагенту нужно менять файлы вне своей области.
- Для вывода о правилах, архитектуре, безопасности, праве, финансах или
  источнике истины не хватает полномочий, оснований или профильной приёмки.
  Сам предмет анализа не требует остановки, если подготовка рекомендации
  явно входит в контракт и не передаёт право утверждения.
- Подагенту с правом записи нужно выбирать новые файлы для записи или менять
  источники истины.
- Результат выглядит правдоподобно, но его нельзя дёшево проверить.

## Бюджетные ограничения

- Задавай максимум подагентов на одну родительскую задачу.
- Задавай максимум размера контекста для делегированной задачи.
- Предпочитай один дешёвый проход с проверкой повторным дешёвым попыткам.
- Считай полную стоимость, а не только цену токенов модели.
- Включай стоимость проверки в решение о маршрутизации.
- Отключай делегирование для микрозадач, где накладные расходы поручения
  преобладают.
- Не придумывай универсальные числовые пороги. Используй проектные измерения,
  если они есть; иначе начинай с консервативных ограничений и пересматривай их
  после малого эксперимента.

## Сопоставление уровней с моделями

Для черновика политики используй названия уровней, пока конкретные модели не
известны. Для внедрения сначала попробуй получить список моделей из текущей
среды Codex или другого целевого окружения. Не бери модели из документации,
глобальных настроек или другого проекта как готовое решение. Если
автообнаружение не сработало, спроси у пользователя простой список доступных
моделей и сам сопоставь их с назначениями. Если модели не известны, фиксируй
открытое решение вместо молчаливой подстановки.

```text
cheap:
  model:
  strengths:
  forbidden_for:
  max_context:
  max_retries:

medium:
  model:
  strengths:
  forbidden_for:
  max_context:
  max_retries:

strong:
  model:
  responsibilities:
  must_review:
```

Если в проекте несколько дешёвых или средних моделей, разделяй их по
возможностям, а не только по цене: извлечение, код, чтение длинного контекста,
многоязычная работа, использование инструментов или надёжность
структурированного результата.

## Оснастки и адаптеры проверки

Сначала определи все оснастки, через которые проект действительно запускает
подагентов. Для каждой зафиксируй пользовательский слой, проектные
переопределения, источник моделей и технический след реального запуска.
Не переносись автоматически между оснастками по совпадению имени модели.

### Три контракта адаптеров

Слово «адаптер» покрывает три разные роли. Они различаются вызовом, ответом и
местом записи в настройке. Файл, выполняющий один контракт, не годится для
другого.

| Роль | Где записан | Вызов | Ожидаемый ответ |
| --- | --- | --- | --- |
| Адаптер каталога | ключ раздела `[adapters]` | `<команда> list` | JSON с `harness`, `status` и массивом `models` |
| Проба модели | тот же ключ раздела `[adapters]` | `<команда> <модель>`, запрос в стандартном вводе | непустой текст и код возврата 0 |
| Адаптер класса исполнения | поле `adapter` назначения класса для оснастки | запускается `run-execution-class` | первая строка JSON с `model`, `usage` и `model_evidence` |

Запись в `[adapters]` обязана выполнять оба первых контракта. Адаптер, который
отвечает только на пробу, ломает обнаружение каталога, поэтому его нельзя
подставлять в `[adapters]` ради заполнения раздела. Адаптер класса исполнения
в `[adapters]` не записывается.

Прежде чем записать команду в `[adapters]`, запусти её с аргументом `list` и
убедись, что ответ разбирается как JSON с массивом `models`. Сообщение
`reason_kind` в `adapter_contract` от `discover-subagent-models` означает
неподходящий адаптер, а не недоступную оснастку.

### Возможности оснастки

До назначения классов зафиксируй для каждой активной оснастки четыре
возможности и источник свидетельства по каждой:

- адаптер каталога моделей — есть или нет;
- адаптер класса исполнения — есть или нет;
- допустимые режимы доступа, в том числе право записи;
- способ подтверждения фактической модели.

Возможности берутся из состава поставки и проверенного запуска, а не из
совпадения имён. Для поставляемых адаптеров это состояние таково:

- Codex: `install-codex-tools` кладёт адаптер каталога как
  `tools/adapters/codex-subagents` и адаптер класса как
  `tools/adapters/codex-role`. Адаптер класса пока не извлекает независимое
  свидетельство модели.
- Claude: `install-claude-tools` кладёт адаптер класса
  `tools/adapters/claude-role` и запись возможностей
  `tools/adapters/claude-capabilities.json`; адаптер работает лишь в режиме
  чтения. Адаптера каталога для этой оснастки в поставке нет, поэтому шаг
  обнаружения каталога для неё невыполним.

Отсутствие возможности не отменяет задачу и не разрешает подмену. Если
возможность отсутствует, класс для этой оснастки остаётся ненастроенным,
задачу выполняет родитель, а ограничение записывается в настройку и в итоговый
ответ с названием недостающей части.

### Область действия правил проекта

Правило проекта, исполнимое не во всех активных оснастках, записывай одним из
трёх способов: пометь его областью действия и добавь равноценную ветвь для
остальных оснасток, переформулируй критерий нейтрально либо назови ограничение
явно. Критерий проверки формулируй через наблюдаемый след запуска активной
оснастки, а не через события одной из них. Имена ролей, моделей и путей к
средствам конкретной оснастки держи в локальной настройке, а не в правиле.

### Проверка моделей

Проба модели использует один контракт для любой оснастки:

```text
<команда адаптера> <модель>
```

Адаптер получает короткий запрос из стандартного ввода, возвращает текстовый
ответ в стандартный вывод и завершает работу с кодом 0 только при успешном
вызове модели. Запиши команды и модели в неотслеживаемый
`subagents.local.toml`, либо используй поддерживаемый пользовательский слой
оснастки. Если в Git найден старый файл политики с моделями, сообщи о миграции
и не переписывай его без отдельного решения пользователя.

Проверяй модели командой:

```bash
tools/check-subagent-models --config subagents.local.toml
```

Результат `available` разрешает назначение модели. `unavailable` и
`unverified` требуют замены модели или восстановления доступа. Эта проверка не
заменяет журнал фактического запуска подагента.

## Пример Codex-конфигурации

Для Codex политика маршрутизации не заменяет техническую настройку агентов
Codex. В режиме внедрения проверь или создай проектные файлы `.codex/`.
Если `.codex/` отсутствует, создай настройку с нуля, а не останавливайся на
инструкции пользователю.

Если одинаковая схема подагентов нужна в нескольких проектах на одной машине,
сначала проверь глобальный слой Codex: `$CODEX_HOME`, `~/.codex/config.toml`,
профили `~/.codex/<profile>.config.toml` и поддерживаемое место для глобальных
определений агентов в текущей версии Codex. Общие параметры и стандартные роли
лучше держать глобально, а в проекте оставлять только переопределения.

Если глобального слоя ещё нет, но в текущем проекте уже есть рабочая `.codex/`
схема, предложи перенос:

1. Выделить общие параметры fan-out, стандартные роли, модели и правила
   проверки.
2. Перенести их в глобальную конфигурацию или глобальный профиль Codex.
3. Оставить в проекте только локальные отличия и короткую ссылку на глобальную
   схему.
4. Проверить фактический запуск подагента после переноса по JSONL и строке
   расхода.

Сначала покажи этот перенос человеку как согласуемый черновик прямо в ответе.
Не создавай отдельный документ проекта для плана переноса, если человек явно не
попросил сохранить план в файле. После согласования применяй изменения к
конфигурации и проверяй реальный запуск.

Для версии схемы сам выбери короткое имя по области действия и источнику
настройки. Не проси человека придумывать служебный идентификатор. Покажи
выбранное имя и версию в человекочитаемой записи:

```text
Схема подагентов: <имя>, версия <дата или версия>.
Источник: <источник>.
```

Минимальные ограничения fan-out:

```toml
# .codex/config.toml
[features]
# Включай только если текущий Codex CLI показывает, что реальный fan-out
# находится за этим флагом.
enable_fanout = true

[agents]
max_threads = 2
max_depth = 1
# Не сокращай ради скорости, если цель — стоимость.
job_max_runtime_seconds = 1800
```

`max_threads` ограничивает число одновременных потоков. `max_depth = 1`
запрещает рекурсивный fan-out: дочерний агент не должен порождать следующий
уровень подагентов без отдельного решения.

Пример дешёвого read-only исследователя:

```toml
# .codex/agents/cheap_explorer.toml
name = "cheap_explorer"
description = "Read-only explorer for low-risk evidence gathering."
model = "<cheap-model>"
model_reasoning_effort = "low"
sandbox_mode = "read-only"
developer_instructions = """
Work only on narrow read-only tasks.
Search and read the minimum required files.
Return concise structured findings with file references.
Do not edit files.
Do not decide policy.
Escalate on ambiguity, conflicting evidence, missing context, or requests to
change project sources of truth.
"""
```

Пример дешёвого исполнителя для малых обратимых правок:

```toml
# .codex/agents/cheap_patch_worker.toml
name = "cheap_patch_worker"
description = "Cheap bounded patch worker for small reversible edits requested by the parent agent."
model = "<cheap-code-model>"
model_reasoning_effort = "low"
sandbox_mode = "workspace-write"
developer_instructions = """
Edit files only when the parent task gives an explicit file list or a narrow
write scope.
Make only small reversible changes with a cheap verification path.
Return changed files, summary, verification performed or recommended, risk, and
escalation_needed.
Do not edit AGENTS.md, skills, rules, templates, requirements, architecture
decisions, or other sources of truth.
Do not broaden the task, choose unrelated files, accept the final result, or make
project decisions.
Escalate on ambiguity, missing write scope, failing verification, broad context,
or requests to change project sources of truth.
"""
```

Не превращай `cheap_explorer` в роль с правом записи. Старые проекты обновляй
добавлением отдельного patch-worker и сужением общего запрета записи до правила
по умолчанию.

Пример среднего проверяющего для ограниченных сравнений:

```toml
# .codex/agents/bounded_policy_reviewer.toml
name = "bounded_policy_reviewer"
description = "Reviewer for bounded policy drafts and routing consistency."
model = "<medium-model>"
model_reasoning_effort = "medium"
sandbox_mode = "read-only"
developer_instructions = """
Review only the provided policy draft and referenced files.
Check consistency, missing escalation rules, and unsupported claims.
Return risks, required evidence, and suggested corrections.
Do not accept the final result.
Do not edit files.
Escalate if the review requires a project decision or broad context.
"""
```

Для Codex один `AGENTS.md` без пользовательской конфигурации `~/.codex` или
обоснованного проектного слоя `.codex/` не является полной настройкой агентов
Codex. Конкретная политика подагентов должна фиксироваться в целевом проекте
или пользовательском слое, а не в переносимом навыке.

### Фиксация политики в целевом проекте

Используй этот раздел как проверку результата настройки, а не как готовую
политику. Для каждого целевого проекта отдельно реши:

- где живёт рабочая конфигурация подагентов;
- где зафиксированы проектные классы задач для делегирования;
- какие роли, модели, лимиты и запреты доступны именно в этой среде;
- какой технический след доказывает запуск и переключение модели;
- какой отчёт нужен после фактического запуска подагентов.

Если политика фиксируется в `AGENTS.md`, применяй профильный навык сопровождения
`AGENTS.md`. `ai-setup-subagents` отвечает за содержание политики подагентов, но
не заменяет общие правила минимальности, иерархии и машинной пригодности
`AGENTS.md`.

### Ясность обязательности делегирования

В проектных правилах разделяй три уровня обязательности:

| Уровень | Как формулировать | Последствие |
|---|---|---|
| Не применять | Микрозадача или проверка дешевле прямым проходом родителя | Родитель выполняет сам |
| Предпочтительно | Узкий поиск, извлечение фактов или проверка охвата с дешёвой проверкой результата | Родитель пытается делегировать, но может обоснованно не делегировать |
| Обязательно | Пользователь или проектное правило прямо требуют подагента, либо задача нужна для проверки самой схемы подагентов | Недоступность роли, модели, лимита или технического следа блокирует задачу до разрешения человека |

Не смешивай «предпочтительно» и «обязательно» в одном абзаце. Если недоступность
подагента должна блокировать задачу, укажи, какое условие делает запуск
обязательным и какой технический след нужно проверить.

## Обновление старой настройки

Для проекта, настроенного старой версией навыка, используй простой порядок:

1. Найди пользовательский слой `~/.codex/config.toml`, доступные глобальные
   определения агентов, при наличии проектные `.codex/config.toml`,
   `.codex/agents/*.toml`, `AGENTS.md` и `tools/codex-*`.
2. Оставь роли только для чтения (`cheap_explorer`, роли проверки) без права записи.
3. Добавь отдельную роль `cheap_patch_worker` или аналог с `workspace-write`.
4. Замени общий запрет «подагенты не редактируют файлы» на правило по умолчанию
   с исключением для роли с правом записи по явному поручению родителя.
5. Обнови запускатель: по умолчанию `read-only`, для patch-worker только явный
   `CODEX_SUBAGENT_SANDBOX=workspace-write`.
6. Проверь, что источники истины остаются запрещены для дешёвых подагентов
   с правом записи, а родитель принимает результат по различиям и проверке.

Человеку достаточно попросить: «Обнови старую настройку
`ai-setup-subagents` до версии с отдельным дешёвым patch-worker». Остальное
агент должен вывести из файлов проекта.

## Маршрут через отдельный процесс для выбора модели

### Переносимые контракты

`discover-subagent-models --adapter '<команда>'` получает JSON-каталог одной
оснастки. Для Codex команда адаптера обращается к App Server и возвращает
страницы `model/list`. В каталоге сохраняются точные идентификаторы, скрытость
и варианты усилия. Другие оснастки подключаются тем же контрактом. При неудаче
поле `reason_kind` разделяет незапущенную команду, невыполненный контракт
каталога, тайм-аут и признак сбоя среды. Вывод о недоступности оснастки делай
только по `environment` или `timeout`.

`analyze-subagent-sessions --sessions <каталог> --cwd <проект>` выдаёт только
агрегаты: родительские сессии, завершённые ходы, токены, вызовы инструментов,
наблюдаемые события записи, длительность и сигналы наследования модели. Это
сводка активности без предметной классификации задач. Он не сохраняет
и не печатает запросы или содержимое журналов.

`run-execution-class <класс> --target <оснастка>` читает неотслеживаемый
`subagents.local.toml` и стандартный ввод. Класс задаёт контракт результата и
ограничения задачи. Назначение класса для оснастки задаёт модель, усилие, режим
доступа и адаптер. Входные файлы передаются только явными `--input`. Журнал,
итог и вывод ошибок сохраняются локально. Несовпадение назначенной и фактической
модели, отсутствие класса, назначения или `agent_path = null` означает провал,
а не успешный запуск.

Если запуск обслуживает обязательство профильной роли, передай
`--obligation <идентификатор>`. В записи запуска появятся `run_id`,
`obligation_id`, назначенная и фактическая модели, `model_matches`, пути к
журналу и результату, доступность результата и код завершения. Поля фиксируют
наблюдаемый запуск и расположение результата. Они не создают и не закрывают
обязательство, не подтверждают смысловую пригодность результата, не разрешают
исключение человека и не сохраняют текст запроса. Без параметра прежний вызов
совместим с прежней политикой.

Для точного идентификатора модель должна совпасть буквально. Когда оснастка
принимает псевдоним, сравнивай его только с подтверждённым значением.

### Свидетельство модели

Первая строка ответа доверенного адаптера — объект JSON с `model`, `usage`
и `model_evidence`. Для подтверждения адаптер сохраняет исходный поток событий
оснастки в журнал, заданный запускателем через `CODEX_ROLE_LOG` или
`CLAUDE_ROLE_LOG`. Пример ссылки:

```json
{"model":"observed-model","model_evidence":{"source":"journal","line":3,"field":["message","model"]},"usage":null}
```

`line` — номер строки JSONL от единицы, `field` — последовательность ключей
объектов JSON. Ссылка ведёт на событие исполнения, не на копию параметров
запроса. Не создавай событие модели из назначения. Запускатель проверяет
ссылку в собственном уникальном журнале и сохраняет путь, строку, поле и
SHA-256 прочитанного журнала. Адаптер остаётся доверенной частью интеграции:
проверка ссылки не доказывает достоверность произвольного адаптера или
серверную идентичность модели независимо от оснастки.

Отчёт разделяет `assigned_model`, заявление адаптера `reported_model` и
подтверждённую `actual_model`. При проверяемом свидетельстве `model_status`
равен `confirmed`, а `model_matches` показывает результат сравнения с
назначением. При отсутствующей или повреждённой ссылке `model_status` равен
`unconfirmed`, `actual_model` и `model_matches` равны `null`, причина находится
в `model_evidence_reason`. Прежний заголовок только с `model` больше не
подтверждает модель. Оба запускателя, включая `run-subagent-role`, сохраняют
полученный ответ, но возвращают код 1 при неподтверждённой или несовпавшей
модели. Успех процесса и подтверждение модели не заменяют приёмку содержания
родителем и сами не закрывают обязательство профильной роли.

Поставляемый адаптер Codex пока не извлекает независимое свидетельство модели
и возвращает `model: null`. Параметр `--model` остаётся только назначением.
Это ограничение подтверждения, а не свидетельство подмены модели.
Адаптер Claude ссылается на `assistant.message.model`. Одного системного
события настройки недостаточно. Несколько разных моделей или ответ без имени
модели оставляют подтверждение неизвестным.

Для псевдонимов оснастки действует прежнее правило: когда оснастка
принимает псевдоним, локальное назначение указывает `actual_model_prefix` —
префикс фактически допустимого идентификатора. Сопоставление по семейству без
такого префикса запрещено. Так подмена модели остаётся наблюдаемой, но локальная
политика не зависит от формата отчёта конкретной оснастки.

```toml
[execution_classes.cheap_readonly_research]
writes = false
result = "status, items, evidence, confidence, risk, open_questions, escalation_needed"
stop = "неоднозначность, конфликтующие свидетельства или выход за границу"

[targets.<оснастка>.execution_classes.cheap_readonly_research]
model = "точный-идентификатор-или-псевдоним"
effort = "low"
sandbox = "read-only"
adapter = ["tools/adapters/<оснастка>-role"]
# actual_model_prefix нужен только для псевдонима.
```

Сохраняй `run-subagent-role` для совместимости с локальной политикой старых
проектов, но в новых примерах запускай класс исполнения. Сохраняй
`codex-model-subagent` для прямого запуска модели вне схемы классов.

Если проверка показывает, что встроенный fan-out создаёт дочерний поток, но не
применяет модель из пользовательского или проектного слоя Codex, используй
отдельный процесс Codex для задач, где модель должна быть выбрана
гарантированно.

Переносимые запускатели лежат в директории `scripts/` навыка:

- `codex-model-subagent` — запуск выбранной модели;
- `codex-usage-report` — краткий, однострочный, подробный и JSON-отчёт;
- `run-execution-class` — запуск класса через локальное назначение оснастки;
- `evaluate-model-selection.py` — проверка полной матрицы пилота и
  воспроизведение последовательного выбора без модельных вызовов;
- `install-subagent-tools` — копирование переносимых средств проверки и запуска
  в `<project-root>/tools`;
- `install-codex-tools` — дополнительно копирование средств Codex, адаптера
  класса исполнения `codex-role` и адаптера каталога, который устанавливается
  под именем `codex-subagents`.
- `install-claude-tools` — дополнительно копирование адаптера класса
  исполнения Claude и записи его возможностей. Адаптер каталога моделей для
  этой оснастки не поставляется.

Установщик следует общим правилам установщиков оснастки (навык `ai-setup-apm`,
`references/tooling-installers.md`): вызов `install-* [project-root]`,
копирование в `tools/`, строка `installed=` в конце.

Отображение файлов для всех трёх установщиков задаёт
`scripts/subagent-tools.manifest`. После установки проверь рабочую копию тем же
манифестом: `check-subagent-tools-drift.py --profile portable`, `--profile
codex` или `--profile claude`. При пропаже или расхождении файла не исправляй
`tools/` вручную: повтори соответствующий установщик.

При внедрении в проект выполни установку из директории навыка:

```bash
.apm/skills/ai-setup-subagents/scripts/install-subagent-tools .
```

После установки вызов выглядит так:

```bash
printf '%s\n' 'Найди один факт только во входном файле.' | \
  tools/run-execution-class cheap_readonly_research --target <оснастка> \
  --obligation <идентификатор-обязательства> \
  --input <файл>
```

Если среда APM даёт стабильный путь к файлам навыка, можно вызывать
`scripts/run-execution-class` напрямую без копирования в проект.

Для сравнения нескольких назначений одного класса используй отдельную процедуру
из `model-selection-evaluation.md`. Она хранит точные модели и проектные случаи
в локальном слое, а поставляемый скрипт только проверяет готовую матрицу
результатов.

После задачи, где фактически запускались подагенты, однострочный отчёт должен
быть понятен без чтения JSONL:

```text
Модели: экономичная-mini-модель 14.5 тыс. | лимиты: общий 14.5 тыс. | время: 6.9 с
```

Для подробного анализа сохраняй JSONL и финальный ответ. Отдельно проверяй,
какие модели относятся к общему лимиту, какие имеют отдельный лимит, и какие
модели расходуют общий лимит медленнее.

## Проверочный запрос для Codex

Короткая просьба к родителю может не запустить подагента, потому что родитель
вправе решить, что координация дороже прямого выполнения. Для проверки
используй явный контракт:

```text
Follow the current project subagent scheme.
This task should use `cheap_explorer` for bounded evidence gathering if
justified, and may use `strong_reviewer` for an independent second pass if that
is justified by the current policy. Parent agent must make the final acceptance
decision.

Task: review the current subagent scheme using only `.codex/config.toml`,
`~/.codex/config.toml`, user or global agent definitions, optional
project `.codex/agents/*.toml`, `AGENTS.md`, and `ai-setup-subagents`.

Return valid JSON only with keys:
`findings`, `used_subagents`, `escalations`, `rejected_results`.
```

Проверка успешна только при техническом признаке запуска подагента:
`thread_spawn_edges`, `subagent_notification`, дочерний поток в состоянии Codex
или JSONL-событие subagent. Ответ родителя без такого признака не доказывает
работу подагентов.

Не используй `codex exec --ephemeral` как обязательную проверку Codex
subagents. В этом режиме app-server может быть недоступен, из-за чего
порождение дочерних потоков проверяется неправильно.

`/agent` показывает активные потоки агентов. Он может показывать только
`Main [default]`, если дочерние потоки не запущены; это не список файлов
`.codex/agents/*.toml`.

## План измерения

Прогони политику на малом наборе реальных задач и зафиксируй:

- общее число токенов и вызовов инструментов;
- время выполнения;
- число эскалаций;
- число отклонённых результатов подагентов;
- дефекты, найденные после приёмки;
- время проверки родительским агентом;
- была бы та же задача дешевле при прямом проходе сильной моделью.

Пересматривай таблицу маршрутизации, когда дешёвые результаты часто требуют
исправления, эскалации становятся частыми или проверка занимает больше времени,
чем прямое выполнение.

Если измерение сравнивает несколько кандидатов на один класс, не выбирай
кандидата по одному среднему значению. Применяй предварительный отсев,
повторяемые случаи, отложенную выборку и критерии из
`model-selection-evaluation.md`.
