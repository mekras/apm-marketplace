# Проверка назначения моделей

Эта процедура нужна, когда для одного класса исполнения доступно несколько
кандидатов, а сопоставимое качество экономичного назначения ещё не подтверждено.
Она сравнивает сочетания оснастки, точной модели, уровня рассуждения, класса
задач и контракта. Результат для одного сочетания нельзя переносить на другое
без новой проверки.

## Где хранить данные

Храни конкретные модели, задания, снимки проекта, результаты запусков и отчёты
в локальном слое целевого проекта. Подходящий вариант — каталог
`subagent-model-evals.local/`, добавленный в `.git/info/exclude`. Не помещай
точные идентификаторы моделей, историю проекта-потребителя и его результаты в
переносимый навык.

До запуска зафиксируй:

- класс задачи и неизменный контракт результата
- SHA-256 точного текста или канонического представления контракта
- кандидатов и точные идентификаторы фактически запускаемых моделей
- критерии приёмки и определение критического дефекта
- способ измерения модельного расхода
- способ перевода времени родительской проверки в единицы полной стоимости
- пороги качества, экономии и допустимого роста времени проверки
- требуемый объём отложенной выборки и основание его выбора.

Если время родителя нельзя перевести в общую единицу, сохраняй модельный расход
и время отдельно. В этом случае нельзя подтверждать снижение полной стоимости.

## Подготовка случаев

Для холодного старта используй общие случаи только как предварительный сигнал.
После появления истории предпочитай новые реальные задачи и реконструкцию
задач из Git:

1. Возьми снимок проекта до принятого изменения.
2. Восстанови намерение по задаче, требованию, сообщению коммита и доступным
   проверкам. Если намерение требует домысла, не используй случай.
3. Удали текущее дерево, позднюю историю и название принятого решения из входов
   кандидата.
4. Зафиксируй разрешённые файлы, инструменты, область записи и условие
   остановки.
5. Составь критерии, допускающие несколько корректных решений. Прежнее
   изменение подтверждает реализуемость, но не служит единственным эталоном.
6. Сначала помести случай в настроечную выборку. Более новые случаи оставь для
   отложенной проверки.

Начальная настроечная выборка для каждого класса содержит минимум два обычных,
два пограничных случая, один случай обязательной остановки или эскалации и один
случай с привлекательным запрещённым действием. Этот минимум проверяет
работоспособность процедуры, но сам по себе не доказывает малое различие
качества.

## Предварительный отсев

Исключай кандидата только для текущего класса, если модель недоступна,
фактическая модель не подтверждается, отсутствуют обязательные возможности,
минимальный опыт превышает бюджет либо кандидат дважды провалил один и тот же
детерминированный базовый случай. Единичная субъективная оценка не является
достаточным отсевом.

Верни кандидата при изменении модели, оснастки, цены, контракта или класса
задач. Сохрани причину исключения в `candidates[].eligibility` локального
входного файла.

## Сбор полной матрицы пилота

Один раз выполни все прошедшие отсев сочетания на настроечной и отложенной
выборках. Для каждого сочетания и случая нужно не меньше числа повторов из
`settings.minimum_repeats`. Перемешивай порядок запусков. Сначала применяй
детерминированные проверки, затем слепую приёмку по рубрике без названия модели
и прежнего принятого изменения.

В `runs[]` сохрани:

- `candidate_id`, `case_id` и номер `repeat`
- `accepted_without_revision`
- `critical_defect`
- `model_cost_units`
- `review_seconds`
- `total_cost_units`, если способ объединения расходов зафиксирован заранее.

Артефакты модели и журналы запуска храни рядом с локальной записью, но не
включай их тексты в сводный отчёт без необходимости. Не сохраняй секреты и пути
за пределами целевого проекта.

## P0 без запуска скрипта

Если Python недоступен, вручную:

1. Проверь полноту матрицы и предварительный отсев.
2. Открывай всем кандидатам два первых случая с двумя повторами.
3. После каждой пары новых случаев исключай критические провалы. Остальных
   исключай только если верхняя граница их доли принятия ниже нижней границы
   лидера с учётом допустимого отставания.
4. Среди кандидатов с сопоставимым качеством выбирай меньшую полную стоимость.
5. Сравни выбранное назначение с лучшим результатом полного перебора на
   отложенной выборке.
6. Верни `confirmed`, `refuted` или `insufficient_data`. Сохрани текущую
   политику при недостаточных данных.

Ручной расчёт пометь как не проверенный поставляемой автоматизацией.

## P1 с Python 3

Скопируй образец `assets/model-selection-input.sample.json` в локальный каталог,
заполни кандидатов, случаи и результаты, затем выполни:

```bash
python3 tools/evaluate-model-selection.py \
  --input subagent-model-evals.local/<класс>/matrix.json \
  --output subagent-model-evals.local/<класс>/report.json
```

Скрипт использует только стандартную библиотеку Python. Он проверяет формат и
полноту матрицы, применяет интервалы Уилсона, воспроизводит последовательный
отбор по заранее заданному порядку случаев и сравнивает его стоимость с полным
перебором. Выход содержит хэш входа, раскрытые раунды, исключения, выбранного
кандидата, хэш проверенного контракта, отложенное сравнение и основание статуса.

`confirmed` означает, что записанные пороги выполнены в границах набора.
Изменение рабочей политики всё равно требует решения владельца. `refuted`
запрещает выдавать экономичное назначение за равноценное. `insufficient_data`
сохраняет текущий или эталонный маршрут.

## Накопление проектных данных

После пилота добавляй новые подходящие задачи в хронологически более новую
отложенную выборку. Модель-претендент запускается только в изолированной копии,
с явным бюджетом и не чаще установленной локальной политикой доли задач.
Пересматривай назначение при изменении модели, оснастки, цены, контракта,
ухудшении рабочих результатов или накоплении достаточного числа новых случаев.
