# Настройка после ответа о целях

Читай эту процедуру только после выполнения первого этапа `../SKILL.md`.

Перед существенной правкой политики подагентов получи `ai-work-control/full`;
продолжай по его результату без повторения контроля.

## Переносимость

P0 проектирует и записывает политику средствами агента по процедуре навыка. До
запуска файла из `../scripts/**` проверь его интерпретатор и платформу. Если Python
или POSIX-среда недоступны, продолжи настройку вручную по справкам и пометь
автоматическое обнаружение, запуск либо анализ как непроверенные. Не устанавливай
недостающую среду без явного решения пользователя.

Навык помогает настроить политику подагентов для конкретного проекта или
пользовательской среды. Он не хранит политики целевых проектов внутри себя:
здесь остаются метод, шаблоны, критерии проверки и переносимые инструменты.

## Главная граница

Разделяй четыре слоя:

- метод настройки — этот навык;
- политика целевого проекта — пользовательская настройка активной оснастки,
  неотслеживаемый `subagents.local.toml` или, только по явному решению
  пользователя, проектный файл в Git;
- техническая конфигурация — поддерживаемый слой активной оснастки, профили,
  определения агентов, запускатели и отчёты;
- текущий запуск — фактические подагенты, модели, JSONL, лимиты и результат.

Не записывай роли, модели, лимиты, Git-правила и исключения конкретного проекта
в переносимый навык. Если нужно изменить `AGENTS.md`, сначала применяй
профильный навык сопровождения `AGENTS.md`; `ai-setup-subagents` отвечает только
за содержание политики подагентов.

## Режимы

- `policy` — спроектировать или проверить политику без изменения файлов.
- `implementation` — зафиксировать политику и конфигурацию в целевом проекте
  или пользовательском слое.
- `repair` — исправить существующую схему после провала маршрутизации,
  перерасхода, отсутствия технического следа или смешения слоёв.

Явный запрет правок всегда означает `policy`. Запросы «настрой», «внедри»,
«зафиксируй», «обнови схему», «исправь настройку» означают `implementation` или
`repair`, если пользователь не ограничил работу черновиком.

## Состояние и срок проверки

Для проекта-потребителя различай три состояния: политика настроена, пользователь
явно отказался от её создания, решение ещё не принято. Храни состояние, срок
повторной проверки и дату последней успешной проверки в проектном локальном
слое. Рекомендуемый переносимый формат описан в
`../assets/subagents.local.toml.sample`.

Во время настройки спроси срок повторной проверки и предложи 30 дней как
значение по умолчанию. Полную проверку запускай по явному запросу, при отсутствии
и политики, и зафиксированного отказа либо после истечения срока существующей
политики. Отсутствующую, нечитаемую или будущую дату считай требующей проверки.
Явный отказ подавляет автоматический запуск из-за отсутствия политики, но прямой
запрос пользователя имеет приоритет. Срок повторной проверки применяется только
к состоянию `configured`; для `creation_declined` не вычисляй следующую дату.

После успешной проверки предложи отдельным изменением обновить дату. В режиме
без записи только сообщи дату, которую нужно зафиксировать: не выдавай её за
сохранённую. Если пользователь отказался создавать политику и разрешил записать
решение, зафиксируй состояние `creation_declined`; не подменяй отказ пустой или
неполной политикой.

## Процедура после подтверждения целей

Проектирование, внедрение и подтверждение имеют отдельные результаты. Общий
технический блокер останавливает зависимые проверки, но не отменяет подготовку
полного предложения. Сохраняемая конфигурация не становится рекомендацией
только потому, что уже существует.

1. Используй цели и приоритеты, подтверждённые или исправленные пользователем по `../SKILL.md`. Свяжи с ними
   критерии приёмки предложения, конфигурации и проверок отдельно. Установи
   режим и границы записи. Не считай экономию целью по умолчанию.
2. Определи активные оснастки по запросу, текущей среде и настройкам. Прочитай
   пользовательский и проектный слои, определения агентов, запускатели,
   ограничения и источники истины. Наличие исполняемого файла само по себе
   не делает оснастку активной. Установи модель и усилие текущей сессии
   по доступным метаданным. Настройки по умолчанию не подтверждают параметры
   текущего хода. Неизвестные значения сохрани явно.
3. Составь карту существенных задач по запросу, артефактам и примерам работы.
   Укажи ожидаемый результат, риск, неоднозначность, размер контекста, цену
   ошибки и приёмку. Проверь потребность в сборе фактов, анализе,
   проектировании, поиске и сравнении решений, реализации и проверке.
   Это проверка охвата, а не обязательный набор отдельных ролей.
   Для используемого проекта рекомендуй `analyze-subagent-sessions`.
   Сводка измеряет объём истории, но не доказывает состав задач. При отсутствии
   содержательной выборки назови границу охвата и опирайся на структуру проекта.
4. Получи каталог каждой активной оснастки через `discover-subagent-models`.
   Семейство служит условием поиска, точное назначение берётся из каталога.
   При сбое обозначь «список не получен», используй проверенные локальные
   данные либо запроси список у пользователя. Рассмотри прежние и новые
   подходящие кандидаты. Для сложных задач включи наиболее способных кандидатов
   по доступным сведениям. Рассмотрение не означает назначения. Название,
   привычка и цена не доказывают пригодность.
5. Выполни раздел «Выбор маршрута, модели и усилия» ниже.
   Сгруппируй задачи по возможностям, полномочиям и приёмке. Подготовка вариантов
   и рекомендаций допустима без права утверждения и записи источника истины.
   Для каждой существенной задачи заполни единую запись из
   `../assets/subagents.local.toml.sample`: предлагаемый маршрут и кандидат,
   основание, текущий маршрут, статус проверки и следующий шаг. Выбери
   предварительное назначение либо явно укажи неразрешённый выбор между
   кандидатами и различающее их свидетельство. Простого упоминания кандидата
   недостаточно. Маршрут родителя или человека обоснуй предметом задачи.
6. До технических запусков представь человеку полное предложение по этой записи.
   Для делегируемых классов задай входы, инструменты, область записи, запреты,
   схему результата, свидетельства, уверенность, остановку и бюджет.
   Проверь полноту предложения и одинаковое применение ограничений к старым
   и новым назначениям. Отдели причину сохранения конфигурации от рекомендации.
   Представление предложения не требует повторного разрешения уже порученного
   внедрения. Общий блокер не позволяет убрать новые маршруты из предложения.
7. Определи проверки, которые могут изменить выбор. Доступность проверь
   последовательными вызовами `check-subagent-models`. Для сравнительного
   выбора применяй `model-selection-evaluation.md`: предварительный
   отсев, пилот и последовательный выбор. До запуска зафиксируй договор и
   критерии содержательной приёмки. При общем отказе свидетельства модели
   оставь сравнение заблокированным для всех затронутых кандидатов и заверши
   предложение по шагу 6. Не запускай остальные модели ради того же отказа.
8. Для внедрения используй самый узкий долговечный слой. По умолчанию это
   пользовательская настройка либо `subagents.local.toml`, исключённый через
   `.git/info/exclude`. Политика в Git требует отдельного прямого согласия.
   При нескольких оснастках сохраняй один договор и отдельные назначения.
   Измени разрешённую конфигурацию. Невыполненные условия внедрения оставь
   явными в текущем маршруте, сохранив предлагаемое решение отдельно.
   Не выдавай запись в `AGENTS.md` за техническую настройку.
9. Проверь запуски по `routing-patterns.md`: модель, журнал, лимиты
   и расход. Используй `run-execution-class` с явными входами и, для профильного
   обязательства, `--obligation`. Назначение, самоотчёт и отдельный поток
   не подтверждают фактическую модель. Нужна проверяемая ссылка на событие
   исполнения. При отсутствии свидетельства или несовпадении не закрывай
   проверку. Если встроенный запуск не применяет модель, проверь отдельный
   процесс. Невозможность запуска обозначь как блокер только зависимой части.
10. Отдельно прими содержание результата каждого проверяемого класса на его
    задаче. Точность извлечения не подтверждает качество проектирования.
    При недостатке свидетельств сохраняй предварительный статус. Технический
    успех не подтверждает полноту политики, качество или экономичность выбора.
11. Перед ответом сопоставь единое предложение, сохранённые файлы и сам ответ
    с подтверждёнными или исправленными пользователем целями по
    `operation-policy.md`. Назови эти цели и покажи, как им отвечает
    схема. Ответ должен показывать существенные
    предлагаемые маршруты и кандидатов, текущие назначения и ограничения.
    Ссылка на отчёт не заменяет эту сводку. Раздельно оцени проектирование,
    внедрение и подтверждение. Укажи выполненные проверки и оставшуюся работу.
    Если запись запрещена, назови незафиксированные сведения явно.

## Выбор маршрута, модели и усилия

Для каждой существенной задачи выполни три отдельных решения. Учитывай
подтверждённые приоритеты пользователя. Экономия не является общей целью
всех проектов, а высокая цена ошибки не задаёт конкретную модель или усилие.

1. **Маршрут.** Сравни делегирование с прямым выполнением текущим родителем:
   возможности, усилие, доступный контекст, полномочия и критерии качества.
   Если родитель подходит, прямое выполнение — исходный вариант. Передача
   требует конкретной пользы по целям пользователя с учётом постановки,
   повторного контекста, исполнения, приёмки и исправлений. Более дешёвые
   токены или меньшая задержка отдельно не доказывают экономии всей задачи.
   Совпадение моделей не запрещает изоляцию контекста или полезную параллельную
   работу, но само по себе их не оправдывает. Обязательную отдельную проверку
   не заменяй самопроверкой. Проверь требуемый вид независимости.
2. **Модель.** Если передача оправдана, сопоставь подходящих кандидатов
   с требованиями задачи. Обоснуй выбор и пропуск подходящих альтернатив.
   Не требуется назначать каждую доступную модель или обязательно проходить
   промежуточную модель пробным вызовом. Существенность решения не доказывает
   необходимость самого способного кандидата. Если сведений недостаточно,
   сохрани предварительный выбор или неразрешённую альтернативу и назови
   свидетельство, которое позволит выбрать. Отсутствие основания для дорогого
   назначения не подтверждает пригодность дешёвого.
3. **Усилие.** Выбери его отдельно от модели. Различай поддерживаемое,
   штатное и достаточное для задачи усилие. Каталог подтверждает первые два,
   но не третье. Штатное значение допустимо как предварительная отправная
   точка с явным статусом. Повышение обоснуй конкретной потребностью задачи,
   например взаимодействием ограничений или длинной цепочкой зависимостей.
   Не повышай модель и усилие одновременно без отдельных оснований.
   Для пригодного родителя сначала рассмотри достаточность текущего усилия
   и возможность его изменения. Не объявляй изменение выполненным без
   подтверждения оснастки. Не выполняй перебор уровней ради заполнения таблицы.

Запиши основания и границы уверенности в едином предложении. При неизвестных
параметрах родителя не подставляй глобальные умолчания и не объявляй сравнение
завершённым. Отсутствующие сведения собери доступным способом. Они ограничивают
только зависимые выводы. Сравнительную пригодность и стоимость проверяй по
`model-selection-evaluation.md`, а не по названиям моделей или разбору TOML.

После коррекции пользователя перепроверь всю затронутую схему: общие правила,
кандидатные и прежние назначения, технические настройки и итоговый ответ.
Устрани противоречия в разрешённой области. Если старое назначение необходимо
сохранить, явно назови причину, последствие и условие замены. Не добавляй
новое исключение поверх противоположного правила. Не повторяй проверки
неизменных частей. Согласованные цели в продолжении не требуют нового вопроса.

## Право на запись

По умолчанию подагенты работают без записи. Отдельный подагент с правом записи
допустим только для малых обратимых правок, когда родитель явно задал файлы или
узкую область записи, запретил менять источники истины и может дёшево проверить
различия.

Подагентам запрещено принимать проектные решения, расширять область задачи,
утверждать результат, менять правила, навыки, шаблоны, `AGENTS.md`,
архитектурные решения, требования и другие источники истины.

Подготовка вариантов, анализ последствий и рекомендация допустимы в рамках
контракта без права утверждения. Родитель принимает результат подагента,
а решение, закреплённое за человеком, передаёт владельцу.

## Что читать дополнительно

- `operation-policy.md` — режимы работы, пользовательское
  взаимодействие, конфигурация оснастки, выбор моделей, право на запись и приёмка.
- `routing-patterns.md` — матрицы маршрутизации, контракты,
  шаблоны результата, конфигурация оснастки, запускатели, диагностика и измерение.
- `model-selection-evaluation.md` — проектные проверочные задания,
  предварительный отсев, последовательный выбор и накопление свидетельств.

## Формат результата

Для `policy` верни:

- цель и нецели;
- классы задач и уровни моделей;
- единое предложение по существенным задачам с кандидатами, основаниями,
  текущими маршрутами, статусами и незакрытыми проверками.
- контракты делегирования;
- правила эскалации;
- проверки качества;
- бюджетные ограничения;
- где предлагается хранить политику;
- открытые решения.

Для `implementation` и `repair` дополнительно верни:

- изменённые файлы и слой фиксации;
- активные оснастки, источник политики и способ исключения локального файла из Git;
- что осталось в `AGENTS.md`, что вынесено в локальную настройку или конфигурацию;
- возможности каждой активной оснастки и источник свидетельства по ним;
- классы, оставшиеся ненастроенными, и недостающую для них часть поставки;
- все проверенные модели, их адаптеры и результат запуска;
- способ проверки фактического запуска;
- результат проверки или блокер;
- остаточные риски и условия пересмотра политики.

## Ограничения

- Не выдавай политику маршрутизации за техническую настройку.
- Не считай один `AGENTS.md` полной настройкой подагентов.
- В переносимом навыке не называй конкретные модели и их поставщиков.
  Примеры кандидатов делай вымышленными, реальные назначения храни локально.
- Не подставляй конкретные модели без проверки доступности в текущей среде или
  явного списка пользователя.
- Не разрешай совпадение модели только по названию семейства, если локальная
  политика не содержит явный допустимый префикс фактического идентификатора.
- Не записывай в правила проекта обязательный шаг, исполнимый только в части
  активных оснасток, без пометки области действия, равноценной ветви или явно
  названного ограничения.
- Не подставляй в раздел `[adapters]` адаптер, который не отвечает каталогом на
  аргумент `list`. Отсутствующую возможность оснастки называй ограничением, а не
  заполняй файлом другого назначения.
- Не объявляй запись настройки проверенной, если она не подтверждена запуском
  того средства, которое эту запись читает.
- Не сохраняй настройки моделей в Git без отдельного прямого согласия пользователя.
- Не создавай сложную схему, если доступна только одна или две модели.
- Не меняй назначение модели автоматически по результату пилота. Даже статус
  `confirmed` служит основанием решения владельца, а не самим решением.
- Не добавляй отчётность по моделям и лимитам для задач без фактического
  запуска подагентов.
- Не выводи и не сохраняй тексты запросов, содержимое сессий или пути вне
  целевого проекта в отчёте анализа истории.
- Не исправляй общие дефекты `AGENTS.md`, Git-правил или документации внутри
  этого навыка; подключай профильный навык и фиксируй проектные правила в
  целевом проекте.
