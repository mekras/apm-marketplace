# Общие настройки и квалификация политики подагентов

Это этап `ai-setup-subagents`, а не отдельный маршрут настройки.
Сначала используй цели и доступные настройки из текущего разговора и среды.
Если общие настройки уже существуют, используй их без повторного создания.
При недоступности назови ограничение, не создавай замену молча.

Для одного проекта достаточно его защищённой локальной политики. Отдельное
пользовательское ядро и проектное уточнение нужны, когда пользователь хочет
разделять общие назначения и условия конкретных проектов. Не создавай их
как обязательный дополнительный слой каждой настройки.

`subagents.local.toml` остаётся приватной рабочей политикой проекта и может
содержать точные назначения. Публикуемое проектное уточнение содержит только
классы задач, критерии и ограничения. Не копируй в него приватное ядро.

Согласуй действующие настройки с `[policy_runtime]` и `policy_applicability`.
При расхождении останови зависимое назначение, не выбирай один файл молча.
Существующие свидетельства используй в их проверенной области. Проверка
формата не квалифицирует связку родителя и подагента и не включает её в
рабочую политику автоматически. Не запускай новые испытания без поручения.

## Без автоматизации

Средствами агента проверь защиту выбранных мест от фактической VCS, разделение
приватных назначений и проектных критериев, ссылки на маршруты и сохранность
обязательных свидетельств. Создавай или исправляй только разрешённые файлы.
Оставь `automatic = false` до доступной детерминированной проверки полного
свидетельства. Отсутствие Python или POSIX не требует установки среды.

## Дополнительная автоматизация

`scripts/execution-policy` требует Python 3.11 или новее и использует только
стандартную библиотеку. Установщик требует POSIX. Проверь среду перед запуском.
Если она недоступна, продолжи вручную и назови непроверенную часть.
Имена команд и форматы перенесены из прежнего навыка без смены схемы.

## Формат политики и проверка

Пользовательское ядро и свидетельства квалификации образуют приватный слой.
Путь к ядру выбирает пользователь. Внутри области VCS допустим только
исключённый из VCS файл либо явное решение пользователя сохранить его в
репозитории. Проектное уточнение можно вести в VCS, если в нём нет точных
моделей, цен, лимитов и данных учётной записи.

## Разделение материалов

| Материал | Где хранить | Что содержит |
| --- | --- | --- |
| Пользовательское ядро | Приватный пользовательский слой | Маршруты и их точные назначения, обязательные свидетельства, ссылки на квалификации |
| Проектное уточнение | Проект | Классы задач, критерии приёмки, дополнительные свидетельства, способ передачи, разрешённые маршруты |
| Свидетельство квалификации | Приватный пользовательский слой | Фактические маршруты, критерии, результаты, след интеграции, признак переделывания и отпечаток политики |

## Команды

Установщик копирует скрипт и два образца в `tools/` целевого проекта:

```bash
.apm/skills/ai-setup-subagents/scripts/install-execution-policy-tools .
```

Создание любого файла требует явного пути. Команда не перезаписывает
существующий файл.

```bash
tools/execution-policy init-user --output <путь-к-ядру>
tools/execution-policy init-project --output execution-policy.project.toml
tools/execution-policy prepare-qualification \
  --user-core <путь-к-ядру> \
  --project-overlay execution-policy.project.toml \
  --task-class проверяемая-задача \
  --output <путь-к-свидетельству>
tools/execution-policy check \
  --user-core <путь-к-ядру> \
  --project-overlay execution-policy.project.toml \
  --qualification <путь-к-свидетельству>
```

Команда `check` печатает действующую политику без точных назначений моделей,
источник каждого правила и классы, не применённые для выбранного класса. Она
отклоняет проектное уточнение, если оно содержит приватные поля, ослабляет
обязательные свидетельства или пытается автоматически применить
неквалифицированный маршрут.

## Свидетельство квалификации

`prepare-qualification` создаёт запись в состоянии `pending`. После сравнения
с эталонным маршрутом ответственный пользователь заполняет фактические маршруты,
пути к каждому обязательному свидетельству, результат каждого критерия и один
из статусов: `qualified` либо `rejected`.

Свидетельство также относится к приватному слою. Если его путь находится в
области Git, `prepare-qualification --git-storage` проверяет отсутствие отслеживания и
исключение файла. Для другой VCS или подтверждённого отсутствия VCS передайте
`--storage-verified` после проверки защиты конкретного места. Не используйте
этот флаг как обход проверки. `--allow-git` оставлен только для отдельного
решения пользователя разрешить версионирование приватного файла.

Для класса с `root_task = true` обязательны пути к следам фактических запусков
эталонного и кандидатного маршрутов. При эскалации свидетельство отдельно
фиксирует её причину и сохранённые результаты предыдущего этапа. Если все
результаты отброшены, `preserved_results` содержит пустой массив. При переделке
её причина и отброшенные результаты указываются в `route_evidence`. Признак
`rework_required` обязателен и не определяет допуск сам по себе: проверяются
конечные критерии всего маршрута. Если отсутствие переделок — обязательный
критерий задачи, повторная работа означает его непрохождение.

В проектном классе `candidate_steps` задаёт последовательность идентификаторов
маршрутов из пользовательского ядра, начиная с кандидата. По умолчанию это
один этап — кандидатный маршрут. `candidate_conditions` содержит по одному
условию на каждый переход, для одного этапа — пустой массив. Квалификация
охватывает именно эту последовательность и условия. Альтернативные ветви
проверяйте отдельно и не распространяйте допуск на непроверенную область.
Скрипт не исполняет переходы и не проверяет истинность их условий при запуске
реальной задачи. Это обязанность внешней интеграции и содержательной проверки.

Поле `route_evidence` в свидетельстве квалификации указывает на существующий
файл JSON, относительный путь отсчитывается от свидетельства. Он содержит:

- `scope`: `whole_route`.
- `candidate_steps`, `candidate_conditions`: проверенный план из политики.
- `actual_candidate_steps`: фактически выполненная последовательность.
- `transition_evidence`: пути к существующим файлам со свидетельствами
  срабатывания условий, по одному на переход в порядке плана. Для одного
  этапа — пустой массив. Содержательную связь условия и наблюдения проверяет
  ответственный за квалификацию.
- `rework_required`: тот же логический признак, что в квалификации.
- `criterion_results`, `result_evidence`: итоги конечных критериев и пути
  к обязательным свидетельствам всего маршрута, в формате основной записи.
  Относительные пути отсчитываются от содержащей их записи. Несуществующий
  файл не считается обязательным свидетельством.
- `assessment_basis`: расположение проверки условий, конечного качества,
  ограничений и области применимости вывода.
- При переделке: непустая причина `rework_reason`, массивы сохранённых
  `preserved_results` и отброшенных `discarded_results` результатов.

Незапланированная последовательность не наследует допуск. Изменение этапов,
условий переходов, назначения любой участвующей модели, среды, критериев,
обязательных свидетельств или способа передачи меняет отпечаток. Старое
свидетельство требует новой квалификации. Для ранее подготовленных записей
нужно создать и заполнить новое свидетельство всего маршрута, а не просто
переписать отпечаток.

Команда проверяет полноту и согласованность свидетельства и явно выводит
`evidence_check=structure_only`. Оценку качества, решение об эквивалентности
и содержание внешнего следа она не подменяет. Допуск по качеству сам по себе
не подтверждает экономию: для неё сравнивают полные расходы обоих маршрутов.
